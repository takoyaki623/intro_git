# 12. 敗北処理・お金・ショップ・道具

関連: [`battle-system.md`](battle-system.md) / [`endgame.md`](endgame.md) / [`regions.md`](regions.md) / [`world.md`](world.md)

---

## 1. 設計方針

[`battle-system.md`](battle-system.md) §9 は「全てのポケモンがひんしになった側の負け」で
止まっていた。**その後に何が起きるかが、どこにも書かれていなかった。**

本章は2つを扱う。

1. **敗北処理** ―― 負けたときに何を失い、どこに戻るか
2. **本編の経済** ―― お金・ショップ・道具

どちらも「周回構造では原作と同じにしてはいけない」という判断が中心になる。

## 2. 敗北処理（本編）―【決定】お金を失わない

原作では全滅時に所持金の一部を失う。**本作では既定で失わない。**

| 項目 | 扱い |
| --- | --- |
| 戻る場所 | **最後に利用したポケモンセンター** |
| 手持ち | **全回復** |
| お金 | **失わない**（既定） |
| 道具・進行フラグ | そのまま |

### 理由

お金を失うペナルティは、**時間を奪うだけで、プレイヤーに何も教えない。**
負けた原因（相性を見誤った、レベルが足りない）とペナルティの内容に関係がなく、
再挑戦までの作業時間が伸びるだけになる。

9地方を周回する本作では、この摩擦が9回積み重なる。
[`world.md`](world.md) の秘伝技廃止、[`capture.md`](capture.md) §8 の捕獲の軽量化と
同じ判断軸で、**周回の摩擦になるだけの要素は落とす。**

### ただし選べるようにする

```ts
type LossPenalty = "none" | "classic";   // classic = 所持金の一部を失う（原作準拠）
```

原作の緊張感を求める人のために設定で選べるようにする。実装は分岐1つで済む。
**既定は `none`。**

## 3. 敗北処理（エンドゲーム）

本編とは目的が違うため、扱いを分ける。

### 施設（連戦）

| 項目 | 扱い |
| --- | --- |
| 連勝 | **リセット。** `ActiveRun` を破棄する |
| BP | **節目までに確定したぶんは受け取れる** |
| 記録 | `bestStreak` を更新（更新できていれば） |
| 手持ち | 影響なし（レベル同期は一時的なもの） |

**「40連勝して負けたら全部ゼロ」にしない。** 節目ごとにBPを確定させる
（[`endgame.md`](endgame.md) §9 の「連勝数が上がるほど単価が上がる」と組み合わせる）。
全部ゼロにすると、高段位に挑む動機そのものが消える。

### トーナメント

そのカップは終了。再挑戦は自由で、参加費もない。
ティア解放（[`endgame.md`](endgame.md) §7）は優勝でのみ進む。

## 4. お金

### 収入

| 経路 | 内容 |
| --- | --- |
| トレーナー戦の賞金 | **トレーナークラスの基準額 × 相手の最高レベル** |
| 落ちている道具の売却 | |
| イベント報酬 | `giveMoney`（[`world.md`](world.md) §6） |

### 支出

| 経路 | 内容 |
| --- | --- |
| ショップでの購入 | 主経路（§5） |
| イベントによる支払い | `takeMoney`（[`world.md`](world.md) §6）。入場料・カジノ等 |

**個体を強くするものは、この経路では買えない**（§7）。

### 範囲

**地方をまたがない**（[`regions.md`](regions.md) §5）。
[`save-data.md`](save-data.md) §3 の通り、置き場所が `RegionProgress` の中にしかない。

## 5. ショップ

```ts
type Shop = {
  id: ShopId;
  stock: {
    item: ItemId;
    price: number;
    condition?: Condition;      // world.md §6 の Condition を再利用
  }[];
};
```

- **バッジ数に応じて品揃えが増える**（原作準拠）。`condition` に `badges >= n` を置くだけで表現できる
- 売却価格は購入価格の半額を既定とし、道具側で上書きできるようにする
- ショップは `world.md` の `{ kind: "shop"; inventory: ShopId }` コマンドから開く

`Condition` を `world.md` と共有するのが要点。品揃えの解禁条件のために
別の仕組みを作らない。

## 6. 道具

```ts
type Item = {
  id: ItemId;
  name: string;
  category: ItemCategory;
  price?: number;              // 未設定 = 買えない
  sellable: boolean;
  effect?: ItemEffect;         // 技効果と同じくデータ駆動のレジストリ方式
  usableIn: ("field" | "battle")[];
};

type ItemCategory =
  | "recovery"    // HP・PP・状態異常・ひんし
  | "ball"        // capture.md §3
  | "held"        // 戦闘中に持たせる
  | "evolution"   // progression.md §11
  | "training"    // progression.md §9。BP交換のみ
  | "tm"          // わざマシン
  | "key"         // 大切なもの。進行に関わる
  | "treasure";   // 売却用
```

`effect` は [`battle-system.md`](battle-system.md) §11 の技効果と**同じレジストリ方式**にする。
道具を1件足す = JSONを1行、を維持する。

## 7. 本編経済と BP経済の分離 ―【中心的な判断】

2つの通貨が存在する。**役割を厳密に分ける。**

| 通貨 | 範囲 | 買えるもの |
| --- | --- | --- |
| **お金** | **地方の中だけ** | 消耗品・ボール・基本的な持ち物 |
| **BP** | **全体共通・恒久** | 育成アイテム・レア持ち物・わざマシン・教え技・幻ポケモン |

### 原則：お金では個体を強くできない

> **個体を強くする手段は、すべて BP 側に置く。**

理由が2つある。

1. **お金は地方内で完結し持ち越さない。** そこで育成できてしまうと、
   「お金を稼ぎやすい地方」が有利になり、地方間の対称性が崩れる
2. **エンドゲームを唯一の成長の受け皿にする。**
   [`progression.md`](progression.md) §10 で「施設を遊ぶ → BPを稼ぐ → 個体を強化する →
   上位に挑む」の循環を主動線に据えた。お金でも強化できると、この動線が二重になって薄まる

お金は「その地方を攻略するための消耗品を買う」ためだけのものと位置づける。
地方をクリアした時点で役目が終わり、持ち越さないのが自然になる。

### わざマシンの扱い

わざマシンは両方に登場するが、意味が違う。

- **ショップで買えるもの**: その地方の攻略に使う基本的な技
- **BP交換のみのもの**: 対戦で強力な技・教え技（[`progression.md`](progression.md) §8）

## 8. 検証項目

[`data-schema.md`](data-schema.md) §6 に追加する。

| 項目 | 根拠 |
| --- | --- |
| `training` カテゴリの道具に `price` が設定されていない（＝お金で買えない） | §7 の原則 |
| ショップの `stock` の全 `item` が存在し、`price` を持つ |  |
| 全 `ItemEffect.kind` にハンドラが登録されている | §6 |
| 売却可能な道具に売値が導出できる |  |

**§7 の原則を、CIで守る。** 「お金では個体を強くできない」を運用ルールにせず、
`training` カテゴリに価格を付けたら検証が落ちる形にする。

## 8.5 v0.9 の実装記録

道具・ショップ・BP交換所・本編の敗北処理が入り、この章のほぼ全部が動く形になった。

### 「持たせる効果」と「使う効果」を別の欄にした

`HeldEffect`（持たせる）と `UseEffect`（バッグから使う）を**別の型・別の TSV 欄**にした。

同じ「道具の効果」に見えるので1つにまとめたくなるが、発動条件も対象も違う。
混ぜると **「持たせると回復し続けるきずぐすり」** のような、意味の無い組み合わせが
型として通ってしまう。分けたことで、検証項目 #63（recovery カテゴリなのに使えない）と
#64（使えるのに使い切りでない）が書けるようになった。

`UseEffect` の種類は5つ（`heal` / `healRatio` / `cure` / `revive` / `pp`）だけで、
きずぐすり・いいキズぐすり・すごいキズぐすりは**同じ `heal` の数値違い**。
道具を1種足すのは TSV を1行足すことで、コードは1行も増えない。

かいふくのくすり（全回復 + 状態異常）だけは合成が要ったので、
`Condition` の `and` / `or` と同じ形で `multi` を足した。**1つでも効けば成功**にしてある
―― HP が満タンでも状態異常は治ってほしいため。

### バトル中とマップ上で、同じ実装を通す

回復量の計算を2箇所に書くと、いつか片方だけずれる。
そこで対象を `UseTarget`（HP・状態異常・PP の3つだけ）に揃えてから渡す形にした。
バトル中は `BattlePokemon`、マップ上は `PokemonInstance` ―― 型は違うが、
**道具が触るのはこの3つだけ**なので1つにできる。

テストは「回復量が同じであること」を直接確かめている（`use-item.test.ts`）。

### 持ち物が、v0.5 から4バージョンぶん誰にも届いていなかった

**バトル側の持ち物効果は v0.5 から動いていたが、本編で持たせる手段が無かった。**
35種のハンドラが、施設の貸しポケモンでしか働いていなかったことになる。

§7 の「BP交換のみの持ち物」を実装したことで初めて気づいた。
[`README.md`](README.md) の「検証が通ることと目的が達成されていることは別」の
3例目にあたる ―― 型も検証もテストも、この状態を1度も咎めなかった。

繋いだ瞬間に、`writeBack` が**消費された持ち物を戻していなかった**ことも露見した。
きのみを1回使うと永久に消えるべきなのに、instance には残り続けていた。
施設は毎回作り直すので、そこでは誰も踏まなかった。

### お金と BP が混ざらないことを CI で守る

§7 の「お金では個体を強くできない」を、検証項目 #66（お金でも BP でも買える道具を作らない）と
#67（お金でも BP でも手に入らない持ち物を作らない）にした。
**運用ルールにせず、データを書き換えたら落ちる形にしてある。**

### 敗北処理

§2 のとおりに実装した。戻り先は `RegionProgress.respawn`。
「最後に利用したポケモンセンター」は、`healParty` イベントが起きた場所を
そのまま復活地点にする形で表した ―― **回復してくれた場所が戻る場所**という規則を、
回復イベント側に持たせている。ポケモンセンターを1軒足すのに、コードは要らない。

`lossPenalty: "classic"` は所持金の半分。既定は `none`。

## 9. 実装の段階

| 版 | 内容 |
| --- | --- |
| **v0.5** | 施設の敗北処理（連勝リセット・BP確定）。持ち物としての道具 ―― **実装済み** |
| v0.7 | 落ちている道具の取得 |
| **v0.9** | バッグ・道具の使用・ショップ・**本編の敗北処理**・BP交換所 ―― **実装済み**（§8.5） |
| v0.10 | バッジ連動の品揃え |

**敗北処理は施設側（v0.5）が先に来る。** マップより施設が先に実装されるため
（[`../game-plan.md`](../game-plan.md) §8）、「拠点に戻る」処理より
「連勝リセット」処理の方が先に必要になる。

### 施設の敗北処理で決めたこと（v0.5 実装時）

> **連勝はリセットされるが、そこまでに確定した BP は残す。**

「20連勝して負けたら全部消える」形にすると、挑戦そのものが割に合わなくなる。
§2 の「ペナルティは時間を奪うだけで何も教えない」という判断軸を、施設側にも適用した。

持ち物は32種を投入した。**価格の有無で入手経路を分けている。**

| 種類 | 価格 | 入手 |
| --- | --- | --- |
| タイプ強化アイテム18種（もくたん等） | あり | お金で買える「基本的な持ち物」 |
| こだわり系・いのちのたま・たべのこし等14種 | なし | BP・報酬のみ（§7 の「レア持ち物」） |

§7 の通貨の分離を、価格欄の有無というデータの形で表している。
