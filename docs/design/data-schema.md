## 1. 設計方針

[`README.md`](README.md) の線引きで「**今、完璧に確定させるもの**」の筆頭がデータ構造だった。
理由は単純で、**後から変えると全データの作り直しになる**から。

数千件のデータが載った後にスキーマを変えるのは、実質的に不可能になる。
ここだけは実装前に固めきる。

### 正はどこにあるか

| 層 | 役割 |
| --- | --- |
| `packages/data/schema/*.ts`（zod） | **最終的な正。** ランタイム検証とTS型の両方をここから導出する |
| 本章 | そのスキーマの設計。全体像と設計意図 |
| 01〜07 各章の型定義 | **説明用の抜粋。** 差分が出たら本章とスキーマが優先 |

各章に型を再掲したままにすると必ずずれる。**「正は zod スキーマ、設計は本章」**を規則とする。

## 2. 静的データと動的データの境界

**本章で最も重要な構造上の判断。**

| 種別 | 内容 | 保存先 | 変わるタイミング |
| --- | --- | --- | --- |
| **静的データ（マスタ）** | 種族・技・特性・道具・トレーナー・地方・施設定義 | リポジトリ内の JSON | **開発時のみ** |
| **動的データ（セーブ）** | 手持ち・ボックス・図鑑・BP・進行状況 | ブラウザのストレージ | プレイ中 |

### 動的データは静的データを ID で参照するだけにする

```ts
// ❌ セーブに種族の中身を埋め込む
{ species: { id: "pikachu", baseStats: {...}, types: [...] } }

// ✅ IDだけを持つ
{ species: "pikachu" }
```

埋め込むと、**バランス調整で種族値を変えた瞬間に既存セーブが古い値を持ち続ける**。
9地方ぶんの長期プレイを前提にする以上、これは致命的になる。
（セーブの互換性は [`save-data.md`](save-data.md) で扱う）

## 3. ID体系 ― 1,000件超を型で守る

IDを `string` にすると、数千箇所の参照でタイプミスが検出されない。

**決定: IDのユニオン型を JSON から自動生成する。**

```
packages/data/**/*.json   （正）
        │
        │ tools/gen-ids.ts
        ▼
packages/data/generated/ids.d.ts
        │
        ▼
type SpeciesId = "bulbasaur" | "ivysaur" | ... ;   // 1,025要素
type MoveId    = "tackle" | "thunderbolt" | ... ;  // 約920要素
```

- **エディタで補完が効き、タイプミスがコンパイルエラーになる**
- 1,000要素程度のユニオンは TypeScript が問題なく扱える
- 生成物はコミットする（CIで再生成し、差分があれば失敗させる）

数千件のデータを人力で書く以上、この投資は確実に回収できる。

> **【v0.7 で判明・v0.9.5 で決着】生成した型を誰も import していなかった。**
> `tools/gen-ids.ts` は v0.4 から動き、CI の `--check` も通っていた。
> だが `SpeciesId` は今も `string` のままで、生成した `GeneratedSpeciesId` を
> 参照している箇所が1つも無かった。「補完が効く」「タイプミスがコンパイルエラーになる」という
> 目的は、**5バージョンにわたって1つも達成されていなかった。**

### 3.1 v0.9.5 の決着 ― 主張の方を現実に合わせた

v0.9.5 で繋ごうとして、**この構造では型として効かない**ことが分かった。
借りの正体はコードの不足ではなく、**上の主張が大きすぎたこと**だった。

| 繋げなかった理由 | 内容 |
| --- | --- |
| **TS は JSON の文字列を広げる** | `facilities.json` の `"battle-towr"` は `string` として読まれる。ユニオンで検査するのは**原理的にできない**。`satisfies` も通らない |
| **`GameData` 注入の意味が壊れる** | `gameData.species(id)` を狭めると `PokemonInstance.species`（設計上 `string`）を渡せない。core は「2種2技だけの `GameData`」でも動かねばならず、151種に縛った時点でそれが崩れる |
| **ID は `string` として流れる設計** | セーブから読んだ値・ユーザ操作で選ばれた値は、どこかで必ず `string` になる |

さらに調べると、**生成ユニオンが防げる「静かな失敗」が1つも見つからなかった。**

| 誤りの入り口 | 今どう落ちるか |
| --- | --- |
| JSON に書いた存在しない ID | `validate` #49 がエラー（実績あり） |
| コードから存在しない ID を引く | `MissingDataError` が実行時に投げる |
| 生成物が古い | `npm run check` が落とす |
| `MANUAL_REJECT` のような手書きリストの ID | **そもそも生成ユニオンに含まれない**（除外対象なので） |

**どれもうるさく失敗する。** 型で守る価値があるのは「静かに間違う」ものだけなので、
生成ユニオンの出番は狭い。

#### 決めたこと

> **JSON に書いた ID の持ち主は型ではなく `tools/validate.ts`。**
> **型で守るのは「人が TS にリテラルで書いた ID」だけ。**

`packages/data/src/ids.ts` に恒等関数（`mapId()` / `speciesId()` …）を置いた。

```ts
export const START: Place = { map: mapId("kanto-players-house-1f"), … };
//                                  ^ 打ち間違いはここでコンパイルエラー
```

**返り値は `string` に広げる。** 狭いまま返しても受け取る側（core の `string`）で
どうせ広がるのに、「狭い型が流れている」という誤解だけが残るため。
やりたいのは**書いた瞬間の検査**であって、型を持ち回ることではない。

適用範囲は現時点で `player.ts` の1箇所。**少ないのが実態で、増やすために
偽の用途を作らない。** 拠点（v0.10）とジム（v0.12）でマップ ID を手書きするので、
そこで自然に増える。

#### 教訓

**「検証が通っている」は「目的が達成されている」の証拠にならない**（`README.md` 参照）。
そしてこの件の返し方は、**足りないコードを書くことではなく、達成していない主張を降ろすこと**だった。
目的を現実に合わせて書き直すのも、借りの返し方の1つとして残す。

### 命名規則

- ID は **英小文字ケバブケース**（`hyper-beam`, `kanto-route-1`）
- 表示名は日本語で `name` フィールドに持つ。**IDに日本語を使わない**
- ID は一度公開したら変更しない（セーブが参照するため）

## 4. ファイル構成

```
packages/data/
  schema/                  zod スキーマ（正）
  generated/               自動生成のID型
  species/                 図鑑番号帯で分割（001-100.json 等）
  moves/
  abilities/
  items/
  type-chart.json
  exp-tables.json        成長曲線6種 × Lv100。tools/gen-exp-tables.ts が生成
  natures.json
  battle-sets/             施設の相手プール（grade別）
  facilities/
  tournaments/
  regions/
    kanto/                 ← 1地方 = 1ディレクトリ = 1リリース
      region.json
      flags.json           宣言済みフラグID一覧（world.md §6）
      encounters/
      trainers/
      named/
      maps/                変換済みマップ（world.md §2）
      events/              イベントスクリプト（world.md §6）
      shops/               ショップの品揃え（economy.md §5）
    johto/
    ...

  source/
    maps/                  マップの原本（*.map テキスト）。world.md §2.1
    *.tsv                  種族・技・特性・道具などの原本

  ../../assets/            グラフィック・音声。コードからパス依存しない
  ../../maps-src/          Tiled の原本（*.tmx）。ビルド対象外・コミット対象外
```

**Tiled の原本は `packages/data/` の外に置く。** 制作時の中間成果物であり、
ゲームが読むのは変換後の JSON だけ（[`world.md`](world.md) §2）。

> **v0.7 の実装状況:** 地方ごとのディレクトリ分割はまだ行っていない。
> マップ4枚・イベント15件の段階で先に分けると、参照の解決だけが複雑になる。
> 現状は `packages/data/{maps,events,encounters,trainers,flags}.json` の平置きで、
> **`region` フィールドは最初から全マップに入れてある**ので、
> v0.10（カントー全域）で分割するときに情報が足りなくなることはない。
>
> マップの原本は `source/maps/*.map` に置いた。Tiled ではない理由は
> [`world.md`](world.md) §2.1。この形式は**数値と構造だけなのでコミットできる**
> （`maps-src/` が入れられないのとは事情が違う）。

**地方ごとにディレクトリを完全に分ける。** [`regions.md`](regions.md) §8 の
「1地方 = 1リリース」を、ファイル構成のレベルでも成立させる。
新地方の追加が既存ファイルに触らない形になる。

### 進化 ― 章をまたぐため、ここで定義する

[`progression.md`](progression.md) §11 と [`capture.md`](capture.md) §7 の
到達可能性検証の両方が参照する。

```ts
type Evolution = {
  from: SpeciesId;
  to: SpeciesId;
  condition:
    | { kind: "level"; level: number }
    | { kind: "item"; item: ItemId }
    | { kind: "friendship"; min: number }
    | { kind: "link"; heldItem?: ItemId }   // 通信交換進化の代替
    | { kind: "knownMove"; move: MoveId }
    | { kind: "location"; location: LocationId }
    | { kind: "custom"; id: string };
};
```

`condition` を判別可能な共用体にすることで、**到達可能性の検証スクリプトが
条件アイテムの入手経路まで辿れる**（[`capture.md`](capture.md) §7）。
条件を自由文字列にすると検証が不可能になる。

### トレーナー系

| 型 | 定義章 | 用途 |
| --- | --- | --- |
| `Trainer` | [02](named-characters.md) | 一般トレーナー |
| `NamedCharacter` | [02](named-characters.md) §7 | ネームド。`concept` + 3ティア |
| `BattleSet` | [06](endgame.md) §6 | 施設の相手プール・レンタル |
| `AiConfig` | [07](ai.md) §3 | policy × mistakeRate × knowledge |

**`Party` 型を3者で共有する。** `NamedCharacter.tiers` も
`BattleSet` からの生成結果も、最終的に同じ `Party` になる。
バトルエンジンは出自を区別しない。

### 世界・進行系

| 型 | 定義章 |
| --- | --- |
| `RegionDefinition` | [05](regions.md) §8。`challenge` でジム制/島巡り/オープンを表現 |
| `EncounterTable` | [04](capture.md) §9 |
| `Facility` / `Tournament` / `Ruleset` | [06](endgame.md) §4, §11 |
| `HallOfFameEntry` | [05](regions.md) §7 |
| `MapData` / `Warp` / `MapObject` | [11](world.md) §3, §4 |
| `EventScript` / `EventCommand` | [11](world.md) §6 |
| `Shop` | [12](economy.md) §5 |

`Ruleset` は `Facility` と `Tournament` の**両方が持つ**。ここが施設量産の要。

### `Condition` ― 章をまたぐため、ここで所在を明示する

[`world.md`](world.md) §6 で定義した `Condition`（フラグ・バッジ数・所持品による分岐）を、
**イベント分岐・NPCの出現条件・ショップの品揃え解禁**の3箇所が共有する。

用途ごとに別の条件型を作らないこと。分岐の仕組みが3つに分かれると、
検証も3回書くことになる。

## 6. 検証 ― 設計ルールを機械検証に落とす

**本章の中心的な狙い。**

> 設計文書に書いたルールのうち、機械検証できるものは**全て検証項目に落とす。**
> 文書は読まれなくなるが、**CIは必ず実行される。**

### v0.8 で意味が変わった検証項目

公式 learnset を入れた結果、**暫定データ用に書いた品質条件が、原作の事実とぶつかった。**

| # | 項目 | v0.7 まで | v0.8 |
| --- | --- | --- | --- |
| 5 | Lv5 までに攻撃技を覚える | ❌ エラー | ⚠️ 一覧の報告（7種） |

| **59** | **野生で出る種が Lv5 までに技を覚える** | ― | ❌ **新設・エラー** |
| **60** | **「調べる」warp が歩けるマスに無い**（乗ってしまって起動できない） | ― | ❌ **新設・エラー** |

**規則が守るべき品質条件と、事実を写しただけのデータは、扱いが違う。**
前者は生成器のバグなのでエラーにしてよい。後者は原作がそうなっているだけで、
エラーにすると「正しいデータを入れられない」状態になる。

代わりに新設した #59 は**遊べるかどうか**に直結する ――
野生で出る種が わるあがき しかできないと戦闘が成立しない。
「データの正しさ」ではなく「成立するか」を見る検証に置き換わった。

**未追加の技は理由つきで残す。** `source/moves-todo.tsv` に155件、
それぞれ「効果を表せない」「場の効果」「制約が強さを釣り合わせている」等の理由が付く。
`inert` な特性に理由を書かせているのと同じ運用で、
**入れていないことと入れ忘れを区別できるようにする**ため。

## 8. 作業手順 ― コンテンツを1件足す

本設計の中心原則は「**コンテンツを1件足すコストをゼロに近づける**」
（[`README.md`](README.md)）。その手順を明示する。

### 追加の順序（依存があるため守る）

```
技 → 特性・持ち物 → 種族 → 出現テーブル → トレーナー / BattleSet / ネームド
```

種族の `learnset` は技を参照し、出現テーブルは種族を参照する。
**逆順で足すと参照が壊れ、検証（§6）が落ちる。**

### 技を1件追加する

1. `packages/data/moves/` に1件足す

```json
{
  "id": "thunderbolt", "name": "10まんボルト", "type": "electric",
  "category": "special", "power": 90, "accuracy": 100, "pp": 15,
  "priority": 0, "target": "foe",
  "effect": { "kind": "status", "status": "paralysis", "chance": 10 }
}
```

2. `effect.kind` が**既存のものなら、ここで終わり。コードは一切触らない**
3. 新しい `kind` が要る技だけ、`MoveEffect` に型を足し `effectHandlers` に
   ハンドラを1つ書く（[`battle-system.md`](battle-system.md) §11）
4. `tools/gen-ids.ts` が `MoveId` を再生成 → 以降エディタで補完が効く
5. `tools/validate.ts` が検証（ハンドラの登録漏れ、参照の存在）

### ポケモンを1件追加する

1. `packages/data/species/` に1件足す。必要な項目:

| 項目 | 備考 |
| --- | --- |
| `dexNo` / `name` / `types` / `baseStats` | |
| `abilities`（通常・隠れ） | [`progression.md`](progression.md) §6 |
| `learnset` | **技が先に存在している必要がある** |
| `catchRate` | [`capture.md`](capture.md) §2 |
| `expType` / `evYield` | [`progression.md`](progression.md) §7・§4 |
| `genderRatio` | [`progression.md`](progression.md) §13 |
| `evolutions` | §5 の `Evolution` |

2. **入手経路を必ず用意する。** 出現テーブル・進化・イベント報酬・施設報酬のいずれか。
   用意しないと**到達可能性の検証（§6 #9）で落ちる**
3. ID型の再生成 → 検証

**種族の追加でコードを書くことは、原則としてない。**
フォルムチェンジ等の新しい機構が要る場合のみ例外。

### コードを書くことになるのはどんなときか

これが本設計で最も重要な性質。

| 追加するもの | コードが要るか |
| --- | --- |
| **種族 1,025件** | **不要**（1行も増えない） |
| 技 920件 | **効果の種類ぶんだけ**（数十）。個々の技は不要 |
| 特性 310件・持ち物 | 同上 |
| トレーナー・ネームド | 不要 |
| 出現テーブル・マップ・イベント | 不要 |
| 施設・カップ | 不要（`Ruleset` の差し替え） |

**「全ポケモンが出る」は実装課題ではなく入力作業になる** ―― という当初の方針
（[`../game-plan.md`](../game-plan.md) §3）は、この表が成立することを指している。

### 大量に投入する（v0.4 の `tools/`）

151種を手で書くのは現実的ではないため、v0.4 で以下を用意する
（[`../game-plan.md`](../game-plan.md) §8.0）。

| ツール | 役割 |
| --- | --- |
| `tools/import.ts` | 表計算等の一括入力形式 → JSON |
| `tools/scaffold.ts` | 1件追加時の雛形生成（必須項目の書き漏らしを防ぐ） |
| `tools/gen-ids.ts` | ID のユニオン型を生成（§3） |
| `tools/validate.ts` | 全検証項目を実行（§6）。CI で回す |
| `tools/convert-map.ts` | Tiled → 自作スキーマ（[`world.md`](world.md) §2） |

**v0.4 より前（v0.1〜v0.3）は手書きで足りる**（5種8技 → 20種40技）。
ツールが必要になるのは 151種を入れる段階から。

- データのロード方式（全件を初期ロードするか、地方単位で遅延ロードするか）
- `tools/` の入力形式（表計算か、独自の中間形式か）
