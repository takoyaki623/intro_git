バージョン別の実装

各版は前の版の上に積む。番号は実際の依存順序を表す。

v0.1

バトルの骨格

目的は機能の完成ではなく アーキテクチャの証明。設計が間違っていた場合に最小の傷で分かる形にする。データは5種・8技・攻撃技のみ。

実装

  • GameData interface による依存性注入 — core はデータを静的 import しない
  • toBattlePokemon — 3つの出どころ (実個体 / 設計図 / BattleSet) を入口で1つに正規化。levelOverride が後のレベル同期の入口
  • step(data, state, actions) — 「状態＋入力 → 新状態＋イベント列」の純関数。呼び出し元の state は不変
  • シード固定の疑似乱数 (xorshift32)。消費回数も状態に保持
  • ダメージ計算・18×18 タイプ相性・命中判定・急所・PP消費・優先度・素早さ順
  • Action 型は4種すべて定義し、move のみ実装

完了条件の達成

  • 達成 ランダムAI同士が1,000戦して例外なく決着 (無限ループ検出つき)
  • 達成 同一シードで2回流して結果が完全一致

実装して判明したこと

設計文書に「わるあがき」の記述が無かった。 PP が尽きると両者が行動不能になり、バトルが永久に終わらない。 完了条件が「1,000戦が例外なく決着する」なので、ここで必ず引っかかる。 文書レビューを5回やっても出てこなかった種類の穴で、実装したから見つかった。
v0.2

バトルの完成

骨格の上に、バトルとして成立するための要素を積む。データを20種41技へ拡張。

実装

  • 状態異常6種＋混乱 — タイプ無効・スリップダメージ・行動阻害・解除条件
  • 能力ランク補正 (−6〜+6) — 攻撃系と命中/回避で別の倍率表。急所は相手の防御上昇と自分の攻撃下降を無視
  • 交代 — 手持ちを配列化。ひんし後は pendingSwitch で交代を要求し、その間ターンを進めない
  • 変化技と効果レジストリの本格運用 — status / confuse / flinch / statChange / heal / multiHit を追加
  • 命中判定に命中/回避ランクを反映

設計原則の実証

41技すべてが JSON のデータだけで表現できた。 技を1件追加するのに書いたコードは 0行。 新規に書いたのは「効果の種類」6つぶんのハンドラだけ。 「コンテンツを1件足すコストをゼロに近づける」という設計方針の実測値になる。

設計文書の誤りを1件修正

  • もうどくは交代でカウンタが1に戻るだけで、通常のどくには戻らない。文書は「通常のどく扱いに戻る」としていたが原作の挙動と違っていた
v0.3

バトル画面

ブラウザで1戦を通しで遊べる状態にする。プレイヤー vs ランダムAI の 3対3。

実装

  • 技選択 (タイプ色・威力・PP)・交代・強制交代・HPバー・状態異常バッジ・能力ランク表示・手持ち残数・バトルログ
  • 高速モード3段階 (通常 / 高速 / ログのみ) — 周回に耐える操作の軽さ
  • seed 入力で同一バトルを再現 — 決定性が画面上の機能になる
  • アセット不在時のフォールバック (タイプ色の図形) — 通常動作の1つとして実装
  • ライト/ダーク両対応、520px 以下で1カラム

設計判断の変更

Phaser の導入を v0.7 (マップ探索) まで遅らせた。 v0.3 には絵が1枚も無く、設計上 Phaser が担当する「世界の描画」が存在しない。 「世界」が無い段階でゲームエンジンを入れる理由がないため、DOM だけで完結させた。

実機検証で見つけた不具合

  • 修正済 テーマが prefers-color-scheme だけで判定され、閲覧側の明示的なテーマ指定に追随しなかった
  • 修正済 スマホの長押し選択・ダブルタップ拡大が抑制されていなかった
  • 修正済 じこさいせいの PP が10 (第8世代の値)。第9世代では5
v0.4

データ基盤とカントー151種

手入力から解放される回。以降の全ての版がこの基盤に乗る。20種41技 → 151種105技。

実装

  • tools/import.ts — TSV（人が編集する形式）→ JSON。種族値の合計を冗長に持ち、各能力の和と照合する。151件すべて一致
  • tools/gen-ids.ts — ID のユニオン型を JSON から生成。数千箇所の参照をコンパイル時に守る
  • tools/validate.ts — 設計文書のルールを機械検証に落とす。CI で回す
  • tools/scaffold.ts — 1件追加時の雛形生成

実装して判明したこと

「原作の機構を必要とする技」を威力だけ写すと、原作より強い別の技になる。 はかいこうせんは 次ターン動けない から威力150が許されている。 反動を実装しないまま入れると、単に壊れた威力150の技になる。 該当する技を NEEDS_UNIMPLEMENTED_MECHANIC として列挙し、 機構が無いのにデータが存在したら検証が落ちる形にした。5件を差し替え。
gen-ids.ts --check が何も検証せずに通っていた。 「自分が直接実行されたときだけ動く」というガードが実行環境で成立せず、 CI が静かに素通りしていた。無条件実行に変更し、終了コード1を確認した。

learnset は暫定

  • 151種の習得レベルの正確なデータが手元に無いため、規則生成した暫定値を learnsetSource: "provisional" と宣言して持つ
  • 検証が毎回「151/151 が暫定」と報告する。差し替え期限は v0.8（育成）。それまで learnset は体験に影響しない
  • 生成規則には品質条件を入れた ―― 攻撃技のタイプが必ず2種類以上（ノーマル単はゴーストに詰む）、得意な攻撃側と技の分類が噛み合う（とくこうが倍あるのに物理技だけ、を防ぐ）
v0.5

バトルタワー

エンドゲームの最初の形。連戦が成立し、記録が残るところまで。特性・持ち物・ルールセット・AI basic・最小セーブ。

実装

  • 特性・持ち物の機構 — 効果35種のレジストリ。特性48種（うち37種が戦闘中に働く）・持ち物32種
  • Ruleset 駆動の施設 — 施設 = ルールセット + 相手プール + 報酬 の3データ。2つ目の施設でコードは1行も増えていない
  • BattleSet 64件 — 施設の相手を1体単位のプールから抽選して組む。同じプールがレンタルにも使われる
  • AI basic と AiView — 相手の実数値・控え・持ち物が見えない形を型で強制する
  • 最小セーブ — SaveStore interface と localStorage 実装。構造は最終形の部分集合
  • 編成・連戦・結果の画面。フリーバトルと施設が同じ「1戦を進める画面」を共用する

設計判断

特性と持ち物でレジストリを分けなかった。 設計では別々の型だったが、実装すると効果が実際に重なった ―― あついしぼう（特性）と タイプ半減の実（持ち物）、がんじょう と きあいのタスキ。 分けると同じ効果を2回書くことになるため、HeldEffect という 1つの語彙に統一し、ハンドラも1つのレジストリにまとめた。

実機検証

  • 確認 iPhone 13 サイズ・テーマ3状態・横スクロールなし・JSエラーなし
  • 確認 ランダムに押すだけの自動操作で13連勝・40BPまで到達し、リロード後も記録が残る

バトル仕様の詳細

ダメージ計算 (第9世代準拠)

基礎 = floor(floor(floor(2 × Lv / 5 + 2) × 威力 × A / D) / 50) + 2
       A・D には特性/持ち物による実数値の倍率を適用（こだわり系・こんじょう等）

補正の適用順:
  3. 急所 ×1.5      (相手の防御上昇と自分の攻撃下降を無視)
  4. 乱数 85〜100%   (16段階の整数から抽選)
  5. タイプ一致 ×1.5
  6. タイプ相性 ×0 / 0.25 / 0.5 / 1 / 2 / 4
  7. やけど ×0.5     (物理技のみ。こんじょう等は無視)
  8. その他          (持ち物・特性 — v0.5 で追加)
最低ダメージ 1 (相性0倍を除く)
手計算との一致を検証済み。 Lv50 ピカチュウ (とくこう70) の10まんボルト → ラプラス (とくぼう115・HP205) は 基礎26 → タイプ一致39 → 相性2倍 で 78。実装の出力と1の位まで一致する。 この値は reference-data.test.ts で固定してある。

06

特性・持ち物のレジストリ

特性は約310種、持ち物は数百ある。1つずつ if を書く構造にすると、 「コンテンツを1件足すコストをゼロに近づける」という中心原則が崩れる。技効果と同じ形にした。

特性と持ち物で語彙を分けない。 Ability.effect と Item.held は同じ HeldEffect 型を指し、 ハンドラも1つのレジストリに入る。分けると、あついしぼう（特性）と タイプ半減の実（持ち物）を 2回実装することになる。 
// 効果の種類 → 必要なフックだけを実装したハンドラ
const heldHandlers = {
  pinchBoost:  { attackMultiplier: (e, c) => ... },      // もうか・げきりゅう
  typeAbsorb:  { absorb:           (e, c) => ... },      // ふゆう・ちょすい
  endure:      { endures:          (e, c) => ... },      // がんじょう・きあいのタスキ
  contactStatus: { onContacted:    (e, c) => ... },      // せいでんき・ほのおのからだ
  ...
};

効果の種類 35

ダメージ倍率・実数値・命中・急所・無効化・登場時・接触時・ターン終了・きのみ発動など、25のフックを持つ。 特性48種と持ち物32種の計80件が、この35種の組み合わせで表現されている。

コードを書く回数

特性・持ち物を1件足すのは TSV に1行。 たとえばタイプ強化アイテムは18種あるが、効果の種類は typeBoost 1つで、 18行のデータになっている。

エンドゲーム ― ルールセット駆動の施設

施設をハードコードしない。施設 = ルールセット + 相手プール + 報酬 の3つのデータで定義する。 これが「施設を安く量産する」ための土台になる。

type Facility = {
  ruleset: Ruleset;        // 編成・バトル・連戦のルール
  rentalGrade: Grade;      // 貸し出す個体の強さ（相手より上に置く）
  bands: GradeBand[];      // 連勝数 → 相手の grade と AI
  bpByStreak: {...}[];     // 連勝数 → 1戦あたりの BP
  streakCap: number;       // v0.5 の上限（AI smart と同時に解除）
};
施設レンタル相手 (1〜10 / 11〜20)1戦の BP制覇率
バトルタワーgrade 4grade 1 → 22 〜 845 / 60
バトルタワー・スーパーgrade 4grade 2 → 36 〜 2010 / 60
2つ目の施設で増えたコードは 0 行。 違いは bands と bpByStreak だけで、JSON を1件足しただけ。 タイプ縛りカップが requiredType の差し替えだけで18施設になる、という設計の最初の実証になっている。

施設の相手は手書きのパーティではなく、1体単位のプールから抽選して組む。 64件を grade 1〜4 に16件ずつ配置した。

施設の敗北処理

連勝はリセットされるが、そこまでに確定した BP は残る。 「20連勝して負けたら全部消える」形にすると、挑戦そのものが割に合わなくなる。 本編の敗北処理で「ペナルティは時間を奪うだけで何も教えない」と判断した軸を、施設側にも適用した。

AI ― 情報を型で制限する

AI に BattleState をそのまま渡さない。 渡すと、実装者が無意識に「相手の手持ち・技・持ち物を知っている」前提のコードを書いてしまい、 一度そうなると剥がせない。AiView という制限された型を渡して機械的に縛る。 
type AiView = {
  own: { active; party; activeIndex };          // 自分のものは全部見える
  foe: {
    species; level; types;
    hpRatio;          // 割合だけ。実数値は見えない
    status; statStages;
    revealedMoves;    // 一度使われた技だけ
    revealedParty;    // 一度場に出た個体だけ
  };
  turn; legal;
};

相手の実数値は種族値・レベル・個体値31・努力値0 から推定する。 実際より低く出ることが多いが、basic の判断には十分な精度になる。 相手の特性・持ち物は推定に混ぜない ―― 見えないものは使わない。

相対勝率（同じ編成どうし・500戦）

設定random に対する勝率
basic / mistakeRate 099.4%
basic / mistakeRate 0.1598.4%
basic / mistakeRate 0.3098.0%
basic / mistakeRate 0.5097.4%
basic / mistakeRate 0.8092.2%
mistakeRate の傾きが緩いことが分かった。 定義どおり「スコア上位3手からランダムに選ぶ」ため、 候補が4〜6手しかないバトルでは上位3手がほぼ全体になり、 それでも全手から等確率に選ぶ random よりずっと強い。
mistakeRate は「弱くする」つまみではなく「詰めを甘くする」つまみだった。 難易度の主な段差は AI ではなく相手の個体の強さが作っている。

悪手の回帰テスト

  • 相性0倍の技を選ばない ／ PP切れの技を選ばない
  • 満タンの相手に回復技を撃たない ／ HPが減っていれば回復する
  • すでに状態異常の相手に状態異常技を撃たない
  • 倒せる技があれば必ずそれを選ぶ
  • 同じ盤面では必ず同じ行動を返す（決定性）

セーブ ― 最小実装、ただし抽象化は今

v0.5 で保存するのは BP と施設の記録だけ。 だが 保存先の抽象化とマイグレーションの鎖は今のうちに作る ―― 後から挟めないため。

v0.5 localStorage

v0.9 IndexedDB

共通ボックス数千体で 5MB を超えるため移行する。差し替えるのは上の1ファイルだけで、呼び出し側は一行も変わらない。

type SaveData = {
  schemaVersion: 1;                     // 必ず最初のフィールド
  global: {                             // 地方をまたぐ（恒久）
    bp: number;
    endgame: { facilityRecords: Record<FacilityId, FacilityRecord> };
  };
  settings: { battleSpeed: ... };
};
