## 1. この文書の目的

「どんなゲームを作るか」と「どう作れば途中で破綻しないか」を決める。
作りたいものが大きいので、スコープの扱い方を最初に固定する。

**詳細設計は [`design/`](design/) に分割**。全体像と進捗は [`design/README.md`](design/README.md) を参照。

## 2. ゲームの全体像

**一本道のストーリーを進めるゲームではなく、「制覇率」で進むゲーム。**

構造は2層に分かれる。

```
┌─ 本編：地方チャレンジ ────────────────┐
│  各地方 = 独立した1本のゲーム         │  ← ポケモンを集める層
│  Lv5 から始まり殿堂入りで完結          │
│  手持ちは地方をまたいで持ち越さない     │
└───────────────┬──────────────────────┘
                │ 捕まえたポケモンは共通ボックス・共通図鑑へ永続蓄積
                ▼
┌─ エンドゲーム：横断コンテンツ ────────┐
│  歴代ネームドキャラのトーナメント       │  ← 集めたポケモンを使う層
│  ルール特化のバトル施設群              │  ← ゲームの本体はここ
└──────────────────────────────────────┘
```

進行の軸は3本。どれをどの順で進めてもよい。

1. **地方を殿堂入りする**（横に増える）
2. **図鑑を埋める**（地方をまたぐ）
3. **エンドゲームを踏破する**（縦に深まる）

### なぜ「地方を順に制覇」にしないのか

各地方は「Lv5で始まり Lv60前後で終わる」前提で設計されている。これを直列に繋ぐと、

- **レベルカーブが成立しない。** 2地方目の入口で手持ちが既にLv60。金銀がカントーを再調整したのと同じ問題が8回起きる。しかも地方を1つ足すたびに既存地方の調整をやり直すことになる。
- **「全ポケモンが出る」が死ぬ。** カントー完走時点で完成した手持ちがあると、ジョウトのLv5を捕まえる理由がない。1,025種入れても使われるのは最初の30種だけになる。
- **同じ構造の9回反復。** 合計200時間超。遊ぶ側も作る側も持たない。

地方を独立させると全て解ける。そして開発上いちばん効くのは、
**地方を追加するときに既存地方を再調整しなくてよくなる**こと。1地方 = 1リリースになる。

> 補足: 「1本の連続した旅」にこだわる場合、地方2つが上限。金銀がやったのがそれで、3つ目からは破綻する。

## 3. 3つの希望の扱い

| 希望 | 素直に実装した場合の規模（概算） | 本方針での回収先 |
| --- | --- | --- |
| 全てのポケモンが出る | 1,025種 + フォルム違い。技は約900。 | 各地方でその地方のポケモンを使わざるを得ない構造 → 自然に全種へ出番が回る。共通ボックスに蓄積。 |
| 今までの全てのトレーナーが出る | 本編累計で数千人。 | 地方内の配置 + **エンドゲームのトーナメント**。ネームドキャラはこちらが主戦場。 |
| 原作のマップを再現 | 9地方・数百マップ。1マップ数時間〜。 | 地方単位で1つずつ追加。最も工数が重いので最後に回す。 |

### 中心原則

> **「全部入り」はゴールではなく設計制約。**
> エンジン（ルール）とコンテンツ（データ）を分離し、
> コンテンツを1件足すコストが限りなくゼロに近づくように作る。

この原則を守る限り、途中で開発が止まっても「遊べるもの」が手元に残る。

## 4. 本編：地方チャレンジ

- 各地方は Lv5 スタート・8バッジ・四天王・殿堂入りで完結する独立した1本。
- **手持ちは地方をまたいで持ち越さない。** 各地方は現地のポケモンで攻略する。
- 捕まえたポケモンは共通ボックス・共通図鑑に永続的に蓄積される。
- 殿堂入りしたチームは「殿堂」に記録され、エンドゲームで使える。
- 地方は順不同に選べる（最初はカントーのみ、以降は緩い解放条件）。
- **相棒枠**: 次の地方に1体だけ連れて行ける（Lv は現地の帯に合わせて補正）。喪失感の緩和用、要調整。

## 5. エンドゲーム（ゲームの本体）

集めたポケモンの行き場であり、長期的に遊ばれる層。**マップをほぼ必要としない**ため、
個人開発と極めて相性が良い。ルールを1つ変えるだけで新コンテンツになる。

### 5.1 歴代ネームド トーナメント

ブラック2/ホワイト2の PWT（ポケモンワールドトーナメント）形式を下敷きにする。
1回のプレイで3〜4戦のトーナメントを勝ち抜く形。セッションの区切りが良い。

**難易度ティア** — 同じキャラのデータを使い回して段階的に強化する:

| ティア | 内容 |
| --- | --- |
| 原作 | 地方攻略中に戦う姿。レベル・構成とも原作準拠。 |
| **本気** | Lv50統一・持ち物あり・技構成を実戦的に・AI強化。 |
| **極** | 個体値/努力値最適化・特性と持ち物フル活用・6体・AI最強・そのキャラのコンセプトを極めた構築。 |

ティアはレベル/持ち物/技/AI強度の差し替えだけで表現する。**キャラを1人追加すれば3段階ぶんのコンテンツになる。**

**カップ（トーナメントの種類）** — 出場者プールを変えるだけで増やせる:

- 地方カップ（カントーカップ = その地方のジムリーダー・四天王・チャンピオンから抽選）
- ジムリーダーカップ（全地方のジムリーダー）
- タイプカップ（ほのおカップ等 = 該当タイプ使いのネームドが集まる）
- チャンピオンカップ（歴代チャンピオンのみ）
- 悪の組織カップ
- 究極カップ（全ネームドの「極」ティアのみ）

### 5.2 バトル施設（ルールセット駆動）

バトルフロンティアの本質は「**ルールを変えることで少ないアセットから大量のコンテンツを生む**」こと。
そのため **施設をハードコードせず、「ルールセット」というデータとして表現する。**

```ts
type Ruleset = {
  levelCap: 50 | 100 | null;              // レベル統一
  teamSize: number;
  teamSource: "own" | "rental";           // レンタル制なら育成不要で遊べる
  itemsAllowed: boolean;                  // 回復道具の持ち込み
  duplicateSpecies: boolean;              // 種族被り禁止
  winCondition: "faint" | "turnLimit";    // ターン制限＋採点（アリーナ式）
  moveSelection: "player" | "auto";       // 技を自分で選べない（パレス式）
  healBetweenBattles: boolean;
  streakLength: number | "endless";
  opponentPool: string;                   // 相手プールのID
};
```

施設 = **ルールセット + 相手プール + 報酬**。この3つのデータで1施設が定義できる。

| 施設 | ルール | 実装コスト |
| --- | --- | --- |
| バトルタワー | 素直な連勝。Lv50統一。 | 低（基準） |
| バトルファクトリー | レンタルポケモンで戦い、勝った相手から1体貰う | 低 |
| バトルアリーナ | 3ターンで判定（残HP・与ダメ・技の当たり方で採点） | 低 |
| バトルパレス | 技を自分で選べない（性格が行動を決める） | 低 |
| バトルホール | 単体で連戦。次の相手のタイプを自分で選ぶ | 低 |
| バトルキャッスル | BPを消費して回復・相手情報を購入する資源管理 | 中 |
| バトルピラミッド | ダンジョン探索＋道具制限 | **高（マップが必要）→ 後回し** |

ピラミッド以外はマップ資産をほぼ必要としない。ここが狙い目。

### 5.3 報酬と進行

エンドゲームには「続ける理由」が要る。

- **BP（バトルポイント）**: 全施設共通通貨。育成アイテム・わざマシン・レア個体・進化アイテムと交換。
- **記録**: 連勝記録、トーナメント制覇履歴、撃破したネームドとティアの一覧。
- **段階解放**: 「本気」ティアは原作ティア撃破後、「極」ティアは本気ティア撃破後に解放。

## 6. 技術スタック

| 項目 | 選定 | 理由 |
| --- | --- | --- |
| 言語 | TypeScript | 型でデータ構造を守れる。データ件数が増えるほど効く。 |
| 実行環境 | ブラウザ | 環境構築が軽く、`vite dev` だけで動く。**公開はしない**（§10） |
| 描画 | Canvas 2D（自前） | **v0.7 で Phaser を見送った。**判断は [`design/ui-flow.md`](design/ui-flow.md) §2.1。 |
| ビルド | Vite | 設定がほぼ不要。 |
| テスト | Vitest | バトルロジックは全てユニットテストで守る。 |
| データ検証 | zod | JSONデータの形をランタイムで検証し、壊れたデータを早期に検出する。 |

## 7. アーキテクチャ

```
packages/
  core/    ルールエンジン。Phaser にもDOMにも依存しない純粋なTS。
           バトル計算・タイプ相性・レベルアップ・状態異常・ルールセット解釈。
           → ここが全ての中心。テストで守る。
  data/    JSON + zodスキーマ。種族・技・トレーナー・ネームド・ルールセット・マップ定義。
           → 増えるのはここだけ、が理想。
  game/    Phaser 層。描画・入力・シーン遷移・セーブ。
  tools/   データ検証、雛形生成、一括変換のスクリプト。
```

**依存の向きは `game → core → data` の一方向のみ。**
これによりバトルロジックをブラウザなしでCLIとテストから動かせる（= v0.1 が成立する）。

### 中核データモデル（初版イメージ）

```ts
type Species = {
  id: string;              // "pikachu"
  dexNo: number;           // 25
  name: string;            // "ピカチュウ"
  types: [Type] | [Type, Type];
  baseStats: { hp; atk; def; spa; spd; spe };
  abilities: string[];
  learnset: { level: number; move: string }[];
};

type Move = {
  id: string; name: string; type: Type;
  category: "physical" | "special" | "status";
  power: number | null; accuracy: number | null; pp: number;
  priority: number; target: Target;
  effect?: { kind: string; chance?: number; /* データ駆動の効果ID */ };
};

type Trainer = {
  id: string; name: string; class: string;   // "ジムリーダー"
  tier: "original" | "serious" | "ultimate"; // 強化ティア
  party: { species: string; level: number; moves: string[];
           item?: string; ability?: string; nature?: string }[];
  ai: "random" | "basic" | "smart";
  dialogue: { before: string; win: string; lose: string };
};
```

技の効果は `switch` の巨大な塊にせず、**効果IDとハンドラのレジストリ**にする。
新しい技を追加する = JSONを1行足す（既存の効果なら）で済むようにする。

## 8. マイルストーン

各マイルストーンは「そこで開発が止まっても遊べる／価値が残る」単位で切る。

**重要な組み替え:** エンドゲーム（バトル施設）はマップをほぼ必要としないため、
**マップより先に作れる**。しかもレンタル制にすれば育成システムすら要らない。
これにより「マップが完成しないと何も遊べない」という個人開発最大のリスクを回避する。

### 8.0 この順序に至った理由（見直しの記録）

初版の計画には、**計画の骨格に関わる問題が2つあった。**

**1. データ投入の基盤が、どの版にも計上されていなかった**

[`design/data-schema.md`](design/data-schema.md) §7 で
「手入力が現実的な量ではない」「`tools/` はゲーム本体と同じくらい重要な成果物」と
結論づけておきながら、**`tools/` がマイルストーンに一度も現れていなかった。**

カントーだけでも151種 × （種族値・タイプ・特性・数十件の learnset）で
数千のデータ点になる。これを手入力する前提の計画は成立しない。
**v0.4 として独立させた。** 以降の全ての版がこの基盤の上に乗る。

**2. v1.0 が、最も作りたいコンテンツを含んでいなかった**

初版では PWT型トーナメント（歴代ネームド戦）が **v1.1**、
つまり「1.0 の後」に置かれていた。だが本作の中心は
エンドゲームであり（[本書 §2](#2-ゲームの全体像)）、歴代ネームドとの戦いは
その主役にあたる。**1.0 が主役を含まないのは、計画の優先順位が
ゲームの設計思想とずれている。**

しかも技術的には、**PWT はタワーができていれば安い。**
必要なのは `Ruleset` と出場者プールだけで、マップも捕獲も要らない。
[`design/endgame.md`](design/endgame.md) §7 の設計がそうなっている。
**v0.6 に前倒しした。**

これにより **v0.6 の時点で「歴代ジムリーダーと戦えるゲーム」が動く。**
マップも捕獲もない状態で、作りたかったものの中核が遊べる。

**3. v0.1 が「証明」と「完成」を混同していた**

初版の v0.1 は「20種・40技・状態異常・ランク補正・交代」を含んでいた。
これは**アーキテクチャの証明**（`GameData` の受け渡し、イベント列、
シード乱数、状態の不変性が機能するか）と、
**バトル機能の完成**を1つの版に押し込んでいる。

前者は5種・8技の攻撃技だけで証明できる。**設計が間違っていた場合、
早く分かるほど傷が浅い。** v0.1 と v0.2 に分割した。

| **v0.1** | **バトルの骨格**（5種・8技・攻撃技のみ・AI random） | ランダムAI同士が1,000戦して例外なく決着する。**アーキテクチャの証明。** |

### 8.2 この順序が守っているもの

- **v0.1 でアーキテクチャが証明される。** 間違っていれば5種8技の段階で分かる
- **v0.3 で初めて目で見える。** ここまでが最長の「何も見えない期間」
- **v0.4 で手入力から解放される。** 以降、データ量は障害でなくなる
- **v0.6 で作りたかったゲームが動く。** マップも捕獲もない状態で歴代ネームドと戦える
- **v0.8 で収集が繋がる。** 捕まえた個体を v0.5/v0.6 に持ち込めるようになる
- **v1.0 は統合であって、新機能ではない**

### 8.3 残る論点

**論点1: v0.5 の最小セーブと v0.9 の本セーブの関係**

v0.5 で連勝記録・BPを保存しないと、タワーが単なるデモになる。
一方 [`design/save-data.md`](design/save-data.md) の設計一式（IndexedDB・
マイグレーション・エクスポート）を v0.5 に前倒すと重すぎる。

→ **v0.5 は `localStorage` に記録だけを保存する暫定実装とし、v0.9 で IndexedDB へ移行する。**
移行は `SaveStore` interface（[`design/save-data.md`](design/save-data.md) §2）を
最初から挟んでおけば、実装の差し替えで済む。**この抽象化を v0.5 で入れることが条件。**

**論点1の結果（v0.5 実装後）:** 決定どおり `SaveStore` を挟んだ上で `localStorage` 実装を入れた。
保存する構造は最終形の部分集合（`global` / `endgame` / `settings`）にしてあるので、
v0.9 の移行は項目の追加で済む。詳細は [`design/save-data.md`](design/save-data.md) §9.5。

**論点2: v0.5 の AI 水準**

[`design/endgame.md`](design/endgame.md) §8 の難易度カーブは21連勝以降で `smart` を要求するが、
`smart` は v1.2 相当の重さ（確定数計算・積みの価値評価）。

→ **v0.5 は連勝上限を設けて `basic` のみ。** 上限解除は v1.2 の `smart` と同時。

**論点2の結果（v0.5 実装後）:** 上限は20連勝に置いた。
実装して分かったのは、**難易度を作っているのは AI ではなく相手の個体の強さ**だったこと
（`mistakeRate` を 0→0.8 に振っても勝率は 99.4%→92.2% しか動かない）。
連勝施設の成立条件そのものにも見落としがあり、
[`design/endgame.md`](design/endgame.md) §11.5 に3件の訂正として記録した。

**論点3: v0.7 では捕獲できない**

マップで野生と遭遇できるが捕獲は v0.8。`Action.run`（逃げる）は v0.7 で必要だが、
`Action.item`（ボール）は v0.8 まで使えない。

→ 意図どおり。v0.7 はマップとエンカウントの疎通確認。
**ただし v0.7 単体では「遊べる」状態にはならない**ことを承知の上で進める。

**論点3の続報（v0.8 実装後）:** 下に書いた「HP が持ち越されない」は解消した。
手持ちが `PokemonInstance`（実個体）になり、HP・PP・状態異常・経験値・なつき度が歩いても残る。
野生戦に消耗が生まれ、ポケモンセンター（ママ）に意味ができた。

**論点3の結果（v0.7 実装後）:** `Action.run` を入れて野生戦から離脱できるようにした。
`Action.item` は v0.8 に送った ―― **回復道具がまだ1つも存在しない**ためで、
`items.json` は戦闘用の持ち物32種しか持っていない
（1番道路に落ちている道具も、やむを得ずオボンのみにしてある）。

想定していなかった副作用が1つある。**HP がマップに持ち越されない。**
手持ちはまだ `PartySpec`（設計図）であって実個体ではないので、
戦うたびに満タンで始まる。結果として **野生戦に消耗が無く、遭遇に意味が生まれない。**
「捕獲が無い」よりこちらの方が「遊べなさ」に効いている。
`healParty` コマンドも演出だけで、回復する対象が存在しない。
**v0.8 の戦闘後シーケンスは、経験値より先に「HP を持ち歩く」ことから始める。**

最も安く、最も重要な検証をここに置く。逆にここで手応えがなければ、
地方追加に進む前に設計を見直すべきという判断ができる。

#### v1.3〜v1.9 ― 地方追加（1地方 = 1リリース）

実装順は**アセットの再利用効率**で決める（[`design/regions.md`](design/regions.md) §2）。

```
ジョウト → ホウエン → シンオウ → イッシュ → カロス → ガラル → アローラ → パルデア
```

アローラ（島巡り）とパルデア（オープンワールド）は
**チャレンジ構造が特殊**なため最後に回す。

**地方を1つ足すと、エンドゲームも自動的に厚くなる。**

| 増えるもの | 効き先 |
| --- | --- |
| 種族・出現テーブル | 図鑑・共通ボックス・`BattleSet` プール |
| ネームド（約15人 × 3ティア） | トーナメントの出場者プール |
| マップ・トレーナー | 地方チャレンジ |

[`design/endgame.md`](design/endgame.md) §7 で「カップの出場者プールは殿堂入り済み地方に限る」
と決めたため、**地方を進めるほどトーナメントの顔ぶれが厚くなる。**
地方追加とエンドゲーム強化が、同じ作業で同時に進む。

| 地方 | ギミック | エンジンへの影響 |

**全1,025種で通ること**が、v2.0 の完了条件。

### 8.5 素材の問題は解消した（§10 の決定による）

### 8.6 learnset をいつ正式データにするか

v0.4 で投入した learnset は**規則生成の暫定データ**で、原作の習得レベルではない。
`learnsetSource: "provisional"` が立っており、検証が毎回そう報告する。

**差し替えの期限は v0.8（育成）。** 理由は、それまで learnset が体験に影響しないから。

| 版 | learnset が効くか |
| --- | --- |
| v0.5 バトルタワー | ❌ `BattleSet` が独立に技を定義する |
| v0.6 トーナメント | ❌ ネームドのパーティが独立に技を定義する |
| v0.7 マップ探索 | △ 野生の技構成に出るが、捕獲がまだ無い |
| **v0.8 育成** | ✅ **レベルアップで技を覚える。ここで初めて体験に直結する** |

**今すぐ正式化しない理由:** 151種 × 十数件の習得レベルという規模の正確なデータが手元にない。
記憶で書くと「正確そうに見えて間違っているデータ」になり、
暫定と宣言してある今の状態より悪くなる。
TSV に列を足すだけで差し替わる構造にしてあるので、
正式なデータが用意できた時点で投入すればよい。

#### 結果（v0.8 着手時）― 出どころが見つかったので差し替えた

**`@pkmn/dex`（Pokémon Showdown のデータ）から公式のレベル技表が取れる。**
一般の Web は環境のポリシーで塞がっているが、npm レジストリは通る。

```
@pkmn/dex （生成時だけの依存）
      │  tools/fetch-official.ts   … 人が明示的に走らせる
      ▼
packages/data/source/learnsets.tsv  （コミットする。差分が読める）
      │  npm run import
      ▼
packages/data/species.json
```

**ビルドを外部データに依存させない。** 取り込みは1回きりの操作で、
結果は原本としてコミットする（マップの原本と同じ構え）。

| | 値 |
| --- | --- |
| 採用世代 | 第9世代 99種 / 第8世代 40種 / 第7世代 12種 |
| どの世代にも無い種 | **0種** |
| レベル技 のべ | 2,238件 |
| 1種あたりの平均 | 5.8件 → **10.0件** |

カントー151種のうち約1/3はスカーレット・バイオレットに登場しないため、
**新しい世代から順に降りて採る。** これで穴なく埋まった。

#### 律速は learnset ではなく技の数だった

正式データを当てはめると、参照される技のうち当プロジェクトに存在するのは**39%**しかなかった。
そこで**142件の技を追加**した（105 → 247件）。数値は全て公式データからの変換で、
**人が書いたのは日本語名だけ**。

| | 件数 |
| --- | --- |
| 追加した技 | 142 |
| 未追加（理由つきで `source/moves-todo.tsv` に残す） | 155 |
| レベル技の充足率 | 39% → **68%** |

未追加の155件は**入れてはいけないもの**が大半で、内訳は
「効果を表せない32／未実装の状態29／個別処理15／場の効果13／能力変化が複数12／
威力が可変11／制約が強さを釣り合わせている11…」。
v0.4 で決めた「原作の機構を要する技をただの威力技として入れない」規則がそのまま効いている。

**「制約が強さを釣り合わせている」11件は手で外した。**
ふいうち・ねこだまし・とっておき・やけくそ・ふういん…
どれもデータからは制約が見えず、抜き取ると**原作より強い別物**になる
（ねこだましは「出た直後の1回だけ」だから優先度+3の確定ひるみが許されている）。

#### 公式 learnset が、最初のライバル戦を壊した

技を正しくしたら、**ヒトカゲを選んだときのライバル戦の勝率が 1.5% になった。**
3択のうち1つが実質詰みという状態で、実測して初めて分かった。

| ライバルの手持ち | フシギダネで | ヒトカゲで | ゼニガメで |
| --- | --- | --- | --- |
| Lv5・攻撃技＋変化技（当初） | 42.3% | **1.5%** | 30.8% |
| Lv4 に下げる | 71.3% | 83.0% | 100.0% |
| **Lv5・攻撃技のみ（採用）** | **46.0%** | **36.0%** | **50.2%** |

**原因はレベルでも種族値でもなく、ライバルが持っていた「しっぽをふる」1つだった。**
Lv5 は1発のダメージが 5〜7 しかないので、ぼうぎょ −1 が
**倒すまでの手数を丸ごと1回増やす。** 上のレベル帯では誤差に埋もれる効果が、
最序盤では勝敗をひっくり返す。

レベルを下げる案（原作からの乖離が大きく、しかも 100% になる）より、
**変化技を持たせない案を採った。** 原作のレベルを保ったまま、3択のどれもが勝負になる。
この勝率は `pokemon.test.ts` で 25〜70% に固定してある。

**負けても再挑戦できるようにした。** 撃破フラグをバトル前ではなく
**勝利イベント側に移した**（world.md §6 のイベント2分割がそのまま効く）。
これが無いと、負けた瞬間にライバルが消えて二度と戦えなくなる。

#### 副作用 ― 暫定データ用に書いた検証が落ちた

「Lv5 までに攻撃技を覚える」「攻撃技のタイプが2種類以上」は、
**暫定 learnset の生成規則が守るべき品質条件**としてエラーにしていた。
公式データではこれが**原作の事実**になる ――
メタモンは へんしん しか覚えないし、ケーシィは テレポート だけ。

→ **エラーではなく一覧の報告に変えた。** 代わりに
「野生で出る種が Lv5 までに技を1つも覚えない」をエラーにした。
こちらは遊べるかどうかに直結する。

`toBattlePokemon` の「技0は例外」も外した。技を持たない個体は
**わるあがきしかできない個体**として成立させる（バトル側は元からその道を持っていた）。

**論点5: v0.9 で「町を1つ足すのにコードが要るか」を測った**（v0.9 実測）

v0.10（カントー全域）が全計画で最大の塊である以上、
**「マップを1枚足すコスト」がこの先の全てを決める。** v0.9 でトキワシティ
（町・ポケモンセンター・ショップ・民家の4枚）を足して、実際に測った。

| 触ったもの | 内容 |
| --- | --- |
| `.map` ×4 / `events.json` / `flags.json` / `shops.json` | データのみ |
| `packages/core` | **0行** |
| `packages/game` | **0行**（タイル色のヒントに3文字足しただけ） |

**コードは書かなくてよかった。** ただし検証が9件のエラーで止めた ――
建物の入口が「入った瞬間に押し戻される」形になっていたのが3件、
NPC をカウンターの上に置いたのが5件、誰も立てないマスが1件。
どれも v0.7 の収穫（#55・#56）と同じ形で、**人は同じ間違いを繰り返す。**

v0.10 の分割方針（南半分・北半分）は変えない。増えるのは
マップとトレーナーのデータ量であって、コードではないことが確かめられた。

**論点4: v0.10（カントー全域）が最大の塊**

マップ数十枚・トレーナー百人以上・ジム8つ。**単一の版としては全計画で最大。**
着手時に「南半分」「北半分」等へ分割することを前提とする。

## 10. 権利について ―【決定】手元では公式素材、リポジトリには入れない

本作は配布も公開もしない**個人利用のゲーム**として作る。この前提で方針を確定する。

### 判断の根拠

| 行為 | 可否 |
| --- | --- |
| 公式のドット絵・BGMを**手元で使う** | ⭕️ **問題ない。** 私的使用のための複製（著作権法30条）の範囲 |
| **公開リポジトリにコミットする** | ❌ **公衆送信にあたる。** 「手元」ではなくなる |
| GitHub Pages で公開する | ❌ 同上 |
| 友人に配る・実況配信する | ❌ 同上 |

ファンゲームが問題になるのは、ほぼ例外なく**配布・公開した場合**。
手元で遊ぶ限りは問題にならない。

### 本リポジトリは公開設定である（重要）

`takoyaki623/intro_git` は **public**。
**`assets/` をコミットした瞬間に、私的使用の範囲を外れる。**
意識せずやってしまいやすいので、`.gitignore` で機械的に防ぐ。

```gitignore
assets/        # グラフィック・音声
maps-src/      # Tiled の原本（原作マップを写したもの）
*.png *.mp3 …  # 拡張子でも二重に防ぐ
```

**コードとデータ（種族値・技・マップ構造などの数値・構造情報）だけをコミットする。**

### 設計上の帰結 ― アセットなしでも動くこと

リポジトリを clone しただけの状態には、絵が1枚も存在しない。
そのため **アセットが無い場合に図形・記号で代替するフォールバックを必ず実装する。**

- これは「素材が無いときの逃げ道」ではなく、**通常動作の1つ**として作る
- [`design/data-schema.md`](design/data-schema.md) §4 でアセットを分離し、
  コードからパス依存しない構造にしたのがそのまま効く
- 開発中も図形モードで進められるため、**素材の調達が実装のボトルネックにならない**

### 手元の素材の入れ方 ― 2経路（v0.10.5 で実装）

「アセットなしでも動く」を通常動作にした上で、**手元でだけ差し替えられる口**を作った。
`packages/game/src/art/source.ts` が絵の出どころを1箇所に集めていて、
無い絵は黙って `drawn`（コードで描く）に落ちる。

| 経路 | 素材の置き場 | 公衆送信になるか |
| --- | --- | --- |
| 開発時（`npm run dev`） | `assets/` を vite が配信。`.gitignore` 済み | ならない（手元だけ） |
| 遊べる版（Artifact） | **利用者が自分の端末の画像を選び、自分のブラウザの IndexedDB に置く** | ならない（どこにも送らない） |

Artifact 版で **ページに素材を同梱しない**のが要点。同梱した時点で配布になる。
Artifact の `assets` capability も使わない ―― あれはホスト側に置く形になるため、
公開リポジトリにコミットするのと同じ問題になる。

素材用の IndexedDB は**セーブとは別の DB** にしてある（`pkmn-rpg-art`）。
同じ DB に入れると (1) 版の上げ下げが絡む (2)「さいしょから」で素材まで消える
(3) **バックアップの書き出しに画像が混ざる** ―― 特に (3) は公衆送信の口が1つ増えることになる。
寿命も持ち主も違うものは、入れ物を分ける。

ファイル名がそのまま絵の名前になる（`tile-T.png` → 木のマス）。
対応表を別に持たないのは、「表に無い名前を入れたのに出ない」が起きたとき
何が悪いのか分からなくなるため。名前が合っていなければ単に `drawn` のまま描かれる。

### GitHub Pages について

[§6](#6-技術スタック) で「GitHub Pages で即公開・共有できる」を利点に挙げていたが、
**公式素材を使う以上、この利点は放棄する。** ブラウザで動く手軽さ（ローカルで
`vite dev` するだけ）は変わらないため、技術選定そのものは維持する。

### 将来公開したくなった場合

素材を自作・フリー素材に差し替えれば、コードとデータはそのまま公開できる。
**そのための構造は最初から用意されている**（アセット分離・フォールバック）。
差し替えを前提にしておくことが、この判断の唯一のコストになる。

## 11. リポジトリ運用（git練習を兼ねる）

- `master`: 常に動く状態を保つ。
- 作業ブランチ: `feat/<内容>`、`fix/<内容>` を切って作業し、PRでマージ。
- コミットは「1つの意味の変更」単位で小さく。メッセージは何を変えたかを日本語で書く。
- マイルストーン到達時にタグを打つ（`v0.1` など）。
