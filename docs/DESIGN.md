# 設計メモ

`/sc:brainstorm` で決めた方向と、そこから逆算した実装順。

## 決めたこと

| 項目       | 決定                                        |
| ---------- | ------------------------------------------- |
| バトル規模 | 手持ち 3 匹 + 交代                          |
| 遊びの単位 | 連戦（勝ち抜き式）。HP は次の戦闘に引き継ぐ |
| 表示言語   | 日本語                                      |
| 技の奥深さ | ダメージ + 状態異常                         |

## この 4 つが要求するもの

4 つとも独立した機能に見えて、**同じ 2 つの土台**を要求します。

**構造化されたバトルログ。** 現在ログは `readonly string[]` に英文が直書きです。日本語化はこれを崩さないと不可能で、状態異常も交代も新しい文言を増やします。イベントを構造で持ち、文言は表示層で組み立てます。副産物としてダメージ数値の表示や被弾側のハイライトも可能になります。

**チームを持つ `BattleState`。** 現在は片側 1 匹固定です。交代は型から作り直しになります。連戦はさらにその外側に「run」の状態を必要とします。

つまり**機能追加の前に土台を敷いたほうが安い**、という結論になります。

## 実装順

依存関係の順です。各段階でテストが緑のまま進みます。

### ~~Phase 0~~ — 状態更新の純粋化 ✅ 完了

`App.tsx` が `setBattle` の更新関数の中で乱数を引いています。StrictMode で 1 ターンあたり 7 → 14 回に倍増することを実測済み。修正後は 7 回で一致することを同じ方法で確認。連戦にすると 1 プレイが長くなり、シード付き乱数でランを再現したくなるので、ここで潰します。数行。

### ~~Phase 1~~ — 構造化ログと日本語化 ✅ 完了

```ts
export type BattleEvent =
  | { kind: 'encounter'; pokemon: string }
  | { kind: 'useMove'; side: Side; pokemon: string; move: string }
  | { kind: 'miss'; side: Side; pokemon: string }
  | { kind: 'damage'; side: Side; pokemon: string; amount: number }
  | { kind: 'critical' }
  | { kind: 'effectiveness'; multiplier: number }
  | { kind: 'faint'; side: Side; pokemon: string }
```

`BattleState.log: string[]` を `events: BattleEvent[]` に置き換え、`src/ui/messages.ts` が日本語へ変換します。
`formatEvent` は `damage` に対して `null` を返します（本家もダメージ数値は表示しない）。
イベント自体は数値を持っているので、HP バーのアニメーションやダメージ表示を後から足せます。

```
「ピカチュウの 10まんボルト！」
「こうかは ばつぐんだ！」
「ゼニガメは たおれた！」
```

データ側の名前も日本語にします（ピカチュウ / 10まんボルト / でんき）。表示言語は日本語のみと決めたので `{ ja, en }` のような構造は持たせません。後から英語を足したくなっても、この構造化を済ませてあれば安く済みます。

### ~~Phase 2~~ — 手持ち 3 匹と交代 ✅ 完了

```ts
export interface TeamState {
  readonly members: readonly BattlePokemon[]
  readonly activeIndex: number
}

export type TurnAction = { type: 'move'; move: Move } | { type: 'switch'; index: number }
```

ルール：

- 交代は 1 ターンを消費する
- 交代は技より先に解決される（本家の優先度）
- ひんし時は強制交代。ターンは消費しない
- 勝敗は「3 匹すべてひんし」で判定

`BattleEvent` には `switch` ひとつではなく `withdraw` と `sendOut` の 2 つを追加しました。
本家が「ピカチュウ もどれ！」と「ゆけっ！ ヒトカゲ！」を別の行で出すのと、
ひんし後の交代では戻す行が出ないのを、そのまま表現できるためです。

相手側の強制交代は `resolveTurn` の中で自動的に解決し、
プレイヤー側だけ `awaitingSwitch` として呼び出し側に返します。
AI は自分で決められるが、プレイヤーには訊く必要がある、という非対称です。

種族を 3 つ足しました（イーブイ・ズバット・イシツブテ）。
`data/teams.ts` の 2 パーティは型相性が噛み合うように選んであり、
たとえばイシツブテ（いわ・じめん）にはピカチュウのでんきが無効なので、
交代が「作業」ではなく「判断」になります。

### ~~Phase 3~~ — 状態異常 ✅ 完了

`どく` `やけど` `まひ` `ねむり` `こおり`。

ターン構造が 2 段になります。**行動フェーズ**のあとに**ターン終了フェーズ**（どく・やけどのスリップダメージ）。

| 状態   | 効果                                |
| ------ | ----------------------------------- |
| どく   | ターン終了時に最大 HP の 1/8        |
| やけど | ターン終了時に 1/16、物理攻撃が半減 |
| まひ   | 素早さ半減、25% の確率で行動不能    |
| ねむり | 1〜3 ターン行動不能                 |
| こおり | 20% で自然解凍するまで行動不能      |

`BattlePokemon` に `status` を追加。イベントも 4 つ増えました
（`statusInflicted` / `statusDamage` / `immobilised` / `statusEnded`）。

実装上の判断：

- `Status` は union にしました。ねむりだけがターン数を持つので、
  やけどのポケモンに無意味なカウンタが生えないようにするためです
- タイプ免疫を入れました（どく→どく・はがね、やけど→ほのお、
  まひ→でんき、こおり→こおり）。でんじはがピカチュウに効きません
- 技に `category: 'status'` を追加。でんじは・ねむりごなは威力を持ちません
- 起床・解凍したターンは行動できます（本家と同じ）

### ~~Phase 4~~ — 連戦と保存 ✅ 完了

```ts
export interface RunState {
  readonly team: readonly BattlePokemon[] // HP は引き継ぐ
  readonly wins: number
  readonly battle: BattleState | null
  readonly over: boolean
}
```

- 勝つたびに相手が強くなる（レベルを上げる）
- 手持ちの HP と状態異常は次の戦闘に引き継ぐ
- 3 匹すべてひんしでラン終了
- `localStorage` に保存。サーバは不要

## バランス設定

未決定としていた 3 点は仮の想定どおり実装し、`src/domain/run.ts` の
`RUN_CONFIG` に集約しました。1 行で調整できます。

```ts
export const RUN_CONFIG = {
  startingLevel: 50,
  levelStepPerWin: 2,
  healingBetweenBattles: 0.25,
  partySize: 3,
}
```

加えて **ひんししたポケモンはランの間ずっと復帰しません**。
これがラン全体をカウントダウンにし、勝ち抜きの緊張感を作っています。
回復は生き残っているポケモンにだけ効き、状態異常も同時に治ります。

相手 AI は `src/domain/ai.ts` にあり、技のスコアリングと交代の判断をします。
`AI_CONFIG.skill` を下げると、たまにランダムな技を選ぶようになります。

### バランスの根拠

腕前の違うボットで通しプレイして測りました（各 200 ラン、1 ランあたりの平均連勝数）。

| プレイヤー    | 考える AI | ランダム AI |
| ------------- | --------- | ----------- |
| 第 1 手を連打 | 0.85      | 1.70        |
| 最善手を選ぶ  | 2.16      | 3.44        |
| 最善手 + 交代 | 2.53      | 3.81        |

`npm run sim` で再測定できます（`src/ai.sim.test.ts`。通常のテスト実行では skip）。

**初期は相手も Lv50 でした。** そのときの数値は「最善手 + 交代」で 0.81 連勝、
つまり初戦で半分落ちる状態でした。原因は五分の勝負を繰り返す設計で、
毎戦の勝率が 50% なら期待連勝数は 1 になります。

回復量を 0.25 → 0.55 に上げても 0.81 → 0.90 しか動きませんでした。
**回復は戦闘の「間」にしか効かないので、初戦の敗北を防げない**ためです。
相手の初期レベルを 42 に下げたところ 0.81 → 2.40 になりました。

腕前で 3 倍の差（0.85 対 2.53）がつくので、判断が結果に反映されています。

## のこっている改善候補

- 相手 AI に交代とタイプ相性の判断を入れる
- ダメージ数値の表示や HP バーのアニメーション（`damage` イベントが数値を持っています）
- 能力変化（つるぎのまい・いかくなど）
- 手持ちの編成を選べるようにする

## 変えないこと

- `src/domain/` は React を参照しない。ルールは純粋関数のまま
- 乱数は引数で受け取る。テストで固定できる状態を保つ
- データはローカル。PokéAPI は使わない（テストの決定性とオフライン動作を優先）
