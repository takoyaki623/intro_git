# 11. マップ・イベント・NPC

関連: [`regions.md`](regions.md) / [`capture.md`](capture.md) / [`save-data.md`](save-data.md) / [`economy.md`](economy.md)

## 1. 設計方針

「原作のマップを再現」は最初の3つの希望の1つでありながら、**最も工数が重い**領域。
9地方で数百マップになる。

> **マップは「作る」ものではなく「流し込む」ものにする。**

つまり設計の目標は、良いマップを作ることではなく、
**マップを大量に流し込める仕組みと道具を用意すること**に置く。
[`README.md`](README.md) の中心原則（コンテンツ追加のコストをゼロに近づける）が、
最も強く問われる章になる。

## 2. マップデータ形式 ―【決定】Tiled を採用する

**決定事項: マップ制作には Tiled（無料のタイルマップエディタ）を使う。**
未決事項だった「Tiled の採用可否」をここで確定する。

### 理由

- タイルマップエディタの自作は数ヶ月規模の作業になる。**得るものがない**
- Tiled は JSON 出力に対応し、Phaser も公式にサポートしている
- **数百マップを作る以上、エディタの品質が生産性を直接決める**

### ただし Tiled 形式に依存しない

```
*.tmx / *.tmj （Tiled の出力・制作時の正）
      │
      │ tools/convert-map.ts   ビルド時に変換
      ▼
自作スキーマの JSON （ゲームが読むのはこちらだけ）
```

Tiled の JSON をそのままランタイムに渡すと、外部ツールの都合に縛られる。
**中間形式として扱い、ゲーム本体は自作スキーマだけを知る。**
将来エディタを乗り換えても、変換スクリプトを差し替えるだけで済む。

### 2.1 【訂正・v0.7】当面の原本はテキストのマップソースにする

Tiled 採用の決定は、上の「原本を差し替えても影響は変換スクリプトに閉じる」という
構えのおかげで、**痛みなく先送りできる**ことが実装してみて分かった。

**決定: v0.7 の原本は `packages/data/source/maps/*.map`（テキスト）とする。**

```
id: kanto-pallet-town
name: マサラタウン
region: kanto

legend:                 # 文字 → 地形。`!` 前置で通行不可
. normal
, grass
T !normal
D normal

grid:                   # 見たままの格子
TTTTT.TTTTTT
T..........T
...

warps:                  # 座標 種類 接続先マップ 座標 向き
5,0 step kanto-route-1 5,16 up
3,4 interact kanto-players-house-1f 3,6 up

objects:                # ID 座標 種別 [イベントID] [if:フラグ=真偽]
pallet-kid 8,6 npc:boy:static kanto.pallet.kid
pallet-oak-blocker 5,1 npc:oak:static kanto.pallet.oak-block if:kanto.pallet.got-starter=false
```

理由:

- **Tiled の価値はタイルを「塗る」ことにあるが、塗るタイルが1枚も存在しない**
  （[`../game-plan.md`](../game-plan.md) §10）。v0.7 で必要なのは
  通行可否・地形・接続・オブジェクトだけで、これは文字で書ける
- `maps-src/`（Tiled の原本）は**リポジトリに入れられない**（原作マップの写しのため）。
  一方この形式は数値と構造だけなので**コミットできる。**
  原本がコミットできないと、生成物と原本が別々の場所にある状態が常態化する
- 差分が読める。「どのマスの通行判定を変えたか」が git の diff にそのまま出る

**Tiled への移行は、`tools/convert-map.ts` に読み込み口を1つ足すだけ**で済む。
出力スキーマは変わらないので、ゲーム側は何も知らなくてよい ―― これが §2 の狙いだった。

## 3. マップの構造

```ts
type MapData = {
  id: MapId;                        // "kanto-pallet-town"
  region: RegionId;
  size: { width: number; height: number };   // タイル単位

  layers: {
    ground: TileId[];               // 地面
    decoration: TileId[];           // 上に乗る装飾
    overhead: TileId[];             // プレイヤーより手前に描く（木の上部など）
  };
  collision: boolean[];             // 通行可否
  terrain: TerrainId[];             // 草むら・水上・砂 等（エンカウント判定に使う §5）

  warps: Warp[];
  objects: MapObject[];
  encounters?: EncounterTableId[];  // capture.md §9 への参照。**地形が方式を決める**（§7.3）
  flyPoint?: { x: number; y: number; flag: FlagId };  // そらをとぶ の行き先（§7.2）
  onEnter?: EventId;                // マップに入った瞬間に走る（§7.2）
  bgm?: string;
};
```

- レイヤは3枚に固定する。可変にすると Tiled 側の運用が崩れる
- `collision` と `terrain` を**タイル画像から推測しない**。明示的な配列として持つ
  （見た目とルールを分離しておかないと、タイルを差し替えた瞬間に挙動が変わる）

### マップ接続

```ts
type Warp = {
  at: { x: number; y: number };
  to: { map: MapId; x: number; y: number; facing: Direction };
  trigger: "step" | "interact";     // 踏む / 調べる（ドアなど）
};
```

**検証項目**: 全 `warp.to.map` が存在し、座標がマップ範囲内で、通行可能タイルであること。
数百マップを手で繋ぐ以上、接続ミスは必ず起きる。CIで潰す（[`data-schema.md`](data-schema.md) §6）。

## 4. オブジェクトと NPC

```ts
type MapObject = {
  id: string;
  at: { x: number; y: number };
  kind:
    | { type: "npc"; sprite: SpriteId; movement: "static" | "wander" | "route" }
    | { type: "trainer"; trainer: TrainerId; sight: number; direction: Direction }
    | { type: "item"; item: ItemId; hidden: boolean }
    | { type: "sign" }
    | { type: "obstacle"; clearedBy: FieldAbilityId };   // §7
  event?: EventScript;              // §6
  condition?: Condition;            // このフラグが立っていれば出現／消滅
};
```

- **トレーナーの視線**（`sight`）は、向いている方向に N マス。原作の挙動（v0.12 で実装・§9.5）
- **`movement` は `static` だけ実装する。**【決定・v0.12】NPC が歩くと経路探索の道具が壊れる（§9.5）
- `condition` により、イベント進行でNPCが現れたり消えたりする
- 撃破済みトレーナーは `flags` で管理し、再戦は原作準拠で行わない（施設で戦えるため）

## 5. エンカウント判定

1歩ごとに判定する（原作準拠）。

```
歩いたタイルの terrain がエンカウント対象か
        │ Yes
        ▼
エンカウント率で抽選 → 成立したら EncounterTable から抽選
```

- エンカウント率は `terrain` ごとに定義（草むら・洞窟・水上で異なる）
- 抽選は [`capture.md`](capture.md) §9 の `EncounterTable` を参照
- **連続で出続ける／全く出ない、の救済を入れる**（直前のエンカウントから最低歩数、
  一定歩数を超えたら確率上昇）。原作より緩めてよい ―― 9地方を周回する本作では、
  理不尽な連続エンカウントは摩擦として重すぎる

### 5.1 実測（v0.7）― 「救済」はひとつのものではなかった

草むらだけを 15 万歩ぶん歩かせて測った（基本遭遇率は 12% に設定）。

| 設定 | 遭遇回数 | 平均歩数 | 最小 | 中央 | 最大 | 実効遭遇率 |
| --- | --- | --- | --- | --- | --- | --- |
| **採用した設定**（猶予5歩＋pity） | 11,399 | 13.2 | 6 | 11 | **37** | **7.6%** |
| 猶予なし（pity のみ） | 18,099 | 8.3 | 1 | 6 | 36 | 12.1% |
| 救済ぜんぶ無し（原作風） | 17,660 | 8.5 | 1 | 6 | **79** | 11.8% |

分かったこと:

1. **`rateByTerrain` は実効遭遇率ではない。** 猶予歩数5があるだけで 12% → 7.6% に落ちる。
   猶予は「連続で出続ける」を止めるつもりの仕掛けだったが、
   実際には**遭遇の総量そのものを4割減らしている。** 設定値を体感値だと思ってはいけない
2. **pity は平均をほとんど動かさない**（8.5 → 8.3）。効くのは分布の裾で、
   最悪ケースを **79歩 → 37歩** に半減させる
3. したがって **2つを「救済」とひとくくりにして増減させてはいけない。**
   猶予は総量を削る調整、pity は裾を切る調整で、効く場所が違う

この表は `packages/core/src/world/movement.ts` の `ENCOUNTER` の直上に写してある。
実効値を固定するテストも置いた（`world.test.ts`）ので、
猶予歩数を触ると実効率が動いたことが検出される。

## 6. イベントシステム ―【最重要】

[`save-data.md`](save-data.md) の `RegionProgress.flags` は**器だけが存在していた。**
それを操作する仕組みがここになる。

### 表現 ―【決定】JSON のコマンド列にする

| 案 | 判断 |
| --- | --- |
| TypeScript でハードコード | ❌ 地方追加のたびにコードが増える。本設計の原則に反する |
| 独自スクリプト言語 | ❌ パーサとエディタ支援の自作コストが見合わない |
| **JSON のコマンド列** | ✅ **採用。** 技効果・ボール補正・ルールセットと同じデータ駆動 |

```ts
type EventScript = EventCommand[];

type EventCommand =
  | { kind: "message"; speaker?: string; text: string }
  | { kind: "choice"; prompt: string; options: { text: string; then: EventScript }[] }
  | { kind: "if"; cond: Condition; then: EventScript; else?: EventScript }
  | { kind: "setFlag"; flag: FlagId; value: boolean }
  | { kind: "battle"; trainer: TrainerId; onWin?: EventId; onLose?: EventId }  // 参照のみ
  | { kind: "giveItem"; item: ItemId; count: number }
  | { kind: "givePokemon"; species: SpeciesId; level: number }
  | { kind: "takeMoney" | "giveMoney"; amount: number }
  | { kind: "healParty" }
  | { kind: "warp"; to: MapId; x: number; y: number }
  | { kind: "moveObject"; object: string; path: Direction[] }
  | { kind: "faceObject"; object: string; direction: Direction }
  | { kind: "wait"; frames: number }
  | { kind: "playSe" | "playBgm"; id: string }
  | { kind: "shop"; inventory: ShopId }          // economy.md §5
  | { kind: "openBox" | "openDex" };

type Condition =
  | { kind: "flag"; flag: FlagId; value: boolean }
  | { kind: "badges"; op: ">=" ; count: number }
  | { kind: "hasItem"; item: ItemId }
  | { kind: "hasSpecies"; species: SpeciesId }
  | { kind: "and" | "or"; of: Condition[] };
```

### インタプリタ

- `packages/core` に置く。**描画に依存しない**
- `message` や `wait` のような**演出を伴うコマンドは、実行を中断して UI に制御を返す**
  （[`ui-flow.md`](ui-flow.md) §4 のバトルと同じ考え方 ―― core は時間を持たない）
- イベントは**原子的に完了する**ものとして扱い、実行の途中状態はセーブしない。
  中断が必要な長大イベントは、フラグで区切って複数イベントに分割する

### `battle` コマンドだけは原子性を保てない

バトルは数分かかる。**「イベントは原子的」という前提と正面から衝突する。**
ブラウザを閉じられたら、イベントの途中でセーブが存在しない状態になる。

**決定: `battle` コマンドはイベントを2つに分割する境界として扱う。**

```
イベント前半（会話 → battle 開始）
      │  ここでフラグを立て、バトルを開始する。イベントはここで終了
      ▼
バトル（この間の中断は「バトルからの離脱」として扱う）
      │
      ▼
イベント後半（フラグと勝敗を条件に、別イベントとして起動）
```

- `battle` コマンドは `EventScript` の**最後のコマンドでなければならない**（検証項目）
- `onWin` / `onLose` は**別のイベントIDへの参照**にする。インラインのスクリプトにしない
- バトル中に中断された場合は、次回起動時に**バトル直前の状態から再開**する
  （トレーナー戦をやり直す。進行は巻き戻らない）

インラインの `onWin` を許すと「バトルを含むイベントの途中状態」が発生し、
セーブできない領域がゲーム内に生まれてしまう。**型のレベルで塞ぐ。**

### フラグIDは静的データ側で宣言する

```ts
// data/regions/kanto/flags.json
["kanto.oak.received-starter", "kanto.gym1.cleared", "kanto.rocket.hideout-open", ...]
```

- **宣言のないフラグを `setFlag` / `Condition` が使っていたら検証エラー**にする
- タイプミスで永久に立たないフラグは、発生してから原因を突き止めるのが極めて困難。
  [`data-schema.md`](data-schema.md) §6 の「調整項目」だったが、**宣言必須で確定する**
- 命名は `<地方>.<系統>.<内容>` のドット区切り

## 7. フィールド技 ―【決定】秘伝技を廃止する

原作では いあいぎり・なみのり 等の秘伝技を覚えたポケモンが進行に必要になる。

**決定: 秘伝技を廃止し、進行能力は「道具または進行フラグ」で解放する。**

```ts
type FieldAbilityId = "cut" | "surf" | "strength" | "rockSmash" | "fly";
```

- 障害物は `{ type: "obstacle"; clearedBy: FieldAbilityId }` として置く
- 対応する能力は、バッジ取得や道具入手で**プレイヤー自身が獲得する**（手持ちに依存しない）

### 理由

- 秘伝要員がパーティ枠を圧迫するのは、**9地方を周回する本作では特に苦痛**になる
- 「技を覚えさせる／忘れさせる」という独立したサブシステムが丸ごと不要になる
- 第7世代以降の原作も実質この方向（ライドポケモン等）

[`capture.md`](capture.md) §8、[`progression.md`](progression.md) の
「周回の摩擦を減らす」方針と一貫している。

### 7.1 実装（v0.12-d）

5つとも実装した。**ゲームのコードに「いあいぎり」という文字列は1つも無い。**
能力の一覧・解放条件・文面は `packages/data/field-abilities.json` にある。

| 決めたこと | そうした理由 |
| --- | --- |
| 解放条件は `Condition` を使い回す | 分岐・NPCの出現条件と同じ型。「解放条件」専用の型を作ると書き方が2つに割れる |
| 条件は **フラグ ∧ バッジ** の2段 | 教われば覚える／バッジが licence。原作の「バッジが無いと使えない」をデータだけで表せる |
| `WorldState.abilities` は**派生値**。保存しない | 保存すると「フラグは消えたのに なみのり だけ使える」状態を作れてしまう |
| どけた障害物（`cleared`）も**保存しない** | 原作と同じで出入りすれば戻る。セーブに「世界のどこを壊したか」が溜まらない |
| どけた印は `マップID:オブジェクトID` | オブジェクトIDはマップの中でしか一意でない。名前だけだと別の町の岩まで消える |
| 水は**通行不可のまま置き、能力で例外にする** | 逆にすると、能力の実装を消した瞬間に海の上を歩けるマップができる。既定は塞がっている側へ倒す |

消える処理は `visibleObjects()` の1箇所に入れた。
当たり判定・描画・トレーナーの視線がそこを通るので、**3つが勝手に揃う。**

> **秘伝マシンは道具にもしない**（v1.1-b）。わざマシンを取り込むとき、
> 公式データには HM01〜HM08 も同じ表に入っている。技として実装済みのもの
> （いあいぎり・なみのり・かいりき・たきのぼり）もあるが、**「教える道具」を作ると
> 廃止した機構が裏口から戻ってくる。** `machines.tsv` に理由つきで8件落としてある。

### 7.3 何をする能力か（v1.1-c）

v0.12-d の5つは**どれも「障害物をどける」**だった。だから `FieldAbility` は
解放条件しか持っていなくてよかった ―― 釣りと探知が入って初めて、
**「何をする能力か」という欄が要る**ことが分かる。

```ts
type FieldEffect =
  | { kind: "clear"; then?: { method } }   // どける（省略時これ。既存5件は無変更）
  | { kind: "walk"; terrain }              // その地形の上を移動できる
  | { kind: "fish"; method }               // 水面を調べて釣る
  | { kind: "reveal" }                     // 隠れているものを見つける
  | { kind: "travel" };                    // 行った町へ飛ぶ
```

**省略したら `clear`。** 既存の いあいぎり・かいりき はデータを1文字も変えていない。

| 決めたこと | そうした理由 |
| --- | --- |
| `fieldActions` は**1問だけ**答える（向いているマスに対して何をするか） | 「移動できるか」と「調べたら何が起きるか」を1つの関数にすると、どちらでもない `walk` が両方に嘘の答えを返す |
| `walk` と `travel` は `null` を返す（効く場所が違う） | **黙って何も書かないのと、理由つきで何もしないのは別**（`inert` な特性と同じ運用） |
| さおは**良いものが先に当たる**（選ばせない） | 原作に無い操作。選択肢が1つ増えるたびに歩みが遅くなる |
| いわくだき の野生は `clear.then` の1行 | 「どける」と「出る」を1つの能力に持たせたので、他の能力にも `then` を足すだけで付く |
| 隠しアイテムは `visibleObjects()` で消す | **v0.12-d の障害物と同じ1箇所。** 描画・踏みつけ・視線が勝手に揃う |

#### `canSwimTo` に "water" と書いてあった

v0.12-d の実装は `terrain === "water" && abilities.includes("surf")` ―― **`core` が
特定の地形と特定の能力の名前を知っていた。** 地形と能力の対応は
`field-abilities.json` にしかないので、そちらから導く形に直した。

`WorldState.walkable`（`abilities` と同じ派生値・保存しない）に入れる。
足したとき**片方だけ入れ直す場所が4箇所あって、実際に
「なみのり は使えるのに水に入れない」世界ができた** ――
`syncAbilities()` に2行まとめて、呼ぶ側が選べないようにした。

#### 固定シンボル ―― `EventCommand` に1つ

三鳥・ミュウツー・カビゴンは「その場で始まる野生戦」。
`battle`（トレーナー戦）に相乗りさせず `wildBattle` を足した ――
**勝っても逃げても「もう そこには居ない」**という終わり方が違うため。

フラグは**戦う前に立てる。** 結果で分けると、逃げたときだけシンボルが残る。
v0.7 から宣言だけされていた `EncounterTable.method: "static"` は、
結局この形では要らなかった（表ではなくイベントが持つ方が素直だった）。

### 7.2 そらをとぶ

行き先は**マップ自身が名乗る**（`MapData.flyPoint`）。
「行ける町の一覧」を別の表に持つと、マップを消したときにそこだけ残る。

`flyPoint.flag` は「一度でも来たか」の記録で、`onEnter`（マップに入った瞬間に走る
イベント）で立てる約束にしてある。**約束を破ると検証 #82 が落ちる** ――
行き先として宣言したのに一生選べないマップは、遊んで気づくには遠すぎる。

`onEnter` はこの版で足した唯一のイベント口で、四天王の「戻れない部屋」もここで塞ぐ。

### 7.3 なみのり と出現テーブル

水の上を歩けるようにしたら、**草むらのポケモンが海から出てきた。**
`MapData.encounters` が1つしか持てず、`EncounterTable.method` を誰も見ていなかった。

- `encounters` を配列にし、**地形が方式を決める**（`METHOD_BY_TERRAIN`）
- 表が無い地形では抽選そのものをしない（乱数を空回しすると再生が合わなくなる）

## 8. マップ作成のワークフロー

数百マップを作る以上、**道具立てがそのまま生産性になる。**

1. Tiled でマップを描く（タイルセットは地方間で共有する）
2. `tools/convert-map.ts` で自作スキーマへ変換
3. `tools/validate.ts` で検証
   - warp の接続先が存在し、通行可能タイルか
   - `encounters` の参照先が存在するか
   - `trainer` / `item` / `flag` の参照が存在するか
   - 到達不能な領域がないか（**プレイヤーが入れない/出られない区画の検出**）
4. 地方の全マップが揃ったら [`capture.md`](capture.md) §7 の到達可能性検証を回す

**タイルセットは地方間で共有する。** カントーとジョウトは特に共有率が高く、
[`regions.md`](regions.md) §2 で実装順を隣接地方にした理由がここにある。

### 9.1 v0.7 の結果

完了条件は満たした。マサラタウン・主人公の家・オーキド研究所・1番道路の4枚で、
家 → 町 → 研究所（最初の1匹）→ ライバル戦 → 町 → 1番道路 → 野生戦 → 逃走 まで通る。
同じ道行きを2通りで検証している ―― `core` だけで通す単体テストと、
ブラウザを実際に動かす `tools/playthrough.mjs`。

**フラグによる分岐は2つの形で効く**ことを確認した:

- `Condition` を持つオブジェクトは**存在ごと消える**。
  最初の1匹を受け取るまで、町の北口はオーキド本人が塞いでいる
- イベント内の `if` は**同じNPCの台詞を変える**

#### 実装が設計を訂正したところ

**1. 「マップを1枚足すコスト」は思ったより座標にある。**
コードは1行も増えなかった（狙いどおり）が、**手で書いた座標は必ず間違える。**
このバージョンで検証が捕まえたのは、warp の接続ミスではなく
「机に囲まれて一生話しかけられない NPC」と「四方を塞がれた1マス」だった。
そこで検証項目 #55（到達不能な区画）に加えて **#56（話しかけられないオブジェクト）**
を足した。**歩けるマスが全部繋がっていることと、置いたものが起動できることは別。**

**2. `battle` を「末尾のみ」に縛った判断は正しかったが、縛り方が足りなかった。**
§6 では「`EventScript` の最後のコマンド」と書いていたが、
`if` や `choice` の枝の中に `battle` がある場合を規定していなかった。
実装では**「自分が属する列の末尾であり、かつ祖先も全て末尾である」**まで縛った。
ライバル戦は「選んだ1匹に応じて相手が変わる」ため `if` の3分岐の底に `battle` があり、
この規定が無いと最初の実データで破れていた。

**3. `givePokemon` の技指定が UI まで届いていなかった。**
コマンドは `moves?` を持っていたのに、`EventEffect` に載せ忘れていた。
型は通り、テストも通り、**ブラウザで動かしてヒトカゲが「ひのこ」1つで戦っていた**
ことで初めて分かった。`tools/playthrough.mjs` を書いた理由がこれ。

**4. 段差は「地形」で表現できた。**
一方通行の向きを地形IDに持たせる（`ledge-down` 等）案もあったが、
南向き以外は9地方を通してごく少数なので、**1方向に固定して定数1つで表した。**
必要になったら地形を増やす。

#### 【訂正・v0.8】ドアは「調べる」ではなく「踏む」

v0.7 では家と研究所のドアを `interact`（調べる）warp にしていた。
**その結果、建物に入れなかった。**

ドアのマスは歩けるので、近づいて「上」を押すと **調べる前にドアの上へ乗ってしまう。**
乗ってしまえば目の前は壁なので、そこで「しらべる」を押しても何も起きない。
原作でもドアは踏んで入るもので、`interact` は看板や机に使うものだった。

**検証項目 #60 を足した ―― 「調べる warp が歩けるマスにあってはならない。」**
歩けるマスにある `interact` warp は、**構造的に絶対に起動できない**。
到達不能な床（#55）や話しかけられないNPC（#56）と同じ種類の誤りで、
やはり「置いたのに起動しない」形をしている。

#### 【追加・v0.8】押しっぱなしで歩く

1入力1歩にしていたため、スマホでは**指で何度も叩く**操作になっていた。
さらに歩行アニメ中の入力を捨てていたので、連打しても進まなかった。

- 「今どちらを押しているか」を状態として持ち、**離すまで歩き続ける**
- 向き直りの直後に、同じ方向へ**もう一度だけ試す** ――
  進める先なら1タップで動き、壁や看板なら向き直りだけで止まる。
  「壁際で向きを変えられる」という向き直りの目的は損なわれない
- 十字キーから「けってい」を分けた。十字の中央に置くと、
  歩いているつもりで話しかけてしまう

**歩かなかったとき（向き直り・壁）にも待ち時間を入れた。**
これが無いと、押しっぱなしの繰り返しが `await` を挟まずに回り続け、
**画面が固まって指を離すことすらできなくなる。** 実装中に一度そうなった。

#### v0.7 では**やっていない**こと

- **世界の状態を保存していない。** フラグ・所持金・手持ちはリロードで消える。
  `SaveData` のスキーマ変更（v2 → v3）を伴うので v0.9 の IndexedDB 移行とまとめる
- **HP がマップに持ち越されない。** 手持ちはまだ `PartySpec`（設計図）で、
  戦うたびに満タンから始まる。`healParty` も演出だけ。**v0.8 の最優先はこれ**
  （[`../game-plan.md`](../game-plan.md) §8.3 論点3の結果）
- **トレーナーの視線**（`sight`）は型にあるだけで判定していない。v0.10
- NPC の `movement`（`wander` / `route`）も同様に未実装

### 9.2 v0.9 の結果 ― 町を1つ足すのに、コードは1行も要らなかった

トキワシティ（町・ポケモンセンター・フレンドリィショップ・民家の4枚）を足した。
**変更したのは `.map` ファイル4枚・`events.json`・`flags.json`・`shops.json` だけ。**
`packages/game` も `packages/core` も1行も触っていない。

これは v0.7 の「エンジンとデータを分ける」判断が実際に効いた最初の証拠になる。
ただし、無条件ではない ―― 検証が**9件のエラーで止めた**。

| 検証が止めたもの | 内容 |
| --- | --- |
| #47 warp の接続 | 建物の入口が、接続先の warp マスの上を指していた（入った瞬間に押し戻される無限往復）×3 |
| #48 オブジェクト | カウンターや机の上に NPC を置いていた ×5 |
| #55 到達可能性 | 北の出口を作ったが、警備員で塞いだので誰も立てないマスが1つ残った |

どれも**そのまま出せば「入れない建物」「話しかけられない店員」になる。**
v0.7 の収穫（#55・#56）と同じ形の誤りを、町を1つ足しただけで3種類やり直している。
**人はマップを置くたびに同じ間違いをする。** 検証に落としておく価値はここにある。

### 9.3 `WorldState` と `PlayerState` の二重の持ち主を解消した

`core` が読み書きする `WorldState`（`flags` / `badges` / `money` / `bag` / `partySpecies`）と、
UI が持つ `PlayerState` が、**同じものを別々に持っていた。**
v0.9 で `player` を唯一の持ち主にした（[`save-data.md`](save-data.md) §9.7）。

繋いだ瞬間に、**同じ道具を2回もらっていた**ことが分かった ――
`core` の `giveItem` ハンドラと UI の `gotItem` 効果が両方 +1 していた。
入れ物が別だったので、合計だけが静かに倍になっていた。

### 9.4 台本は座標を数えるのをやめた

`tools/playthrough.mjs` は v0.7 から「押した回数」でマップを歩いていたが、
**町を1つ足しただけで全部通らなくなった。**
今は `maps.json` を読んで経路探索する（段差の一方通行・踏む warp・オブジェクトの
通行判定まで含む）。目的地はマップをまたいで指定できる。

副産物として、**負けて家に飛ばされても台本が続く**ようになった。
座標を数える台本は、想定していない場所に飛んだ時点で意味を失っていた。

### 9.5 v0.12 の結果 ― 視線・ジム・バッジ

§4 に型だけあった `sight` を実装した。規則は原作のまま
（向いている方向に N マス／壁と他のオブジェクトで切れる）で、
1つだけ足したのが **近い方を優先する**という決まり。
視線が重なるマスで遠い方が先に来ると、すり抜けて奥から呼ばれたように見える。

**視線は野生より先に見る。** 草むらを横切ってトレーナーの前に出たとき、
野生が割り込むと「見つかったのに何も起きない」状態になる。

#### 視線は画面に描く

原作は視線を描かない。だが**本作のトレーナーはただの四角**なので、
どちらを向いているか分からないまま見つかるのは理不尽でしかない。
向いている側に印を置き、届く範囲を薄く塗る。
**判定と同じ規則で切る**（`spotterAt` と同じく壁とオブジェクトで途切れる）
―― 見えているものと当たり判定がずれると、そちらの方が理不尽になる。

#### 「！」は押さなくても消える

見つかったのはこちらの操作ではない。
「押さないと進まない」を挟むと、理不尽さの上に手間が乗る。

#### NPC は動かさない ―【決定】

`movement` は型に `wander` / `route` があるが、**`static` 以外は実装しない。**

理由は経路探索。`playthrough.mjs` も `shots.mjs` も
「オブジェクトは動かない」前提でマップを歩いている。
NPC が歩くと**この2つの道具が同時に壊れる**わりに、得られるのは町の賑わいだけ。

賑わいが欲しくなったら「**向きだけ変える**」で足す。マスを動かさない限り、
経路探索は成り立ち続ける。検証 #79 が `static` 以外を止める。

#### バッジは増分ではなく到達点

`giveBadge` が受け取るのは「これで何個目になるか」。
同じイベントを2回踏んでも増えず、ジムの順番を入れ替えても数が狂わない。
バッジは進行の目盛りなので、**何個持っているかだけが意味を持つ**。

#### 台本が「視線」で歩けなくなった

視線バトルは**会話から始まる**（向こうから話しかけてくる）。
`goToMap` は会話を捌かずに次のキーを押していたので、
以降の入力が全部そちらに吸われ、**歩いていないのに歩いたことになっていた。**
会話を消してから進む形に直した。

同じところでもう1つ。ジムを通すために手持ちを Lv50 まで上げたのに、
**ヒトカゲの「ひっかく」と「ひのこ」ではイワークを削り切れず、全滅した**
（ぼうぎょ160・ほのお半減）。レベルだけでは相性を越えられないことが、
台本の側で先に出た形になる ―― ゲーム内の子どもが言っているとおりだった。

### 9.6 v0.12-b の結果 ― 町2つとジム2つを、コード0行で足せた

§9.2 で「町を1つ足すのにコードは1行も要らなかった」を確かめた。
v0.12-b はその**8倍の規模**（マップ14枚・トレーナー11人・イベント45件）で
同じことを試した結果になる。

| 足したもの | コード |
| --- | --- |
| 3番道路・おつきみやま・4〜6番道路 | 0行 |
| ハナダシティとジム2（カスミ）・ポケセン・ショップ・民家 | 0行 |
| クチバシティとジム3（マチス）・ポケセン・ショップ | 0行 |
| **バッジで品揃えが変わるショップ** | **0行** |

**バッジ連動のショップにコードが要らなかった**のは、
イベントの条件に `badges` が v0.7 から入っていたため。
`if` で `shop` の `inventory` を選ぶだけで済む。

```
いらっしゃいませ!
if badges >= 4 → shop kanto-mart-3
else if badges >= 2 → shop kanto-mart-2
else → shop kanto-mart-1
```

足したコードは**検証1つだけ**（下記 #80）。

#### 訂正: 到達可能性を1枚の中でしか見ていなかった

検証 #55 は**マップ1枚の中**の孤立区画を探していた。
おつきみやまを書いたとき7行目の壁が右まで届いていて**南半分が丸ごと切れていた**が、
そこは「到達できないマス」ではなく「行き止まりだが繋がっている区画」なので素通りした。

気づいたのは、台本が「経路なし」と言ったとき。

**訂正: 地方の入口から、その地方の全マップへ歩いて行けることを見る（#80）。**
踏む warp を辿り、段差の一方通行も条件つきオブジェクトも同じ規則で扱う。
足したあと**わざと壁を戻して、実際に止まることを確かめた。**

#### 台本の穴が2つ出た

1. **条件つきのオブジェクトを素通りできる前提だった。**
   経路探索は「進行で消えるもの」を壁として数えない。だが実際には塞いでいるので、
   おつみみやまのやまおとこに**永久にぶつかり続けていた**。
   ぶつかったら話しかける（人がやることと同じ）ようにした。
2. **`drain()` が店を閉じていた。** 品揃えは `#menu` ではなく
   会話枠の選択肢として出る。`drain()` は選択肢の**いちばん下**を押すので、
   開いた瞬間に「やめる」を選んでいた。

どちらも「道具が世界の作りに追いついていない」形で、
**世界を広げるたびに道具の前提が1つ壊れる**、という v0.9 からの傾向がそのまま続いている。

### 9.7 v0.12-c ― ジムの順番も、条件だけで縛れた

シオン・ヤマブキ・タマムシ・セキチクとジム4〜6を足した。マップは 33 → 53枚。
**ここもコードは1行も要らなかった**（検証も足していない）。

原作のバッジ順は エリカ(4) → キョウ(5) → ナツメ(6) だが、
地理的にはヤマブキが手前にある。原作は「飲み物を欲しがる警備員」で塞いでいた。

本作は**バッジの数で塞ぐ**。

```
けいび:
  if badges >= 5 → 「どうぞ おとおりください」＋ 通す
  else           → 「バッジ 5つの ちょうせんしゃしか あいません」
```

`badges` はイベントの条件に v0.7 から入っている。
**進行の順番はデータの問題であって、コードの問題ではない** ―― これで3回目の確認になる
（v0.9 の町追加、v0.12-b のショップ、今回のジム順）。

#### ポケモンタワーとサファリゾーンは「置くだけ」にした

どちらも原作では専用の機構がある（ゴーストの正体・ボールを投げる別ルール）。
**機構が無いまま形だけ作らない**という v0.4 からの方針に従い、
タワーは1階だけ・サファリは看板だけにしてある。
「まだ しめとる」と言う管理人が居るのは、**無いことを黙って隠さない**ため。

### 9.8 v0.12-d ― フィールド技。ここで初めてコードが要った

v0.9・v0.12-b・v0.12-c と「町を足すのにコードは0行」が3回続いたが、
**フィールド技は0行では足せなかった。** 足した機構は3つだけ:

| 足したもの | なぜコードが要ったか |
| --- | --- |
| `fieldAbilitiesFor` / `obstacleKey` / `canClear` | 「持っている能力」という概念そのものが無かった |
| `interact` の `obstacle` 分岐 | 調べた先が**イベントでも warp でもない**3つめの答えになった |
| `MapData.onEnter` | 「マップに入った瞬間」という口が1つも無かった |

逆に**データだけで済んだ**もの:
5つの能力の解放条件・解放してくれる NPC・障害物の設置・そらをとぶ の行き先9つ。
能力を1つ増やすときに触るのは `FIELD_ABILITIES` の1行と JSON だけになっている。

#### 3つの前提が同時に壊れた

1. **`EncounterTable.method` を誰も見ていなかった。**
   水の上を歩けるようにした瞬間、草むらのポケモンが海から出てきた。
   `encounters` を配列にし、地形が方式を決める形へ直した（§7.3）。
2. **到達可能性が障害物を壁として数えていた。**
   #55 も #80 も「置いた岩の先」を到達不能と報告した。
   どちらも**地形として繋がっているか**を見る場所なので、障害物と水は通れる扱いにした。
   「今の進行度で行けるか」は #84（その技が世界のどこかで手に入るか）が別に見る。
3. **`wild-usable` が Lv5 固定で測っていた。**
   なみのり の表を Lv15〜 で作ったのに「Lv5 で技が無い」と言われた。
   実際に出るレベルで測り直した ―― **測る対象が違えば、通っても落ちても意味が無い**
   （v0.12 のライバル戦と同じ誤り）。

#### 置き場所は、条件が正しくても間違える

セキチクの おおきな いわ を最初 (10,8) に置いた。
条件も種別も正しかったが、そこは**ポケモンセンターの入口へ登るマス**で、
街の施設が丸ごと閉じた。#80 が「ポケセンへ歩いて行けない」と言って止めた。

v0.12-c のヤマブキの警備員（条件は正しいのに扉を塞げていなかった）と同じ形で、
**向きだけが逆**になっている。どちらも検証が拾ったので、置き場所は目視で守らない。

### 9.9 v0.12-e ― カントーが輪になった

グレンじま・トキワジム・19〜21番水道を足して**ジム8つが揃った**。マップは 53 → 61枚。
**コードは1行も足していない**（検証を1つ足しただけ）。

いちばん大きいのは形が変わったこと。

| | v0.12-d まで | v0.12-e |
| --- | --- | --- |
| カントーのマップ | 49枚 / 隣接ペア 48 | 57枚 / 隣接ペア 57 |
| 木か | **ちょうど木**（辺 = 頂点 − 1） | **閉路が1つ** |

21番水道が グレンじま と マサラタウン を結んだので、
**グレンへ南から入って北から出られる。** ここまでのカントーは、どの道路も
ちょうど2か所を繋ぐだけの一直線だった。

閉路を作るのに要ったのは `.map` を3枚書くことだけで、
`warp` で部屋を任意に繋ぐ作り（初代〜BW と同じ）が最初から閉路を許していた。
検証 #80 も BFS なので、そのまま通っている。

グレンじまへは**なみのり が無いと行けない。** これは文章ではなくテストで縛ってある
（能力別に踏破可能なマップを塗って、`kanto-cinnabar-island` が入らないことを見る）。

#### 訂正: 建物を出ると町の反対側に立っていた

`#85` を足したその場で、**7か所が落ちた。**

```
kanto-fuchsia-city (10,7) → kanto-fuchsia-pokecenter から戻ると (3,4)＝10マス離れた場所に出る
```

v0.12-c の4つの町（タマムシ・ヤマブキ・シオン・セキチク）で、ポケモンセンターや
ショップを出ると**町の反対側に飛ばされていた。** 原本を写して座標だけ直し忘れた形。

見逃した理由がはっきりしている ――
**「歩けないマス」でも「繋がっていない」でもない**ので、#47 も #55 も #80 も通る。
遊べば1秒で分かるのに、機械の目には正常に見える種類の壊れ方だった。

> **#85: 入って出たら、入口の前に立っている。**
> 出入口が1つしかない建物についてだけ見る（複数ある建物は対がひとつに決まらない）。

足した直後に**わざと1件戻して、実際に止まることを確かめた**（#80 と同じ手順）。

### 9.10 v0.12-f ― 四天王。カントーが1本で終わるようになった

22・23番道路、チャンピオンロード、セキエイこうげん、四天王4人＋チャンピオンを足した。
マップは 61 → 71枚。**ここもゲームのコードは0行**（検証を1つ足しただけ）。

#### 「戻れない部屋」は、機構ではなくデータで作れた

v0.12 の計画では、ここが**「v0.12 で初めて本物のコードが要る場所」**だと見ていた。
実際に書いてみると要らなかった。

| やりたかったこと | どう作ったか |
| --- | --- |
| 入ったら戻れない | **戻る warp を置かない。** それだけ |
| 次の扉は勝つまで開かない | 扉のマスに、条件つきのオブジェクトを1つ置く |
| 負けたら追い出される | 既存の全滅処理がそのまま働く（復活地点へ戻る） |

「戻れない」は**足す機構ではなく、置かない選択**だった。
`onEnter`（v0.12-d）を使うつもりでいたが、使わずに済んでいる ―― 
**先に用意した口が、結局要らなかった**という記録として残す。

#### かいりき の見せ場

チャンピオンロードの (4,2) に かいりき の岩を置いた。
北の出口へ続く道はここ1本なので、**岩をどけないと抜けられない。**

v0.12-d では かいりき は道具1つのための寄り道だったが、
ここで初めて進行そのものを止めている。
「抜けられないこと」も「どけると抜けられること」もテストで縛ってある。

#### 検証 #86 ― 出入口を、消えないもので塞いでいないか

扉のマスにオブジェクトを置く形にしたので、**条件を書き忘れると
その出入口は永久に死ぬ。** 見た目は普通の扉で、踏んでも何も起きない。

> **#86: 踏む warp のマスに、条件の無いオブジェクトが乗っていないこと。**

条件つきなら正しい使い方（勝つまで開かない扉）なので、そこだけを見分ける。
足したあと**わざと条件を外して、実際に止まることを確かめた。**

#### 台本が四天王に勝てなかった ―― 戦い方の問題だった

四天王を通そうとして、**ワタルに3連敗**した。手持ちは Lv100 が6匹。
負ける道理が無いので調べたところ、台本の戦い方そのものが原因だった。

| 直したこと | なぜ効いたか |
| --- | --- |
| 技を**順番に回す**（先頭から押していた） | ワタルは5匹中3匹が ひこう。**じしん を延々と0ダメージで撃っていた** |
| **とくしゅ技で揃える**（物理で殴っていた） | リザードンは こうげき 84 / とくこう 109。半分損をしていた |
| 手持ちを6匹に・ラムのみを持たせる | キクコの さいみんじゅつ + あやしいひかり はレベル差では解けない |

いちばん効いたのは**技を回す**ことだった。
「先頭の技を押し続ける」は、相性が0倍の相手に当たった瞬間に無限ループになる。

**これはゲームの欠陥ではなく、台本の欠陥。** 人なら1ターンで気づく。
ただ「レベルを上げれば通る」で押し切らずに済んだのは、
**負けた理由を数えたから**で、レベルを上げるほうを先にやっていたら
ずっと原因に気づかないままだった。

## 9.8 「隣とは何か」を1箇所にした（v1.1-a）

v1.0 まで、**同じ判定が3箇所に書かれていた。**

| どこ | 何を見ていたか |
| --- | --- |
| `tools/validate.ts` | 地方の連結性（#55）と、マップ1枚の塗りつぶし（#55・#56） |
| `tools/playthrough.mjs` | 台本の経路探索 |
| `tools/shots.mjs` | 撮影の経路探索 |

3つとも「段差は南向きにだけ2マス飛ぶ」「踏む warp は同じ1歩の中で移る」
「水は なみのり で越えられる」を**それぞれ書いていた**。
書いてある内容が同じうちは害が出ない ―― 出るのは規則が増えたときで、
**氷の床（v1.1-f）はこの3つを同時に壊す。**

そこで `core` に置き、道具はそれを呼ぶだけにした。

```ts
neighborsOf(map, world, x, y, options, mapById): Neighbor[]
canEnter(map, world, x, y, options): boolean
```

**能力は `WorldState` で渡す。** 台本は「なみのり を覚えた」「この岩をどけた」を
そのまま `abilities` / `cleared` に入れる ―― ゲーム本体と同じ形なので、
**経路探索とゲームが食い違いようがない。**

違うのは「見立て」だけで、options はその2つに絞ってある。

| 見立て | 誰が使うか | なぜ |
| --- | --- | --- |
| `ignoreConditional` | 検証・両台本 | 進行で消える門番を壁として数えると、開通済みの道まで閉じる |
| `ignoreObstacles` | 検証・撮影 | どければ通れる岩を壁にすると、その先が全部「到達不能」になる |
| `followWarps: false` | 塗りつぶし（#55） | 1枚の中の「入れるが出られない区画」を探している |

### 一本化して初めて食い違いが見えた

`shots.mjs` は**コメントに「障害物は壁のまま」と書いてあり、コードはそうなっていなかった。**
どちらが正しいか決めずに置き換えたら、撮影が2か所で `△`（狙いと違う場所を撮った）を出した
―― チャンピオンロードの岩の先が全部撮れなくなっていた。

正しいのはコードの方だった（撮影用のセーブは能力を全部持っている）。
**3箇所に散っている間は、コメントと実装がずれても誰も気づかない。**

### 世界を広げるたびに、道具の前提が1つ壊れる（4件目）

| 版 | 広げたもの | 壊れた前提 |
| --- | --- | --- |
| v0.12-b | 洞窟 | 到達可能性をマップ1枚の中でしか見ていなかった |
| v0.12-d | 障害物・なみのり | 経路探索が「今できること」を知らなかった |
| v0.12-f | 戻れない部屋 | 撮影が水を通れず、別の町を撮っていた |
| **v1.1-a** | **海の出現表** | **`spot()` が「フィールドは必ず出ている」と思っていた** |
| **v1.1-b** | **バッグから使う道具** | **`#open-bag` を「開く」だと思っていた（実際は開閉の切り替え）** |
| **v1.1-c** | **道をふさぐ固定シンボル** | **撮影用セーブがカビゴンをどけていなかった（8枚が16番道路で止まった）** |

クチバの海には v1.0 まで出現表が無かった。取り込みで15枚ぶんの surf 表が付いた瞬間、
**なみのり の1歩の直後にバトルが割り込む**ようになり、`#field-canvas` を
30秒待って台本が落ちた ―― **一度も通っていなかった道**が、データが増えた日に通った。

直し方はいつも同じ形になる。**「たまたま起きなかったこと」を前提にしない。**
歩く関数は、現在地を見に行く前に「今バトルなら片付ける」を挟む。

カビゴンの件は**気づくのが1版おくれた。** v1.1-c では通し確認だけを回して
撮影を回さなかったからで、通しは たまたま カビゴンを起こす区間が
セキチクより先にあった ―― **順番が違えばそこで止まっていた。**

> **道具は2本とも回す。** 片方だけ緑なのは「壊れていない」の証拠にならない。

**ただし `spot()` の中でやってはいけない。** 最初そう直したら、
野生戦の回数を数える区間が「0回」になった ―― 数えたい相手を、
現在地を見るついでに黙って倒していた。**片付けるのは歩く関数の中だけ。**

### 台本の誤報は、ゲームの不具合に見える（v1.1-b）

わざマシンを「おぼえない」で断ったとき、台本は
**「やめたのに道具が 0こ になった」**と報告した。ゲームの側の取り返しのつかない
不具合に見えるが、実際には**1こ のまま残っていた。**

`#open-bag` は開く/閉じるの**切り替え**で、道具を使ったあとパネルは開いたまま
描き直される。そこをもう一度押した台本は**バッグを閉じ**、空のパネルを読んで
「0こ」と数えていた。

**確かめ方はいつも同じ。** 短い台本を1本書いて、その操作だけをブラウザでやってみる
―― 30分の通し確認の中で疑うより速く、しかも切り分けが1回で済む。
以後、台本の側では「押す」ではなく**「開いていることにする」**と書く。

### 台本を強くした変更が、別の台本の前提を壊す（v1.1-b）

v1.1-a で `goToMap` に「割り込んだバトルを片付ける」を足した。**それ自体は正しい。**
だが全滅の検査は「HP を1にする → 草むらへ歩く → 負ける」の順に書かれていて、
**歩いている途中で全滅し、ポケモンセンターで回復してしまう**ようになった。
草むらに着いた時点では満タンで、確かめたい状態が消えている。

直し方は**順番の入れ替えだけ**（草むらに着いてから弱くする）。
仕組みではなく段取りの問題なので、コードは1行も増えない。

> **「道具を強くしたら、その道具を使う側の前提を1つ壊す」**
> ―― §9.8 の表と同じ形が、台本どうしの間でも起きる。

## 9.9 公式データを2箇所から採ると、版がずれる（v1.1-b）

わざマシンの番号と技の対応は **FRLG（第3世代）** から取り込んでいる。
どの種がマシンで何を覚えるかの互換表は **第9〜7世代** から採っている
（`fetch-official.ts` が learnset の `'M'` を選る）。

**この2つは揃っていない。**

> でんげきは（tm34）は FRLG ではマシンだが、いま**誰もマシンでは覚えない。**

道具にすると「バッグに入っているが、どの手持ちに使っても断られるマシン」ができる。
書いた瞬間の検証 #95 がこれを捕まえた ―― **1本だけなので、手で見ていたら気づかない。**

対処は2つに分けた。

1. `fetch-machines.ts` が「互換表に持つ種がいない」を判定して落とす。
   **理由つきで `machines.tsv` に残る**ので、いつか互換表の版を変えたときに戻ってくる
2. マチスの贈り物だけ 10まんボルト に替えた（原作は でんげきは）。
   でんげきは 自体は技として実装済みで、レベルでは覚えられる ――
   **消えたのは「マシンとして配る」経路だけ**

**じてんしゃも同じ用心をしている。** 速くするのは見た目だけで、
**1入力＝1マスは変えない** ―― 2マス進む実装にすると `playthrough.mjs` と
`shots.mjs` が同時に、しかも黙ってずれる（§9.8 の3件目と同じ壊れ方）。
`core` は時間を持たないので、影響は `field.ts` の定数1つに閉じる。

## 9.10 構造の嘘 ―― ヤマブキが2叉路だった（v1.1-d）

v1.0 までのカントーには、**通っているのに間違っている**接続が1つあった。

| | v1.0 まで | 原作 |
| --- | --- | --- |
| 5番道路 | ハナダ → **6番道路へ直通** | ハナダ → ヤマブキ**北門** |
| 6番道路 | 5番道路 → クチバ | ヤマブキ**南門** → クチバ |
| ちかつうろ | 無い | 5番⇄6番の**任意の近道** |
| ヤマブキの出入口 | 2つ（西・東） | **4つ** |

**近道のほうが本道になっていた。** 地図としては繋がっているので、
検証も台本も何も言わない ―― 見つかるのは原作の地図と見比べたときだけ。

### けんもんじょ は「2つ warp を持つ小マップ」

ゲート建物はポケモンセンターと同じ形で、**新しい機構は1つも要らなかった。**
4棟足して、5〜8番道路の warp を繋ぎ替えただけ。

ちかつうろ も同じ ―― 入口の家2軒＋通路1枚で、
**ヤマブキを通らない道が「近道として」存在する**状態に戻った。

### 検証が7種類の間違いを1回で捕まえた

7枚のマップを足して繋ぎ替えたとき、最初の `npm run validate` で出たエラー:

| 出たもの | 何を間違えたか |
| --- | --- |
| 接続先が踏む warp の上（2件） | 扉のマスに着地させていた（無限往復になる） |
| 接続先が通行不可（2件） | 建物の壁に着地させていた |
| 調べる warp が歩けるマスにある（3件） | 階段を `interact` にしたが、他の扉は全部 `step` |
| 往復すると4〜6マス離れる（3件） | ジム・ポケセン・ショップの**戻り先が古い座標のまま** |
| 地方の連結性（1件） | `interact` の warp は `neighborsOf` が辿らない |

**最後の1件が設計の答えになった。** 階段だけ `interact` にする理由が無い ――
他の扉は全部 `step` なので、揃えたら連結性の問題も消えた。
**「例外を作らない」が、そのまま検査を通る道だった。**
