# 設計文書

実装前に設計を固めるための文書群。上位方針は [`../game-plan.md`](../game-plan.md) を参照。

## 設計の進め方：何を確定させ、何を先送りするか

設計を「完璧にする」対象を取り違えると、実装時に丸ごと作り直しになる。
以下の線引きを全文書で共通のルールとする。

### 今、完璧に確定させるもの

- **データ構造**（型定義・スキーマ）— 後から変えると全データの作り直しになる。最優先。
- **システムの境界**（何がどこに責務を持つか）— 依存の向きを間違えると剥がせなくなる。
- **キャラクター/世界のコンセプト**— 数値と違い、実装しても答えは出ない。今考えるべきもの。
- **計算式の定義**（ダメージ式など）— 原作準拠なので今確定できる。

### 実装してから決めるもの（設計では「調整項目」と明記する）

- 具体的な数値バランス（経験値テーブル、BP価格、捕獲率、AIの判断閾値）
- 演出のタイミング・尺
- UIの細かいレイアウト

数値は必ず**定数として1箇所にまとめ、コードに散らさない**。
そうすれば「実装してから決める」が安全になる。設計段階でやるべきはこの構造化であって、
数値そのものを当てにいくことではない。

## 設計を貫く3つの考え方

11文書を通して、判断の根拠になっているのは次の3つ。迷ったらここに戻る。

### 1. 「全部入り」はゴールではなく設計制約

エンジン（ルール）とコンテンツ（データ）を分離し、
**コンテンツを1件足すコストを限りなくゼロに近づける。**
技も、ボールも、施設も、ネームドも、地方も、全て「データを足すだけ」で増える形にした。
そうすれば「全ポケモン・全トレーナー」は実装課題ではなく入力作業になる。

### 2. 設計ルールは、文書ではなくCIと構造で守る

**文書はいずれ読まれなくなるが、CIは必ず実行される。**

- 全1,025種の到達可能性 → 入手経路のグラフ探索を CI で検証（[`capture.md`](capture.md) §7）
- ネームドの一貫性・戦術の重複 → 検証項目に落とす（[`data-schema.md`](data-schema.md) §6）
- マイグレーションの鎖 → 過去版サンプルを CI で通す（[`save-data.md`](save-data.md) §5）
- 「お金を持ち越さない」 → **お金の置き場所を地方の中にしか作らない**（[`save-data.md`](save-data.md) §3）
- 「他地方のポケモンを使わせない」 → **共通ボックスを地方チャレンジ中に開けなくする**（[`capture.md`](capture.md) §4）

規律を人間の注意力に預けない。

### 3. 途中で止まっても遊べるものが残る形にする

個人の長期開発で最も高い risk は「完成しないこと」。
そのため各マイルストーンを「そこで止まっても価値が残る」単位で切り、
**マップが1枚もない v0.3 の時点で遊べるゲームが成立する**構成にした
（[`../game-plan.md`](../game-plan.md) §8）。

## 3回目の見直しで検出した問題（2026-08-16）

### `Action` 型に道具・逃走がなかった（根幹）

type Action = { kind: "move" } | { kind: "switch" };

[`capture.md`](capture.md) §2 は捕獲判定を式まで含めて設計しているのに、
**ボールを投げる行動がバトルの型に存在しなかった。**
戦闘中の道具使用（[`economy.md`](economy.md) §6 の `usableIn: "battle"`）も、
野生戦からの逃走も同様。[`battle-system.md`](battle-system.md) §1・§2 で修正。

**章ごとに設計を深めた結果、章をまたぐ動線（捕獲＝バトルの行動）が
どちらの章の主題でもなく、両方から漏れた。**

### 決定の帰結を追い切れていなかった（2件）

- **レベル同期の「上げる」方向**（[`progression.md`](progression.md) §12）を許した結果、

### 未定義の分岐（3件）

## 4回目の見直しで検出した問題（2026-08-16）

3回目の教訓に従い、**章の中身ではなく章をまたぐ動線**を追った。6件検出。
**今回はアーキテクチャの根幹に2件あり、前3回と質が違う。**

### `core` がマスタデータをどう参照するか、どこにも書かれていなかった

`core` は種族値も技の威力も知らなければ計算できない。それなのに
**データをどう受け取るかが12文書のどこにも書かれていなかった。**

放置して素直に実装すると `core` が全データを静的 import することになり、
**v0.1 の完了条件「20種・40技でテストする」が成立しない。**
`GameData` interface による依存性注入として [`battle-system.md`](battle-system.md) §1 で確定。

「依存の向きは `game → core → data`」は書いてあったが、
**それが型の依存なのか実体の依存なのかを詰めていなかった。**

### バトル終了後の処理が一行しかなかった

経験値・努力値・進化・図鑑・賞金・技習得・なつき度は、**それぞれの章に書いてある。**
だが**誰がいつ実行するかは、どの章にも書かれていなかった。**
各章が自分の担当分だけを書き、シーケンス全体を持つ主がいなかった。

[`battle-system.md`](battle-system.md) §10.5 に戦闘後シーケンスとして集約。
実行順に意味があること（努力値付与はレベルアップ後の実数値計算に影響する）、
レンタル個体は対象外にすること（図鑑が埋まると収集の意味が消える）も明記した。

### 残り4件

- **バトル参加者の正規化が未設計。** `PokemonInstance`（実在の個体）・`Party`（設計図）・
  `BattleSet` は形が違うのに、「バトルエンジンは出自を区別しない」とだけ書いてあった
- **進化判定のタイミングが未定義**（条件は定義済みだが、いつ判定するかがなかった）
- **`Settings` 型が存在しない。** 各章が「設定で選べる」と書き続けた結果、
  誰も定義しないまま `save-data.md` が参照だけしていた
- **`moveSelection: "auto"`（パレス式）で誰が技を決めるか未定義**

### 教訓 ― 「全員が自分の担当だけ書く」と、繋ぎ役が消える

4回の傾向がさらにはっきりした。

| 回 | 漏れたもの | 性質 |
| --- | --- | --- |
| 1 | 全滅処理・マップ・経済 | 章そのものがなかった |
| 2 | 色違い・08への統合 | 章の間に落ちた |
| 3 | 捕獲＝バトルの行動 | どちらの章の主題でもなかった |
| 4 | データ参照・戦闘後シーケンス | **各章が自分の担当分だけ書いた結果、全体を持つ主がいなかった** |

`Settings` が象徴的で、**5つの章が「設定で選べる」と書き、誰も型を定義しなかった。**
複数章が言及する要素は、**必ずどこか1章を「持ち主」として決める**必要がある。

## 設計フェーズの完了について

12文書すべてが揃った。ただし**設計が「完璧」になったわけではない**。
各文書末尾の「調整項目」は、**実装して触らないと正解が出ない**もので、
今それを決めても作り直しになる。設計フェーズの成果は、

- データ構造・システムの境界・キャラのコンセプトを確定させたこと
- 決めるべきでないことを「調整項目」として**明示的に先送りしたこと**

の両方にある。

### 未決のまま残っているもの

いずれも実装の開始をブロックしない（v0.1 は `core` のみで UI もアセットも不要）。

- （解決済み）グラフィック素材 → [`../game-plan.md`](../game-plan.md) §10
- ストーリー・主人公は原作準拠かオリジナルか

（「マップ作成に Tiled を使うか」は [`world.md`](world.md) §2 で採用に確定したが、

文書をいくら読み直しても出てこない。

> 前者は見直しで、後者は実装でしか見つからない。**両方いる。**
