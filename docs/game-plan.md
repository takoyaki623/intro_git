# ポケモン風RPG 開発方針

最終更新: 2026-08-16 / ステータス: ドラフト（v0.1 着手前）

---

## 1. この文書の目的

「どんなゲームを作るか」ではなく **「どう作れば途中で破綻しないか」** を決める。
作りたいものが大きいので、スコープの扱い方を最初に固定する。

## 2. 出発点となる3つの希望と、その扱い

| 希望 | 素直に実装した場合の規模（概算） | 本方針での扱い |
| --- | --- | --- |
| 全てのポケモンが出る | 1,025種 + フォルム違い。技は約900。 | **設計制約**。データ件数に依存しないデータ駆動設計にする。最初に入れるのは20種。 |
| 今までの全てのトレーナーが出る | 本編累計で数千人。 | **設計制約**。トレーナーもJSONデータとして外出しし、コードを触らず追加できる形にする。 |
| 原作のマップを再現 | 9地方・数百マップ。1マップ作るのに数時間〜。 | **最後**。マップは最も工数が重く、最も作り直しが発生する。カントー1地方から。 |

### 中心原則

> **「全部入り」はゴールではなく設計制約。**
> エンジン（ルール）とコンテンツ（データ）を分離し、
> コンテンツを1件足すコストが限りなくゼロに近づくように作る。
> そうすれば「全ポケモン対応」は実装課題ではなく、単なる入力作業になる。

この原則を守る限り、途中で開発が止まっても「20種だけ遊べるゲーム」が手元に残る。
守らないと「1,025種ぶんの中途半端なコード」が残って何も遊べない。

## 3. 技術スタック

| 項目 | 選定 | 理由 |
| --- | --- | --- |
| 言語 | TypeScript | 型でデータ構造を守れる。データ件数が増えるほど効く。 |
| 実行環境 | ブラウザ | 環境構築が軽く、GitHub Pages で即公開・共有できる。 |
| 描画 | Phaser 3（2D） | タイルマップ・スプライト・入力が揃っている。導入は v0.2 以降で可。 |
| ビルド | Vite | 設定がほぼ不要。 |
| テスト | Vitest | バトルロジックは全てユニットテストで守る。 |
| データ検証 | zod | JSONデータの形をランタイムで検証し、壊れたデータを早期に検出する。 |

## 4. アーキテクチャ

```
packages/
  core/    ルールエンジン。Phaser にもDOMにも依存しない純粋なTS。
           バトル計算・タイプ相性・レベルアップ・状態異常。
           → ここが全ての中心。テストで100%守る。
  data/    JSON + zodスキーマ。ポケモン種族・技・トレーナー・マップ定義。
           → 増えるのはここだけ、が理想。
  game/    Phaser 層。描画・入力・シーン遷移・セーブ。
  tools/   データ検証、雛形生成、一括変換のスクリプト。
```

**依存の向きは `game → core → data` の一方向のみ。** `core` から `game` を参照しない。
これにより、バトルロジックをブラウザなしでCLIとテストから動かせる（= v0.1 が成立する）。

### 中核データモデル（初版イメージ）

```ts
type Species = {
  id: string;              // "pikachu"
  dexNo: number;           // 25
  name: string;            // "ピカチュウ"
  types: [Type] | [Type, Type];
  baseStats: { hp; atk; def; spa; spd; spe };
  abilities: string[];
  learnset: { level: number; move: string }[];
};

type Move = {
  id: string; name: string; type: Type;
  category: "physical" | "special" | "status";
  power: number | null; accuracy: number | null; pp: number;
  priority: number; target: Target;
  effect?: { kind: string; chance?: number; /* データ駆動の効果ID */ };
};

type Trainer = {
  id: string; name: string; class: string;   // "ジムリーダー"
  party: { species: string; level: number; moves: string[] }[];
  ai: "random" | "basic" | "smart";
  dialogue: { before: string; win: string; lose: string };
};
```

技の効果は `switch` の巨大な塊にせず、**効果IDとハンドラのレジストリ**にする。
新しい技を追加する = JSONを1行足す（既存の効果なら）、で済むようにする。

## 5. マイルストーン

各マイルストーンは「そこで開発が止まっても遊べる／価値が残る」単位で切る。

| 版 | 内容 | 完了条件 |
| --- | --- | --- |
| **v0.1** | バトルエンジン（UIなし・CLI/テストのみ） | 20種・40技でCPU戦が最後まで決着する。テストが緑。 |
| v0.2 | バトル画面（Phaser + HUD・技選択・演出最小限） | ブラウザで1戦を通しで遊べる。 |
| v0.3 | マップ探索・野生エンカウント | 1つの町と1本の道路を歩き、野生戦に入れる。 |
| v0.4 | 手持ち・ボックス・道具・捕獲・セーブ | 捕まえて育てて再開できる。 |
| v0.5 | カントー全域＋ジムリーダー8人 | ジムを順に攻略できる。 |
| **v1.0** | カントー完走（殿堂入りまで） | エンディングに到達できる。 |
| v1.x〜 | 地方・トレーナー・ポケモンの追加 | ここからは「入力作業」。1件追加のコストが低いことを確認する。 |

「全ポケモン・全トレーナー・全マップ」は v1.x 以降で継続的に埋めていく領域。
v1.0 到達時点で、その拡張が**コード変更なしで可能な状態**になっていることが本当の目標。

## 6. v0.1 の詳細スコープ（次にやること）

**含む:**
- ターン制シングルバトル 1体 vs 1体
- 素早さ順の行動決定、技の優先度
- ダメージ計算（第5世代以降の式に準拠：レベル・威力・攻撃/防御・タイプ一致1.5倍・相性・急所・乱数85〜100%）
- 18×18 のタイプ相性表
- 命中判定、PP消費、ひんし判定
- 状態異常5種（どく・まひ・やけど・ねむり・こおり）
- 能力ランク補正（-6〜+6）
- 交代
- **シード固定の疑似乱数**（同じシードなら同じ試合結果 → テストが書ける）
- CPU AI は "random"（弱くてよい。賢さは v0.5 で）

**含まない:** ダブルバトル、特性、持ち物、天候・フィールド、Zワザ/メガ/テラスタル等のギミック、経験値・レベルアップ。
（特性と持ち物は影響範囲が広いので、バトルの骨格が固まってから v0.4 前後で入れる）

**データ量:** 種族20（御三家3系統＋序盤ポケモン中心）、技40。全ポケモンは入れない。

## 7. 権利について

1点だけ注意事項として。原作のドット絵・BGM・マップ画像をそのまま同梱して公開すると権利上の問題になります。
グラフィックとBGMは自作かフリー素材に置き換え、コードとデータのみをリポジトリで管理する方針にしておくと安全です。
非公開・個人利用の範囲であれば実質的な問題は生じにくいですが、公開時に差し替えられるよう、
**アセットは最初から `assets/` に分離し、コードから直接パス依存しない**構造にしておきます。

## 8. リポジトリ運用（git練習を兼ねる）

- `master`: 常に動く状態を保つ。
- 作業ブランチ: `feat/<内容>`、`fix/<内容>` を切って作業し、PRでマージ。
- コミットは「1つの意味の変更」単位で小さく。メッセージは何を変えたかを日本語で書く。
- マイルストーン到達時にタグを打つ（`v0.1` など）。
