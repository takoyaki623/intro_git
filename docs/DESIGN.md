# 設計メモ

`/sc:brainstorm` で決めた方向と、そこから逆算した実装順。

## 決めたこと

| 項目       | 決定                                        |
| ---------- | ------------------------------------------- |
| バトル規模 | 手持ち 3 匹 + 交代                          |
| 遊びの単位 | 連戦（勝ち抜き式）。HP は次の戦闘に引き継ぐ |
| 表示言語   | 日本語                                      |
| 技の奥深さ | ダメージ + 状態異常                         |

## この 4 つが要求するもの

4 つとも独立した機能に見えて、**同じ 2 つの土台**を要求します。

**構造化されたバトルログ。** 現在ログは `readonly string[]` に英文が直書きです。日本語化はこれを崩さないと不可能で、状態異常も交代も新しい文言を増やします。イベントを構造で持ち、文言は表示層で組み立てます。副産物としてダメージ数値の表示や被弾側のハイライトも可能になります。

**チームを持つ `BattleState`。** 現在は片側 1 匹固定です。交代は型から作り直しになります。連戦はさらにその外側に「run」の状態を必要とします。

つまり**機能追加の前に土台を敷いたほうが安い**、という結論になります。

## 実装順

依存関係の順です。各段階でテストが緑のまま進みます。

### ~~Phase 0~~ — 状態更新の純粋化 ✅ 完了

`App.tsx` が `setBattle` の更新関数の中で乱数を引いています。StrictMode で 1 ターンあたり 7 → 14 回に倍増することを実測済み。修正後は 7 回で一致することを同じ方法で確認。連戦にすると 1 プレイが長くなり、シード付き乱数でランを再現したくなるので、ここで潰します。数行。

### ~~Phase 1~~ — 構造化ログと日本語化 ✅ 完了

```ts
export type BattleEvent =
  | { kind: 'encounter'; pokemon: string }
  | { kind: 'useMove'; side: Side; pokemon: string; move: string }
  | { kind: 'miss'; side: Side; pokemon: string }
  | { kind: 'damage'; side: Side; pokemon: string; amount: number }
  | { kind: 'critical' }
  | { kind: 'effectiveness'; multiplier: number }
  | { kind: 'faint'; side: Side; pokemon: string }
```

`BattleState.log: string[]` を `events: BattleEvent[]` に置き換え、`src/ui/messages.ts` が日本語へ変換します。
`formatEvent` は `damage` に対して `null` を返します（本家もダメージ数値は表示しない）。
イベント自体は数値を持っているので、HP バーのアニメーションやダメージ表示を後から足せます。

```
「ピカチュウの 10まんボルト！」
「こうかは ばつぐんだ！」
「ゼニガメは たおれた！」
```

データ側の名前も日本語にします（ピカチュウ / 10まんボルト / でんき）。表示言語は日本語のみと決めたので `{ ja, en }` のような構造は持たせません。後から英語を足したくなっても、この構造化を済ませてあれば安く済みます。

### ~~Phase 2~~ — 手持ち 3 匹と交代 ✅ 完了

```ts
export interface TeamState {
  readonly members: readonly BattlePokemon[]
  readonly activeIndex: number
}

export type TurnAction = { type: 'move'; move: Move } | { type: 'switch'; index: number }
```

ルール：

- 交代は 1 ターンを消費する
- 交代は技より先に解決される（本家の優先度）
- ひんし時は強制交代。ターンは消費しない
- 勝敗は「3 匹すべてひんし」で判定

`BattleEvent` には `switch` ひとつではなく `withdraw` と `sendOut` の 2 つを追加しました。
本家が「ピカチュウ もどれ！」と「ゆけっ！ ヒトカゲ！」を別の行で出すのと、
ひんし後の交代では戻す行が出ないのを、そのまま表現できるためです。

相手側の強制交代は `resolveTurn` の中で自動的に解決し、
プレイヤー側だけ `awaitingSwitch` として呼び出し側に返します。
AI は自分で決められるが、プレイヤーには訊く必要がある、という非対称です。

種族を 3 つ足しました（イーブイ・ズバット・イシツブテ）。
`data/teams.ts` の 2 パーティは型相性が噛み合うように選んであり、
たとえばイシツブテ（いわ・じめん）にはピカチュウのでんきが無効なので、
交代が「作業」ではなく「判断」になります。

### ~~Phase 3~~ — 状態異常 ✅ 完了

`どく` `やけど` `まひ` `ねむり` `こおり`。

ターン構造が 2 段になります。**行動フェーズ**のあとに**ターン終了フェーズ**（どく・やけどのスリップダメージ）。

| 状態   | 効果                                |
| ------ | ----------------------------------- |
| どく   | ターン終了時に最大 HP の 1/8        |
| やけど | ターン終了時に 1/16、物理攻撃が半減 |
| まひ   | 素早さ半減、25% の確率で行動不能    |
| ねむり | 1〜3 ターン行動不能                 |
| こおり | 20% で自然解凍するまで行動不能      |

`BattlePokemon` に `status` を追加。イベントも 4 つ増えました
（`statusInflicted` / `statusDamage` / `immobilised` / `statusEnded`）。

実装上の判断：

- `Status` は union にしました。ねむりだけがターン数を持つので、
  やけどのポケモンに無意味なカウンタが生えないようにするためです
- タイプ免疫を入れました（どく→どく・はがね、やけど→ほのお、
  まひ→でんき、こおり→こおり）。でんじはがピカチュウに効きません
- 技に `category: 'status'` を追加。でんじは・ねむりごなは威力を持ちません
- 起床・解凍したターンは行動できます（本家と同じ）

### ~~Phase 4~~ — 連戦と保存 ✅ 完了

```ts
export interface RunState {
  readonly team: readonly BattlePokemon[] // HP は引き継ぐ
  readonly wins: number
  readonly battle: BattleState | null
  readonly over: boolean
}
```

- 勝つたびに相手が強くなる（レベルを上げる）
- 手持ちの HP と状態異常は次の戦闘に引き継ぐ
- 3 匹すべてひんしでラン終了
- `localStorage` に保存。サーバは不要

## バランス設定

未決定としていた 3 点は仮の想定どおり実装し、`src/domain/run.ts` の
`RUN_CONFIG` に集約しました。1 行で調整できます。

```ts
export const RUN_CONFIG = {
  startingLevel: 50,
  levelStepPerWin: 2,
  healingBetweenBattles: 0.25,
  partySize: 3,
}
```

加えて **ひんししたポケモンはランの間ずっと復帰しません**。
これがラン全体をカウントダウンにし、勝ち抜きの緊張感を作っています。
回復は生き残っているポケモンにだけ効き、状態異常も同時に治ります。

相手 AI は `src/domain/ai.ts` にあり、技のスコアリングと交代の判断をします。
`AI_CONFIG.skill` を下げると、たまにランダムな技を選ぶようになります。

### バランスの根拠

腕前の違うボットで通しプレイして測りました。
以下は**現在の数字**（ドラフトあり・6 戦クリア、各 800 ラン、考える AI 相手）。

| プレイヤー    | 平均連勝 | クリア率 |
| ------------- | -------- | -------- |
| ランダムな技  | 1.48     | 3.4%     |
| 第 1 手を連打 | 2.60     | 6.8%     |
| 最善手を選ぶ  | 3.62     | 20.6%    |
| 最善手 + 交代 | 3.71     | 22.3%    |

`npm run sim` で再測定できます（`src/ai.sim.test.ts`。通常のテスト実行では skip）。

**ベースラインは「ランダムな技」です。「第 1 手を連打」は基準になりません。**
技リストは強い技から書いてあることが多く、第 1 手連打はそれなりに機能する
戦略になってしまいます（1.48 に対して 2.60）。ここを取り違えて、
一時期「腕前の差は 1.7 倍しかない」と書いていました。誤りです。

どのボットも、勝ったときに出る**無料の技は取ります**（`placeMove`）。
タダのものを取らない前提で測ると、誰も遊んでいないゲームを測ることになります。

**初期は相手も Lv50 でした。** そのときの数値は「最善手 + 交代」で 0.81 連勝、
つまり初戦で半分落ちる状態でした。原因は五分の勝負を繰り返す設計で、
毎戦の勝率が 50% なら期待連勝数は 1 になります。

回復量を 0.25 → 0.55 に上げても 0.81 → 0.90 しか動きませんでした。
**回復は戦闘の「間」にしか効かないので、初戦の敗北を防げない**ためです。
相手の初期レベルを 42 に下げたところ 0.81 → 2.40 になりました。

**毎ターンの技選びで平均 2.4 倍・クリア率で 6.1 倍の差**（1.48 対 3.62）、
交代まで含めると**クリア率で 6.6 倍**（3.4% 対 22.3%）がつきます。
判断は結果にはっきり反映されています。

この差は種族を 31 匹に増やしたときに**広がりました**（3.1 倍 → 6.6 倍）。
手持ちの技構成が毎回変わるので、「とりあえず 1 番目」が通用しなくなります。

## 第 2 期：ランを「カウントダウン」から「ラン」へ

`/sc:brainstorm` で決めた方向。診断は単純で、**プレイヤー側に上向きの動きが一切なかった**ことです。

| ランの中で | プレイヤー                 | 相手          |
| ---------- | -------------------------- | ------------- |
| レベル     | Lv50 のまま変わらない      | 1 勝ごとに +2 |
| 手持ち     | ひんししたら二度と戻らない | 毎戦フル      |
| 勝った報酬 | なし                       | —             |

弱っていく側と強くなっていく側がいるだけで、これは消耗戦です。
さらに最高連勝数がどこにも保存されず、破るべき数字も存在しませんでした。

決めたこと：

| 項目           | 決定                           |
| -------------- | ------------------------------ |
| 連戦の形       | 勝つたびに報酬を 1 つ選ぶ      |
| 記録           | 最高連勝数と、そのときの手持ち |
| 手持ち         | ランダムに配られる             |
| バトルの奥行き | 能力変化を追加                 |

### ~~Phase 5~~ — ランダム配布と記録 ✅ 完了

ランの入口と出口。どちらも小さく、合わせるとランが「毎回違うもの」になります。

- `makePlayerTeam` を `makeOpponent` と同じく `SPECIES_LIST` からの抽選に変える
- 決着時に最高記録を更新。`localStorage` に連勝数・手持ち・日付を残す
- 連勝表示の横に自己ベスト、ラン終了画面に殿堂入りパーティを出す

弱いパーティを引くこともありますが、それがローグライクです。
報酬（Phase 6）で立て直せるので、Phase 5 単体より噛み合います。

実装で決めたこと：

- **0 連勝は記録しません。** 「さいこう 0」は情報がなく、バグに見えます
- 同数のときは古い記録を残します（先に達成したほうが記録）
- 記録には種族名も保存します。種族名を変えても過去の記録が読めるようにするためで、
  欠けていれば現在のデータから補います
- `data/teams.ts` は誰も参照しなくなったので削除しました

### ~~Phase 6~~ — 勝利報酬 ✅ 完了

勝つと 3 択が出て、1 つ選んでから次の相手へ。

| 報酬            | 効果                              | 出る条件         |
| --------------- | --------------------------------- | ---------------- |
| ぜんかいふく    | 立っている全員を全回復            | つねに           |
| そせい          | ひんし 1 匹を最大 HP の半分で復帰 | ひんしがいる     |
| レベルアップ    | 手持ち全員のレベルを上げる        | つねに           |
| なかまを ふやす | ランダムな 1 匹を手持ちに加える   | 手持ちが上限未満 |

報酬の**文言は `src/ui/messages.ts`** に置きます。ルール層は種類だけを持ち、
言葉は UI が組み立てる、という既存の分担をそのまま延長します。

抽選結果は状態に持たせます（再レンダリングのたびに引き直さないため）。
`RunState` に `offer` を追加し、`withBattle` が勝利を検知したときに一度だけ埋め、
`advance` が消費します。選択中にリロードしても失われないよう保存対象にも入れます。

技の入れ替えは「どのポケモンの」「どの技を」の 2 段選択が要るので、この段では入れません。

実装で決めたこと：

- **何もしない報酬は出しません。** 全員満タンなら「ぜんかいふく」、
  ひんしがいなければ「そせい」は候補から外れます
- 戦闘間の回復（35%）は報酬と別に必ず入ります。回復がランを進める土台で、
  報酬はその上の「選択」という位置づけです
- レベルアップは HP の数値ではなく**受けたダメージ量を保つ**ので、
  最大値の増加分がそのまま回復として効きます
- なかまは手持ちにいない種族から選び、レベルは手持ちに合わせます

途中で実バグを 1 件見つけました。**勝った直後にリロードすると報酬が出ずに素通り**していました。
`withBattle` が抽選する設計だったため、抽選前に保存されたランを復元すると穴が空きます。
`withOffer` を切り出し、復元時にも通すようにしました。

### ~~Phase 7~~ — 能力変化 ✅ 完了

`BattlePokemon` に段階（-6〜+6）を持たせます。倍率は本家と同じく
上昇が `(2 + 段階) / 2`、下降が `2 / (2 - 段階)`。

- つるぎのまい（自分の こうげき +2）、にらみつける（相手の ぼうぎょ -1）など
- **交代で元に戻る** — これがあるから積み技と交代が駆け引きになります
- ダメージ計算とイベント・文言に反映

実装で決めたこと：

- 段階の適用は `battleStat()` に集約し、ダメージ計算と行動順の両方が同じ関数を通ります
- 限界に達したときは `applied: 0` を返し、ログが「もう あがらない！」と言います。
  黙って何も起きないより、そう言うほうが親切です
- AI も変化技を評価するようにしました（`AI_CONFIG.stageValue`）。
  評価しないと相手は つるぎのまい を一生使いません

実際に遊ばせてみると、積んだヒトカゲに対して AI がゼニガメへ交代し、
2 倍のなみのりで返してくる展開が出ました。狙った駆け引きが成立しています。

## 第 3 期：見せてから、増やす

`/sc:brainstorm` の診断は、機能が足りないことではなく
**判断に必要な情報を画面が隠していること**でした。

| 隠れているもの   | 影響                                                          |
| ---------------- | ------------------------------------------------------------- |
| ポケモンのタイプ | タイプ相性で成り立つゲームなのに、相手のタイプが分からない    |
| 技の効果         | でんじは は「でんき・へんか」としか出ず、まひ技だと分からない |
| 技の命中率       | アイアンテール（75%）とでんこうせっか（100%）が同じに見える   |

`Move` 型は `effect` も `stageChange` も `accuracy` も持っているのに UI が捨てています。
状態異常と能力変化を足したことで、隠れている情報はむしろ増えました。

決めたこと：

| 項目     | 決定                                       |
| -------- | ------------------------------------------ |
| 情報提示 | タイプをカードに、命中率と効果を技ボタンに |
| 規模     | 種族を 15〜20 匹に増やす                   |
| その先   | 持ち物・特性                               |

**この順でやります。** 種族を増やしても特性を足しても隠れる情報が増えるだけなので、
先に見せ方を直さないと逆効果になります。

### ~~Phase 8~~ — 情報を見せる ✅ 完了

- カードにタイプを表示（複合タイプは 2 つとも）
- 技ボタンに命中率（100% 未満のときだけ。例外を目立たせるため）と
  効果（`まひ 10%`、`こうげき +2`、`あいての ぼうぎょ -1`）
- 相性そのものは表示しません。そこはプレイヤーが考える部分として残します

文言は `src/ui/messages.ts`、色は CSS。既存の分担どおりです。

実装で決めたこと：

- **タイプの色は文字ではなくドットに載せます。** 18 タイプ分の色を
  ライト・ダーク両方で読める明度に調整するのは無理があるので、
  文字は通常色のまま、色は識別のためのドットだけが担います
- 命中率は 100% 未満のときだけ出します。例外を目立たせるためです
- **交代パネルにもタイプを出しました。** 交代先を選ぶのはタイプの判断そのものなので、
  ここが手探りだと片手落ちになります

### ~~Phase 9~~ — 種族を 15〜20 匹に ✅ 完了

いまは 7 匹から 3 匹を引くので毎回ほぼ同じ顔ぶれです。
PokéAPI は使いません。ローカルに持つほうがテストが決定的でオフラインでも動きます。

タイプの偏りが出ないよう、18 タイプを広くカバーする選び方にします。

実装で決めたこと：

- 7 → 18 匹、技は 29。**全 18 タイプが揃っていることをテストで保証**します
  （目視で数えると必ず抜けるので）
- 不変条件テストが**デッドデータを 3 件見つけました**。
  ロスターを入れ替えた過程で、どの種族も覚えない技が残っていたのです。
  アイアンテールはコイル（でんき・はがね）に持たせ、
  ひのこ・みずでっぽうは既存技の下位互換なので削除しました

### 拡張後のバランス

`npm run sim` で測り直しました（1 ランあたりの平均連勝数）。

| プレイヤー    | 拡張前 | 拡張後 |
| ------------- | ------ | ------ |
| 第 1 手を連打 | 0.85   | 1.98   |
| 最善手を選ぶ  | 2.16   | 3.83   |
| 最善手 + 交代 | 2.53   | 3.41   |

全体に易しくなりました。両陣営がランダムに引くので分散が大きくなり、
強い種族（ストライクは こうげき 110・すばやさ 105）を引いたランが伸びるためです。

**ボット相手の測定なので、これ以上は調整しません。** 2〜4 連勝の帯に収まっており、
実際に遊んだ感触なしに詰めても当たりません。

なお「最善手 + 交代」が「最善手」を下回っています。
交代の判断しきい値（1.6 倍）がロスター拡張後は積極的すぎる可能性がありますが、
これはボット側の問題であってゲーム側の問題とは限りません。

### ~~Phase 10~~ — 持ち物・特性 ✅ 完了

一番大きい追加。Phase 8 で見せ方が整っているのが前提です。

- 持ち物：戦闘中の効果（きのみで回復、こだわり系など）
- 特性：常時効果（いかく、ちょすい など）
- どちらも報酬（Phase 6）と噛み合わせる余地があります

実装したもの：

| 特性       | 効果                          | 持ち主               |
| ---------- | ----------------------------- | -------------------- |
| ふゆう     | じめん技が効かない            | ゴース               |
| ちょすい   | みず技を受けると回復          | ジュゴン・メノクラゲ |
| がんじょう | 満タンからの一撃を 1 で耐える | イシツブテ・コイル   |
| いかく     | 場に出ると相手のこうげき -1   | ストライク・デルビル |

| 持ち物         | 効果                                  |
| -------------- | ------------------------------------- |
| たべのこし     | ターン終了時に最大 HP の 1/16 回復    |
| きあいのタスキ | 満タンからの一撃を 1 で耐える（消費） |
| たつじんのおび | こうかばつぐんの技が 1.2 倍           |
| オボンのみ     | HP が半分を割ると 1/4 回復（消費）    |

実装で決めたこと：

- **特性は任意（`ability?`）にしました。** 18 匹全部に付けると「持っていて当たり前」になり、
  特性が個性でなくなります。7 匹だけが持ちます
- 持ち物は**報酬から入手**します。Phase 6 の仕組みにそのまま乗りました
- 「耐える」フックは特性と持ち物で共通です。
  どちらも満タンからのみ発動し、持ち物のほうは消費されます
- **フックの追加箇所は 5 つ**（場に出たとき・相性の上書き・ダメージ倍率・
  ダメージ適用後・ターン終了時）。ここに収めることで battle.ts の各所に
  条件分岐を撒かずに済んでいます

途中で `endOfTurn` をパッチで壊しました（reduce の引数を再代入して、
たべのこしの回復が捨てられる状態）。関数ごと書き直しています。

カードに特性・持ち物の行が増えて **375×667 で技ボタンが 79% しか見えなくなり、
Phase 8 で入れた回帰テストが止めました。** 狙いどおりの働きです。

段階バッジと特性・持ち物を 1 行にまとめ、`.battle` の gap を 1.25rem → 0.85rem、

## 遊んでもらって直したこと

**「ログが少し見にくい。スクロールして下を見ないといけない」**

測ったところ、iPhone SE（375×667）で**ログは 22px しか見えていませんでした。**

1. ログが技ボタンと交代パネルの後ろ、ページ最下部に置かれていた
2. `max-width: 24rem`（384px）のブレークポイントで 1 列になり、

2 番目が効いていて、この 2 区画だけで 607px を占めていました。

| 区画             | 前     | 後       |
| ---------------- | ------ | -------- |
| 技ボタン         | 327px  | 162px    |
| 交代パネル       | 280px  | 100px    |
| ページ全体       | 1085px | 815px    |
| ログの可視率     | 3%     | **100%** |

E2E に「375×667 でログと技ボタンが 100% 見える」という回帰テストを入れてあります。

## 第 4 期：引きを「決めるもの」から「材料」へ

### 何が問題だったか

タイプも技も持ち物も入れたあと、**まだ引きが結果を決めていました。**

1500 ランを、パーティの種族値合計で 4 分割して測った結果（相手初期 Lv42）：

| パーティの強さ | 平均連勝数 |
| -------------- | ---------- |
| 下位 1/4       | 1.13       |

| 中上位 1/4     | 2.11       |

> **後から訂正。** ここで比較対象にしていた「腕前の差 1.7 倍」は、

> 第 1 手連打は基準になりません。ランダムな技を基準に取り直すと腕前の差は
> 平均 2.6 倍・クリア率 8 倍で、引きの差と同じかそれ以上です。

> ドラフトを入れた判断自体は、下限が上がった（0 勝ラン 18% → 8%）ので有効です。

### ~~Phase 11~~ — ドラフト ✅ 完了

`src/domain/draft.ts` / `src/components/DraftScreen.tsx`

**6 匹提示して 3 匹選ぶ**画面をランの最初に置きました。

- 種族値合計・タイプ・特性・攻撃できるタイプ（`coverageSummary`）をカードに出す
  — 選べても情報がなければ選択にならないため
- もう一度押すと選択が戻る。4 匹目は**古い選択を捨てずに拒否**する
  （押し間違いで選択が消えるほうが困る）
- 選んだ順がそのまま手持ちの順になり、1 番目が先発
- **候補は引いた瞬間に保存する。** そうしないとリロードで引き直せてしまい、
  気に入る 6 匹が出るまでリロードするのが最適手になります。
  ドラフトが抑えようとしている引きの偏りが、そのまま戻ってきます

`RunState` には手を入れていません。ドラフトは App の 1 フェーズで、
`startRun(random, roster?)` に選んだ 3 匹を渡すだけです。
保存形式（`pokemon-battle:run`）も戦闘のコードも無傷のままです。

### 効果（1500 ラン、最善手 + 交代、相手初期 Lv44）

| 配り方        | 平均 | 0 勝の割合 | 下位 1/4 | 中下位 | 中上位 | 上位 1/4 | 上下差 |
| ------------- | ---- | ---------- | -------- | ------ | ------ | -------- | ------ |

正直に言うと、狙いの半分です。「強いパーティならランが伸びる」構造は残りました。
ただし残り方が変わりました。ボットは**種族値合計の大きい 3 匹**を取る戦略なので、
上位に居続けるのはその戦略を選んだ結果です。**配られて上位にいるのと、

## 第 5 期：ランに終わりを作る

### 何が問題だったか

ドラフトを入れても、ランが答える問いは**「いつ死ぬか」だけ**でした。
勝ち続けても相手のレベルが上がり続けるので、どこかで必ず負けます。
そうすると報酬の選択はすべて「あと 1 戦もたせるには」になり、
**「クリアまでに何を仕上げるか」という考え方が生まれません。**

### ~~Phase 11~~ — 6 戦でクリア、最後はボス ✅ 完了

`RUN_CONFIG.battlesToClear` / `BOSS_SPECIES` / `isFinalBattle`

- **6 戦勝ち抜けばクリア。** ランに終点ができました
- **6 戦目は 1 匹だけ**。3 匹だと「少し長い 6 戦目」にしかならないので、
  こちらの 3 匹に対して 1 匹という形にしました。**数で押せるのが勝ち筋**です
- ボスは**カイリュー**（種族値合計 600）。ドラフトにも道中にも仲間にも出ません。
  持っているかもしれない相手はボスではないので
- 最後の 1 戦だけ**開始メッセージが変わります**
  （「さいごの あいて カイリューが たちふさがった！」）。
  ルールは何も変えていません。変わるのは立っている相手だけです

**ドラフト画面の「こうげき ○○」がここで効きます。** カイリューは
ドラゴン / ひこうなので**こおりが 4 倍**、いわ・フェアリー・でんき・ドラゴンが 2 倍。
れいとうビームを持つのは 18 匹中 2 匹なので、**6 匹の候補に氷の答えが混ざる確率は約 57%**。
「引きで決まる」ではなく「引いた中から選ぶ」が、最後の 1 戦に直結します。

### なぜ 6 戦か（測って決めました）

1500 ラン、ドラフトあり、最善手 + 交代のボットで測った到達率：

| クリア条件 | ボスまで到達 | クリア    |
| ---------- | ------------ | --------- |
| 8 戦       | 21%          | 13.3%     |
| 7 戦       | 26%          | 16.2%     |
| **6 戦**   | **33%**      | **20.5%** |

8 戦だと**5 ランに 1 ランしかボスを見られません。** ボスは中身なので、
見られないほうが問題です。6 戦なら 3 ランに 1 回は最後まで行き、
5 ランに 1 回クリアできます。**到達したうちの約 6 割がボスを倒す**ので、
壁としても機能しています。

`BestRun` に `cleared` を足して、殿堂入りに「クリア」バッジが出るようにしました。
古い記録は `cleared` がないので false として読みます（消しません）。

## 第 6 期：技を増やし、交代を機能させ、クリアの先を作る

### ~~Phase 12~~ — 技を 29 → 49 に、とんぼがえりと反動を追加 ✅ 完了

**交代がほとんど効いていませんでした。** しきい値を 1.2〜5.0 倍で振っても
平均連勝は 3.32〜3.67 で、すべて誤差の範囲。交代は 1 ターン丸ごと差し出して
相手に 1 発ただでもらう行動なので、タイプ有利を取っても釣り合ってしまいます。

新しい仕組みを 2 つ入れました。

**`switchesOut`（とんぼがえり・ボルトチェンジ）**
攻撃してから交代する。1 ターン損がなくなるので、これだけで交代が使える行動に
なります。**誰を出すかは技を押した時点で選びます**（`TurnAction.switchTo`）。
ターンの途中で止めて訊くのではなく、行動そのものに選択を含める形にしたので、
`resolveTurn` は 1 回の呼び出しのままです。「やめる」で戻れます。

**`recoil`（すてみタックル・フレアドライブ・ワイルドボルト・ブレイブバード）**
与えたダメージの一部が自分に返ります。本家より重い仕組みです。**ひんしはランの間
ずっと戻らない**ので、反動は二度と返ってこない資源を払っています。

ほかに、命中率で威力を買う技（だいもんじ 110/85%、ふぶき 110/70%、
かみなり 110/70%、メガホーン 120/85%、ストーンエッジ 100/80%）と、
埋まっていなかったタイプの技を足しました。

### 強い技を両方に配ると、ランでは対称にならない

技を足しただけで**クリア率が 20% → 8% に落ちました。**

理由は構造です。**相手のパーティは毎戦入れ替わり、こちらは傷を持ち越します。**
技が強くなると戦闘は短く、振れ幅が大きくなる。振れ幅の大きい戦いを繰り返せば、
**持ち越す側だけが損をします。**「両方に同じものを配ったから公平」ではありません。

相手の初期レベルを 44 → 40 に下げて戻しました（実測で 22%）。

### 交代は機能するようになった

800 ラン、ドラフトあり、相手初期 Lv40、考える AI 相手：

| プレイヤー    | 平均連勝 | クリア率 |
| ------------- | -------- | -------- |
| 最善手を選ぶ  | 3.24     | 14.6%    |
| 最善手 + 交代 | 3.57     | 20.1%    |

**交代の有無でクリア率が 14.6% → 20.1%。** とんぼがえり以前は
15.0% → 17.9% だったので、交代の価値はおよそ倍になりました。

### ~~Phase 13~~ — だんかい（周回） ✅ 完了

`src/domain/tiers.ts` / `src/ui/progress.ts` / `src/components/TierPicker.tsx`

クリアしたあとに何もすることがない、という問題への答えです。

- **だんかい 1〜5。** クリアすると次が開きます
- 上げるのは**レベルだけ**（1 段 +3）。すでに難易度を測ってある唯一のつまみで、
  道中もボスも同時に上がり、プレイヤーが新しいルールを覚える必要がありません
- 開いていないだんかいも**鍵つきで表示します**。5 つあると見えることが、
  1 つ目をクリアする理由になります
- 進捗は `pokemon-battle:progress` に**ランとは別に**保存します。ランは終わるたびに
  捨てられるので、そこに乗せるわけにはいきません
- 一度開いただんかいは**下がりません**。だんかい 4 まで行ってから 1 をやり直しても、
  4 までは開いたままです。クリア画面が「あいた！」と言うのは、
  そのランが実際に記録を押し上げたときだけです

### だんかいごとの難易度

300 ラン、最善手 + 交代のボット：

| だんかい | 相手の初期 Lv | 平均連勝 | ボス到達 | クリア |
| -------- | ------------- | -------- | -------- | ------ |
| 1        | 40            | 3.65     | 41%      | 26.0%  |
| 2        | 42            | 3.02     | 28%      | 14.3%  |
| 3        | 44            | 2.42     | 18%      | 7.7%   |
| 4        | 46            | 2.05     | 11%      | 4.3%   |
| 5        | 48            | 1.76     | 8%       | 3.7%   |

**最初は 1 段 +3 で作りましたが、だんかい 5 のクリア率が 0.2% でした。**
それは「難しい」ではなく「無理」です。+2 に下げて、1 段ごとにおよそ半分ずつ
下がる形になりました。だんかい 5 の 3.7% は、このボットの数字です
（報酬を決め打ちで取り、先を読みません）。人が遊べばもう少し上がります。

### `npm run sim` が失敗していた

測定ブロックは 5 秒のデフォルトタイムアウトを超えていて、**正しい数字を出した
あとで「失敗」と報告していました。** 数百ランを回すものなので当然です。
それぞれに 600 秒のタイムアウトを渡しました。

## 第 7 期：報酬に「育てる」を入れる

### 報酬の選択がほぼ飾りだった

500 ラン、「その報酬が出たら必ず取る」戦略ごとのクリア率：

| 報酬のとりかた     | クリア率  |
| ------------------ | --------- |
| そせい優先         | 25.2%     |
| なかまを ふやす    | 23.2%     |
| レベルアップ       | 21.4%     |
| **ランダムに選ぶ** | **19.8%** |
| もちもの           | 15.6%     |
| ぜんかいふく       | 13.4%     |

**ランダムに選んでも 19.8%、最善でも 25.2%。1.27 倍しかありません。**
毎ターンの技選びが 3.1 倍つくのと比べると、報酬画面はほぼ飾りでした。

理由は **5 つの報酬が全部おなじ軸**だったことです。回復・そせい・レベル・
なかま・もちもの——どれも「生き残りやすさ」を少し足すだけで、遊び方は
変わりません。ランごとに別のものになる、というローグライクの核がない。

### ~~Phase 14~~ — わざを おぼえる ✅ 完了

**技をポケモンごとに持たせました**（`BattlePokemon.moves`）。種族から読んで
いると、入れ替えたときに**同じ種族の相手の技まで書き換わります**。

そのうえで「わざを おぼえる」を足しました。押すと**だれに → どの技と
いれかえるか**の 2 段選択。とんぼがえりで作った UI がそのまま使えました。

### 一度失敗している：報酬の 1 つにしたら罠になった

最初は 3 択の 1 つとして入れました。測った結果：

| 方針               | クリア率  |
| ------------------ | --------- |
| そせい優先         | 36.0%     |
| **技を覚えない**   | **30.8%** |
| **技を覚える優先** | **20.4%** |

**技を取ると体を 1 つ捨てることになります。** ランが終わるのは
「3 匹全員ひんし」のときだけなので、体を増やさない報酬は構造的に負けます。
HP を全回復して 1 匹増やす報酬に、技 1 つが勝てるはずがありません。

回復を足して底上げしてみましたが 20.4% → 21.0% でほぼ動かず。
**数字を盛って勝たせるのは設計ではない**ので、やめました。

### 直した形：報酬とは別枠にする

`RunState.moveOffer` を足して、**技は 3 択の外**に出しました。
勝つと「わざを おぼえますか？（ごほうびとは べつ）」が別枠で出て、
取っても取らなくても報酬は 3 択のまま選べます。

生き残りの選択と、ビルドの選択を**別の層に分けた**ということです。

| 方針                | 平均連勝 | クリア率 |
| ------------------- | -------- | -------- |
| 体優先 + 技を覚える | 4.28     | 38.2%    |
| 体優先 + 覚えない   | 4.04     | 31.0%    |
| レベル優先 + 技     | 3.60     | 27.4%    |
| ぜんかいふく優先    | 3.40     | 18.2%    |

技は罠ではなく**純粋な上振れ**（31.0% → 38.2%）になり、報酬そのものの選択には
**2.1 倍の差**（体 38.2% 対 回復 18.2%）が残りました。どちらも狙いどおりです。

**ぜんかいふくは今も一番弱い報酬です。** 戦闘間に 35% の回復が必ず入るので、
ぜんかいふくが足しているのは残りの分だけ。体は増えません。これは罠というより
「安全な選択がいちばん弱い」というローグライクらしい学習で、消していません。

### もちもの も だれに もたせるか えらべます

前は「手ぶらの先頭 1 匹」に自動で渡っていました。いまは
「たべのこしを もらう → だれに？」です。もらう物も画面に出ます
（前は「もちものを もらう」としか出ず、何が来るか分からない選択でした）。

### ~~Phase 15~~ — 種族を 31 匹に ✅ 完了

18 匹では**11 のタイプに種族が 1 匹ずつしかいませんでした。** ドラフトの
6 匹に、チャートのまるまる 1 列への答えが 1 つも入らないことがあり得ます。

穴を埋める選び方で 13 匹足しました：ロコン・モンジャラ・タマタマ・ケーシィ・
イワーク・ニューラ・ココドラ・ヨマワル・キバゴ・エビワラー・クヌギダマ・
ドードー・プリン。**種族値は本家のまま**で、弱いものも入れています——
6 匹の候補は、選ぶ価値のないものが混じっていて初めて選択になります。

不変条件をテストに足しました：**どのタイプにも 2 匹以上いること**、
**どのタイプにも攻撃技を持つ種族がいること**、**ロスターが候補数の数倍あること**。

### 増やしたら、判断の重みが増えた

| プレイヤー    | 18 匹のとき | 31 匹のいま |
| ------------- | ----------- | ----------- |
| ランダムな技  | 6.5%        | 3.4%        |
| 最善手 + 交代 | 20.1%       | 22.3%       |
| **腕前の差**  | **3.1 倍**  | **6.6 倍**  |

**中身を増やすと、判断が効く幅も広がりました。** 手持ちの技構成が毎回
変わるので、「とりあえず 1 番目を押す」が通用しなくなります。
難易度そのものは 20.1% → 22.3% でほぼ動いていないので、再調整はしていません。

## のこっている改善候補

- 技の入れ替え報酬（2 段選択の UI が要る）
- 急所は相手の能力上昇・自分の能力低下を無視する（本家の仕様。今回は入れていません）
