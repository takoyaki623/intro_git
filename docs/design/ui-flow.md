# 10. 画面構成・UI

関連: 全章（特に [`battle-system.md`](battle-system.md) / [`capture.md`](capture.md) / [`endgame.md`](endgame.md)）

---

## 1. 設計方針

UIは「見た目」ではなく**構造の問題**として設計する。本作固有の要求は3つ。

| 要求 | 出どころ |
| --- | --- |
| **数千個体を扱えるリストUI** | 共通ボックス（[`capture.md`](capture.md) §5） |
| **周回に耐える操作の軽さ** | エンドゲーム主軸（[`endgame.md`](endgame.md)） |
| **情報の出し分け** | 本編は育成を隠す（[`progression.md`](progression.md) §1） |

## 2. 描画層の分担 ―【決定】Canvas と DOM を使い分ける

**決定: 世界の描画は Phaser（Canvas）、UIは DOM（HTML/CSS）。**

> **Phaser の導入は v0.7（マップ探索）まで遅らせる**（v0.3 実装時に判断）。
> v0.3 のバトル画面には絵が1枚も無く（[`../game-plan.md`](../game-plan.md) §10）、
> 下表で Phaser が担当する仕事が存在しない。**「世界」が無い段階で
> ゲームエンジンを入れる理由はない。** DOM だけで完結させ、
> マップが必要になった時点で導入する。

| 層 | 担当 |
| --- | --- |
| **Canvas** | マップ探索、キャラの移動、バトルの演出、エフェクト |
| **DOM / HTML** | メニュー、ボックス、図鑑、編成、ショップ、設定、バトルのHUDと技選択 |

### 2.1 Phaser ―【決定・v0.7】導入しない

v0.3 で「マップが必要になった時点で導入する」と先送りにしていた判断を、
その時点（v0.7）で確定する。**採用しない。素の Canvas 2D で描く。**

| Phaser が持っているもの | v0.7 の実情 |
| --- | --- |
| タイルマップの描画 | **タイル画像が1枚も無い**（[`../game-plan.md`](../game-plan.md) §10）。塗るのは矩形だけ |
| スプライトとアニメーション | 同上。プレイヤーも NPC も矩形 |
| 物理・衝突判定 | 使わない。衝突は `collision[]` の配列参照で、格子の外に出ない |
| シーン遷移・入力 | モード切り替えは v0.5 から DOM 側にあり、二重になる |
| アセットローダ | 読むものが無い |

実装してみた結果、**マップ描画は 60 行ほどで足りた**（カメラ追従・矩形塗り・歩行補間）。
一方 Phaser は約 1MB。得るものが無いまま、バンドルとフレームワークの制約だけが増える。

**再検討の条件をここに書いておく**（先送りではなく、条件付きの決定にする）:

- 公式素材を入れてタイルマップとスプライトを実際に描くようになったとき
- 1画面の描画対象が数百に増え、素朴な全面再描画で処理が追いつかなくなったとき

どちらも起きていない。起きたときに `packages/game` の描画部分だけを差し替える。
**`packages/core` は描画を一切知らないので、この差し替えは UI 層の中で閉じる。**

### 理由

- **リスト・検索・スクロールは DOM が圧倒的に安い。** 数千件の仮想スクロールを
  Canvas で自前実装するのは、得るものがない労力になる
- アクセシビリティ・テキスト選択・入力欄が無料で手に入る
- レスポンシブ対応も CSS に任せられる

Canvas でUIまで描く選択は「見た目の統一感」と引き換えに実装量が数倍になる。
本作はコンテンツ量が主戦場なので、**UI実装にコストを割かない方向に倒す。**

### 2.2 マップ画面の作り（v0.7）

バトル画面と同じ構造をそのまま使う ―― **`core` は中断点を返すだけで、待つのは UI の仕事。**

```
stepPlayer() → StepPlayerResult      1歩ぶんの結果（moved / blocked / turned /
                                     jumped / warp / encounter / event）
stepEvent()  → EventEffect[]         「これをやってくれ」の列。message で止まる
```

- 描画は毎回**全面再描画**。差分更新はしない（12×18 マスの矩形塗りに最適化の余地はない）
- 歩行は 130ms の線形補間。**位置の正は整数のマス目**で、補間は描画にしか使わない
- タイルの色は `terrain` と `collision` から決めるのを基本にしつつ、
  **凡例の文字による色の上書きを許す**（§2.3）
- `data-at` 属性に現在地を書き出す。`tools/playthrough.mjs` がこれを読む

### 2.3 アセットが無いときの色 ― 規則から導出しきらない

当初は「色は `terrain` と `collision` だけから決める。タイル文字は見ない」で実装した。
見た目とルールを分離した趣旨に忠実なつもりだったが、**動かしたら町が森に見えた。**
家の壁も木も「通行不可・地形は normal」で、同じ色になる。

**訂正: 凡例の文字ごとの色を持たせ、無ければ規則から決める。**
見た目とルールを分けたのは、**片方をもう片方から導出しないため**であって、
見た目の情報を捨てるためではなかった。通行不可であることは色ではなく枠線で示す
（色を差し替えても「入れない」が読み取れるようにする）。

### 2.4 v0.10.5 の実装 ― 「隣を見る」だけで町に見える

§2.3 で凡例の文字ごとに色を持たせたが、それでも画面は
**同じ大きさの四角が敷き詰められているだけ**だった。1マス＝1色である限り、
色を増やしても密度が上がるだけで、地面と物の区別はつかない。

v0.10.5 で足したのは3つ。**どれもデータを1文字も変えていない。**

| 変えたこと | やっていること | 効き方 |
| --- | --- | --- |
| オートタイル | 上下左右が**同じ種類か**を見て、縁と角だけ描き分ける | 草地に縁ができ、道が繋がる |
| 建物のまとまり描画 | 同じ文字の連結成分を1棟として拾い、屋根・壁・窓・軒に分ける | 家が「壁色の四角の集まり」でなくなる |
| 影とピクセル単位のカメラ | 足元に影、カメラをマス単位でなく画素単位で追従 | 人が地面の上に立って見える |

縁は**内側に**描く。外側に描くと隣り合う同種のマスの間に線が二重に出て、
かえって格子が強調される ―― 「1色の四角が並ぶ」感じを消すのに一番効いたのはこの一点だった。

**建物は「大きさを知って初めて描ける」。** 屋根を上2列に、窓を壁の中央に置くには、
そのマスが塊のどこにあるかを知っている必要がある。1マスずつ塗る限り原理的に描けない。
連結成分の検出はマップごとに1回だけ行って覚える。

#### 世界の色はテーマに追従しない

【決定】**マップの中の世界は明暗テーマに従わない。周りの UI だけが従う。**
ゲーム世界の色は世界の設定であって、閲覧環境の設定ではない。
（§2.3 で「通行不可は色ではなく枠線で示す」と決めたのと同じ筋 ――
見た目の意味を、見る側の都合で書き換えない）

#### 見た目の検証は「撮って並べる」しかない

**見た目に自動判定は無い。** したふりをするより、見る道具を作る方がよい。

- `npm run shots` … 代表8か所をスマホ幅・広い幅で一括撮影（`dist/shots/`）
- `npm run gallery` … それを**1枚の HTML** にまとめる（画像は data URI・外部参照ゼロ）

1枚に閉じてあるのは、そのまま Artifact にして**スマホで見られる**ようにするため。
凡例の色は `art/tiles.ts` から読み出す（手で書き写すとずれる）。

なお `shots.mjs` で最初に踏んだのは
**「歩き終えた」と「着いた」を区別していない**という自分の道具の欠陥だった。
経路を歩き切ったら成功と報告していたので、向き直りで1歩ぶん食われた状態で
「✓ 1番道路」と言いながらマサラタウンを撮っていた。
検証が通ることと目的が達成されていることは別、という v0.7 の話が道具の側で再発した形。

### 2.5 v1.3-f の実装 ― 大きさを変えたら、大きさに紐づく数字も動かす

v1.3-a で1マスを 28px から **16px** に縮めた。座標は比率で書いてあったので
配置は壊れなかったが、**絵のほうが 28px 前提のまま**だった。

| | 28px のとき | 16px にしたら |
| --- | --- | --- |
| 角の丸み | 固定 5px ＝ **18%** | 固定 5px ＝ **31%**。角が面を食う |
| 草 | 縦棒3本＋濃い根元。1株ぶんの余白があった | 余白が消え、並べると**横縞と縦の筋**が立つ |

固定の長さは、大きさが変わった瞬間に**別の意味の数字になる**。
角は `size / 6` の割合に、草は「小さな株を2つ、高さと位置をずらす」形に変えた。

木では逆向きの失敗をした。四隅を「地面色で削って丸く見せる」つもりで
`shade(base, -0.42)` を塗ったが、木の緑は元が暗いので**黒に振り切れ**、
林が「黒い穴の並んだ格子」になった。外周の丸みはオートタイルの角（§2.4）が
すでに持っているので、ここで足す必要は無い ――
**林に見えるのは木そのものより、木と木の間の隙間のほう。**

地面の斑は2つ間違えた。①置く条件を `hint === undefined` にしたが、
`layers.ground` は平地にも凡例文字を入れるので**一度も通らなかった**
（「作った」と「置いた」は別）。②位置を画面の座標から決めていたが、
`camera()` は見える行数が偶数だと半マスずれるので、歩くたびに模様が動いて
**地面が這って見える**ところだった ―― 地面の模様は地面の座標から決める。

### 2.6 v1.3-g の実装 ― 画面の切り替わりに幕を掛ける

原作は場面が変わるとき**必ず何かを挟む**。扉をくぐれば暗転、野生が出れば縞、
トレーナーに見つかれば光ってから閉じる。こちらは器（v1.3-a）を作ったのに
**中身が瞬間で入れ替わっていた**ので、どこへ移ったのかが目で追えなかった。

| 種類 | 形 | 使う所 |
| --- | --- | --- |
| `door` | 暗転 | warp・バトルからの戻り |
| `wild` | 横縞が左右**交互に**閉じる | 野生 |
| `trainer` | 白く数回光ってから上下に閉じる | トレーナー |

縞の向きを1段おきに変えているのは、揃えると**まっすぐ落ちる幕**にしか見えず、
「草むらから何か来た」合図にならないため。戻りは種類を問わず暗転にする ――
縞で戻ると、もう1戦始まるように見える。

**覆いは `.screen` の中ではなく外に1枚だけ置く。**「操作するものは画面の外、
見せるものは画面の中」の唯一の例外で、理由は覆いの役目が
**マップの画面とバトルの画面の入れ替わりを隠すこと**だから ――
中に置くと入れ替えの瞬間に覆いごと消え、そこだけ素が見える。
毎フレーム「いま見えている `.screen`」を測って重ねる。

踏んだのは1つ。バトルへ入るとき `#run` を隠してから覆っていたので、
**どちらの画面も出ていない一瞬**ができ、覆いは重ねる先を見失って何もしなかった。
野生が出ても縞が1枚も出ないのに、エラーは1件も出ない ――
**推測ではなく実測で分けた**（覆いが出た回数を数える probe を書いたら 0 回だった）。
順番を「覆ってから隠す」に直して 23 回。

演出は結果に触れない（§4 と同じ約束）。`motionOn()` が偽 ――
高速モード・ログのみ・`prefers-reduced-motion` ―― なら覆いを1枚も描かずに
入れ替えだけ済ませる。**つまり `playthrough` はこの演出を一度も通らない。**
見た目の版に自動判定は無いので、確かめたのは probe で撮った駒だけ。

### 2.7 v1.4 の実装 ― 窓・家具・人

v1.3 で器（240×160）と絵の作りは原作に寄ったが、**中に置いてあるものが3つ残っていた。**

#### ③ 窓の中身（v1.4-a）

枠は原作の窓にしたのに、中身は Web のカードのままだった ――
題は本文と同じ地の大見出し＋青い罫、押す所は角丸・青枠・高さ32px のボタン、
行は青い罫で区切り、はみ出した行は下端で切れたまま。

| | 直す前 | 直したあと |
| --- | --- | --- |
| 題 | 本文と同じ地に大きな字 | **帯**（`sticky`・送っても残る） |
| ボタン | 角丸・青枠・32px | **角の無い箱**＋右下1pxの影、押すと沈む |
| 行 | 青い罫で区切る | 罫をやめる（10px の字より罫が目立つ） |
| ピル | `border-radius: 999px` | 平ら（`.screen` の中だけ） |
| はみ出し | 下端で切れたまま | **▼**（会話窓と同じ意味） |

▼ の出し入れは `MutationObserver` が見る。**窓の中身を書く所は5つある**ので、
呼ぶ形にすると1つ書き忘れたときに印だけ古くなる ―― 呼ばずに見張る。

途中で `#field-panel button` が CSS に**2つ**あるのを見つけた（v1.3-b の
書き足しが残っていた）。後ろが勝つので、直したはずの角丸が消えなかった。

#### ② 屋内の家具（v1.4-b）

屋外は §2.4・§2.5 で形が出るようになったが、屋内は1マス1色のままだった。
ここでも足したのは1つ。

> **上と下を見る。**

家具は上から見た箱なので、上の縁が天面・下の縁が前面になる。
どちらが縁かは `view.same`（オートタイルと同じ材料）がすでに知っている。

**見た目を足すと、データの兼用が見える。** 研究所の実験台と家の机は
`T`（木）と同じ文字だった ―― 通行不可という規則は同じなので誰も困らなかったが、
木に樹冠を描いた瞬間に**実験台が緑の茂みになった。**
直したのは絵ではなく凡例のほう（屋内3枚・7マスを `t` に分ける）。

#### ① フィールドの人（v1.4-c）

主人公も NPC も**1マスぶんの四角**だった。四角に見える理由は塗り方ではなく
**大きさ**で、原作の人は1マスより背が高い（上のマスへ頭が出る）。
マスにぴったり収める限り、どう塗っても「マス」に見える。

姿は §4.3 と同じで**組む** ―― 髪・肌・服・ズボンの色と、向きと、歩きの駒だけ。
決まった人（オーキド・ママ・ライバル）は表に置き、それ以外は
`sprite` の文字から色を決める。**表だけにするとトレーナー165人ぶんの行が要る**うえ、
書き忘れた人だけ同じ色で立つことになる。

ここで1つ**外した**。トレーナーの向いている側に置いていた白い印は、
v0.12 のコメントに書いてあるとおり「姿がただの四角だから」入れたもので、
人に髪と顔が付き**後ろ向きには目が無い**いま、向きは姿そのもので分かる ――
腰に貼り付いた白い箱にしか見えなくなっていた。**理由が消えたものは一緒に消す。**
視線の帯は残す。あれは向きではなく**届く距離**を見せていて、姿からは分からない。

#### 道具が別の書体で撮っていた

この3つを直す前に、`shots` が**代替書体の画面を撮っていた**ことに気づいた。
画面の文字は DotGothic16（Google Fonts・§10 で唯一許した外部ホスト）だが、
撮影に使う Chromium は proxy を通していないので取りに行けない ――
「見た目に自動判定は無いから撮って見る」と決めた道具が、
**本物と違うものを見せていた。**

書体を先に取っておき、読み込み後に `@font-face` を1枚差し込む形にした。
最初は要求を横取りして中継したが、分割された woff2 を1本ずつ返すことになり、
撮影が不安定になった（`△` が 9〜13件）。**通信には手を出さない。**

その `△` を追ったところ、原因は書体ではなく**台本が返事を読んでいないこと**だった。
`#save-import` は失敗したときも黙っている（画面には「よみこめませんでした」と出る）。
直前の読み込みの `refresh()` が設定画面を作り直すので、書いた直後に
textarea ごと差し替わると空文字を読ませることになる ――
書体はその窓を広げただけで、穴は前からあった。
**時間を数えるのをやめて、返事を読む。**

## 3. 画面構成

```
タイトル
  │ 続きから / 新規 / インポート
  ▼
┌─ ホーム（拠点）────────────────────────┐
│  本作固有の画面。原作には存在しない      │
│  地方が並列で、エンドゲームが別軸のため   │
│  「地方の外側」に起点が必要になる         │
└─┬──────────────────────────────────────┘
  │
  ├─ 地方を選ぶ ──→ マップ探索 ──→ バトル
  │                    └→ 手持ち / バッグ / 地方ボックス
  │
  ├─ エンドゲーム ──→ 施設選択 ──→ 編成 ──→ 連戦
  │                 └→ トーナメント ──→ カップ選択 ──→ 編成
  │
  ├─ 共通ボックス（§5）
  ├─ 図鑑
  ├─ 殿堂・記録
  └─ 設定
```

### ホーム画面が必要な理由

原作は「1つの地方の中」で完結するのでこの画面が存在しない。
本作は**地方が9つ並列にあり、エンドゲームが地方の外にある**ため、
それらを束ねる起点が構造上どうしても必要になる。

ホームに置くもの: 地方の一覧（進行状況・難易度目安）、エンドゲームへの入口、
BP残高、図鑑の完成率、周回加速の段階。**3本の進行軸がここで一望できる**形にする。

### 3.1 v0.10 の実装 ― ホーム画面は「メニュー」ではなく「場所」にした

§3 の図はホームを**画面**として描いていたが、実装では**歩ける拠点マップ**にした。

v0.9 まで、この役目は画面上部のモードタブ（ぼうけん／トーナメント／バトルしせつ／
ネームド／フリーバトル／セーブ）が担っていた。**ゲームというより機能の一覧**で、
「どこに居るのか」がプレイヤーの側に存在しなかった。

拠点をマップにすると:

- 施設・大会・保管庫は**建物に入って受付に話しかける**（原作の手触りに寄る）
- 地方へは**ゲートから入る**。9地方が並んでいることが目に見える
- **マップを足すのに要るのはデータだけ**という性質が、そのままメニュー構造にも効く
  ―― 施設を1つ増やすのに UI のコードは増えない

### 3.2 タブを消すと「逃げ道」が消える

**タブがあった頃は、どこで詰まっても別のタブへ逃げられた。**
消した瞬間、それぞれの画面が自前の出口を持たなければならなくなる。

実際に踏んだ:

> BP交換所で1つ買うと画面が描き直され、**その拍子に「もどる」ボタンが消えて
> 拠点へ戻れなくなった。**

原因は出口を `#menu`（描き直される場所）の中に置いていたこと。
**出口は描き直しに巻き込まれない場所に置く**（`#screen-back` は `#menu` の外）。

同じ理由で、**セーブ／設定への入口だけはヘッダに常設した。**
マップが壊れた版を掴んだとき、バックアップに辿り着けなくなるのがいちばん困る
（エクスポートが唯一の保険・[`save-data.md`](save-data.md) §9.7）。

### 3.3 拠点と地方で、同じ画面が違うものを見る

マップ画面・手持ち・ボックスのコードは1つで、**中身だけが居場所で変わる**。

| | 地方に居る | 拠点に居る |
| --- | --- | --- |
| ボックス | 地方ボックス | **共通ボックス**（ここでだけ引き出せる） |
| 手持ち | その地方の手持ち | 共通ボックスから編成したもの |
| 進行（フラグ・お金・バッジ） | ある | **無い**（拠点に進行という概念が無い） |

`player.region === null` が拠点、という1つの判定に寄せてある。
画面の側は「今どちらに居るか」をほとんど知らなくてよい。

## 4. バトル画面

### core とのつなぎ方

[`battle-system.md`](battle-system.md) の `step()` は **`BattleEvent[]` を返す**。
UIはこれを**キューとして順に消費して演出する**だけ。

```
core:  step(state, actions) → { state, events }
                                   │
UI:    イベントキューを1件ずつ取り出し、演出して次へ
```

- **`core` は時間の概念を持たない。** 演出速度・スキップは完全にUI層の関心事
- これにより「演出を飛ばしても結果が変わらない」ことが構造的に保証される
- テストは `events` を検証するだけでよく、描画を伴わない

### 周回のための高速モード

エンドゲームで数百戦する以上、**演出の長さが直接プレイ体験を殺す。**

| モード | 内容 |
| --- | --- |
| 通常 | 演出あり |
| **高速** | 演出短縮・アニメーション省略 |
| **ログのみ** | 結果テキストだけを流す。連戦の周回向け |

設定で既定値を選べるようにし、バトル中にも切り替えられるようにする。
捕獲演出の短縮（[`capture.md`](capture.md) §8）も同じ設定系統に載せる。

### 表示要素

- HUD: 双方のHP・状態異常・能力ランク（上下矢印）・残り数
- 技選択: タイプ・分類・残PP。**相性の既知/未知の扱いは §6**
- 交代画面: 手持ち一覧、相性の目安
- バトルログ: 遡って読める（何が起きたか分からないまま進まないため）

### 4.1 v0.11.5 の実装 ― 演出を足す前に、足せない造りを直した

上の分担（`core` はイベントを返すだけ・UI が演出する）は v0.1 から守れていた。
だが**演出は1つも無かった**。理由は分担の側ではなく、UI の書き方にあった。

> `#field` の innerHTML を、**イベントごとに全部作り直していた。**

そのため、

- `.fill { transition: width .3s }` は v0.3 から CSS にあったのに**一度も動いていない。**
  幅は毎回「新しい要素の初期値」として即座に確定していた
- 揺れも点滅も、始まった瞬間に要素ごと消える

**作り直しをやめない限り、どんな演出も原理的に効かない。**
v0.10.5 の「1マス1色である限り、色を増やしても密度が上がるだけ」と同じ形で、
足したいものより先に、足せない造りの方を直す必要があった。

**訂正: 骨組みを1回作り、中身だけ差し替える。** 作り直すのは**交代したときだけ**。

作らない側に倒したぶん、片付けは明示的にやることになった ――
バトルを始めるときに `#field` を空にし忘れていて、
撮影したら**1画面に4体並んでいた**（前の戦いの2体が残っていた）。

#### 足した演出

| イベント | 演出 |
| --- | --- |
| `moveUsed` | 技を出した側が前に出る＋**技のタイプ色で場を1瞬染める** |
| `damage` | 揺れる。**ばつぐん・急所は強く、いまひとつは弱く** |
| `statusDamage` / `recoil` / `itemDamage` | 弱く沈む（技の被弾と区別がつく程度に） |
| `drain` / `heal` | 明るくなる |
| `faint` | 落ちる。**これだけ元に戻さない**（次の交代まで倒れたまま） |
| `switchIn` | 下から出る |

**演出は表示を更新する前に掛ける。** 順番を逆にすると、HPバーが先に縮んでから揺れる。

演出が止まる条件は2つ。**高速モード／ログのみ**（周回のための機能なので演出は邪魔）と、
**`prefers-reduced-motion`**（閲覧環境の設定を上書きしない）。
`core` を1行も触っていないので、飛ばしても結果は1ビットも変わらない。

### 4.2 書体 ―「ゲームの声」だけドット字にする

Google Fonts は Artifact 版で使える**唯一の外部ホスト**なので、書体だけは外部参照にできる。
`DotGothic16`（和文ドット風）を、**見出し・会話・ログ・ポケモンの名前**にだけ当てる。
操作系（ボタン・表・設定）は素の書体のまま ―― 全部ドット字にすると小さい字が読めない。

フォールバックには**必ず実在する和文フォント**を積む。
抜けると環境によっては中華フォントに落ちて、字面が別物になる。

**撮影環境からは fonts.googleapis.com へ出られない**ので、
`npm run shots` の写真はフォールバックの姿で写る。
「読み込めなくても成立する」ことの確認にはなっているが、
**本来の姿はこちらでは確認できていない**ことを記録しておく。

### 4.3 v0.12.5 の実装 ― 姿は「描く」のではなく「組む」

丸をやめて、種ごとにシルエットを描き分けた。
**1体ずつ描いていない。** 151種＋追加分を1体ずつ描くのは終わりが無いので、
タイル（v0.10.5）と同じ形にした ―― **種類だけがコードで、種ごとの指定はデータ。**

| | どこにある | 何種類 |
| --- | --- | --- |
| 体型 | `art/sprites.ts` の `SHAPE` | 14 |
| 飾り | 同 `PART` | 14 |
| 種ごとの指定 | `source/art.tsv` → `art.json` | 190行 |

レジストリの形はこれで7回目（技効果・持ち物・イベントコマンド・検証・ボール・タイル）。
**体型を1つ足すのはコードに1行**で、データ側は触らない。

#### 体型・体色・大きさは公式の分類だった

いちばん効いたのは、**姿を自分で決めなかった**こと。
veekun の `pokemon_species.csv` は種族ごとに
`shape_id`（14種）と `color_id`（10色）を持っている。`pokemon.csv` には高さがある。

**どれも絵ではなく分類・数値**なので、[`game-plan.md`](../game-plan.md) §10 のもとで
このリポジトリに置ける。取り込み口は v0.9.5 と同じ形にした（`tools/fetch-art.ts`）。

飾り（炎・葉・角…）だけがこちらの判断で、**タイプから導いている。**
分けておくと、飾りを増やすときに体型を触らずに済む。

#### 「見た目が被った組み数」を測る

シルエットを描き分けるのが目的なので、**被りの多さがそのまま出来の指標**になる。
検証が数えて警告に出す。

| | 被った組数 | 最大 |
| --- | --- | --- |
| 体型・体色・飾りだけ | 39組 | 6種（ポッポ〜カモネギ） |
| **＋大きさ**（公式の高さから4段階） | **16組** | **3種** |

大きさを足したのは、この数字を見てから。
**進化前後が同じ絵になる**のがいちばん目につくので、そこに効いた。

#### 目の位置は体型ごとに持つ

最初は目を固定位置に置いていたが、四足の種で**胴体に目がついた**（頭は左端にある）。
体型ごとに「頭のある場所」を持たせた ―― 体型が変われば頭の位置も変わるので、
これは体型の一部として持つのが正しい。

**まだシルエットの段階。** 目立つ種から詰めるのは次以降で、
その作業も `art.tsv` の1行を書き換えるだけになっている。

### 4.5 v1.5 の実装 ― 「同じ絵の種」を 0 にして、そこを関門にする

§4.3 で姿を**組む**ことにしたが、語彙は「体型・体色・大きさ・飾り」の4つだけだった。
228種を並べたら **37種（17組）が完全に同じ絵**になっていた ――
リザードとブーバー、ピジョンとオニドリル、フシギダネとフシギソウ。
分類が粗いのではなく、**種を分けている特徴を1つも持っていなかった。**

足したのは「見分けるときに人が最初に見る所」4つ。

| 列 | 語彙 | 例 |
| --- | --- | --- |
| `accent` | 体色10色＋差し色6色 | ヒトカゲの腹（cream）、ピカチュウのほお（red） |
| `ears` | 6種 | `long`（ピカチュウ）・`pointed`（イーブイ）・`tuft`（鳥）・`fin`（水） |
| `tail` | 10種 | `flame`・`bolt`・`bushy`・`swirl` は付かないが `curl`・`fan`・`fin` |
| `mark` | 8種 | `belly`・`spots`・`stripes`・`mask`・`swirl`・`cheeks` |

**しっぽは体型から外した。** `upright` が自前で1本描いていて、種のしっぽと二重になる
―― しっぽは体型ではなく種のもの。耳は `head`（頭の位置と大きさ）に合わせる。
目の位置だけでは足りない ―― 目は顔の中の1点で、耳は頭の外周に付く。

#### 警告を関門に上げた（#126）

ここは v0.12.5 から**警告**だった。4つの語彙では 0 にできないものを
「落ちる」にはできないので、数えるだけにしていた。
v1.5 で **0 にできるようになった**ので関門に上げる ――
**一度も 0 にならない検査は、無いのと同じ**だった。
わざと2種を同じにして落ちることを確かめてある。

#### 公式の分類を、そのままにしない所

体型は公式の分類（veekun の `pokemon_species.csv`）から取っているが、
**あの分類は「体の作り」であって「立ち姿」ではない。**
ピカチュウは `Quadruped`、ラプラスは `Fish` に分類されている ――
そのまま描くと本人に見えない。取り込みが作るのは下地で、**原本は TSV** なので、
そこだけ手で詰めた（ピカチュウ→`upright`、ラプラス→`quadruped`）。

#### ここから先は「絵」になる

これ以上似せようとすると、**種ごとに形を指定する**ことになる ――
それは分類ではなく絵で、公開リポジトリに置くものが変わる（§10）。
語彙を増やして組み合わせを増やすところまでが、この作りで行ける範囲。

### 4.4 v1.0 の実装 ― 殿堂は「画面」ではなく「場所」に置いた

チャンピオンに勝つと殿堂入りの画面が出て、記録がセーブに残る。
読み返すのは**拠点の広場に立っている「でんどうの ひ」**から。

v0.10 で「ホーム画面ではなく場所」と決めたので、殿堂もそれに合わせた ――
[`game-plan.md`](../game-plan.md) §8.1 の v1.0 の欄には「ホーム画面・殿堂・設定」と
書いてあるが、**ホーム画面は v0.10 の拠点マップで既に済んでいる。**
ここで新しい画面を1つ増やすより、広場に石碑を1つ置くほうが構造と揃う。

足したのはイベントコマンド2つ（`hallOfFame` / `openHall`）だけで、
石碑も、勝ったときに記録することも、全部データ側にある。

**記録を残してから見せる。** 逆にすると、演出の途中で閉じたときに
「殿堂入りしたのに記録が無い」状態が作れてしまう。

## 5. 共通ボックス ― 最も設計が要る画面

数千個体を扱う。**普通に作ると破綻する唯一の画面。**

### 必須要件

| 要件 | 理由 |
| --- | --- |
| **仮想スクロール** | 数千件をDOMに一度に置けない。可視範囲だけを描画する |
| **検索・フィルタ** | 種族 / タイプ / 捕獲地方 / レベル / 技 / 性格 / 特性 / お気に入り |
| **ソート** | 図鑑番号 / 捕獲順 / レベル / 種族値合計 |
| **一括操作** | 複数選択して移動・逃がす・お気に入り登録 |
| **名前付きチーム保存** | 施設の周回に必須。毎回6体選び直す摩擦を消す |
| **遅延読み込み** | 個体の実体は別ストア（[`save-data.md`](save-data.md) §2）。可視分だけ読む |

### 捕獲地方の表示

`PokemonInstance.meta.caughtRegion`（[`progression.md`](progression.md) §14）を
一覧に出す。9地方を周回する構造では、**これがプレイヤーの記録＝思い出**になる。
ボックスを眺めること自体が、本作では collection の体験になる。

## 6. 情報の出し分け

[`progression.md`](progression.md) §1 の二段構え（本編は育成を隠す、
エンドゲームで深く見せる）を、UIで実現する。

**画面ごとに分岐を書かない。表示レベルを1つの状態で持ち、各画面がそれを参照する。**

```ts
type DisclosureLevel = "basic" | "advanced";
// basic:    種族・レベル・技・HP・状態のみ
// advanced: + 個体値・努力値・性格補正・実数値・タイプ相性の詳細
```

- 初回の殿堂入りで `advanced` に切り替わる
- 設定で任意に切り替えられるようにする（原作の知識がある人は最初から見たい）

### タイプ相性の表示

技選択画面で「こうかばつぐん」等を出すかは、この `DisclosureLevel` に紐づける。

| レベル | 表示 |
| --- | --- |
| `basic` | **一度でも当てたことがある組み合わせ**のみ相性を表示（原作準拠。図鑑の「捕まえた」種にも表示） |
| `advanced` | 常に表示 |

「既知の相性だけ見せる」ための記録は、図鑑とは別に
`seenMatchups: Record<string, true>`（攻撃タイプ × 防御タイプ）としてセーブに持つ。

分岐を各画面に散らすと、新しい画面を足すたびに漏れる。**1箇所で決める。**

## 7. 操作系

| 入力 | 対応 |
| --- | --- |
| キーボード | 方向キー + 決定/キャンセル。**原作準拠の操作感** |
| マウス | クリック操作。メニュー・ボックスは主にこちら |
| タッチ | スマートフォンでの操作。**レスポンシブ対応が前提** |

ブラウザゲームである以上、**PCとスマートフォンの両方で成立させる。**
DOM主体のUIにした判断（§2）が、ここで効いてくる。

## 8. テキストの扱い

会話・技名・種族名・説明文で、テキスト量は膨大になる。

- **テキストは全てデータとして外出しする。** コードに文字列を埋め込まない
- 日本語のみで進めるが、構造としては差し替え可能にしておく（多言語化は当面やらない）
- 会話データは地方ごとのディレクトリに置く（[`data-schema.md`](data-schema.md) §4）
