# 06. エンドゲーム

関連: [`named-characters.md`](named-characters.md) / [`ai.md`](ai.md) / [`progression.md`](progression.md) / [`capture.md`](capture.md) / [`regions.md`](regions.md)

---

## 1. 設計方針

**ここがゲームの本体。** 地方チャレンジは「ポケモンを集め、愛着を作る層」で、
プレイ時間の大半はこの層で消費される。

エンドゲームが個人開発と相性が良い理由:

> **マップをほぼ必要とせず、ルールを1つ変えるだけで新しいコンテンツになる。**

そのため設計の目標は「面白い施設を作る」ことではなく、
**「施設を安く量産できる構造を作る」**ことに置く。

## 2. 構造

```
┌─ トーナメント ──────────────────────┐
│  歴代ネームドが出場する勝ち抜き戦      │  有限だが密度が高い
│  3〜4戦で1セット。カップで分類        │  「誰と戦うか」が主役
└──────────────────────────────────────┘
┌─ バトル施設 ────────────────────────┐
│  ルール特化の連勝チャレンジ           │  無限に遊べる
│  段位が上がるほど相手が強くなる        │  「どう戦うか」が主役
└──────────────────────────────────────┘
        ↓ 両方から BP を得る
   BP → 育成アイテム・レア個体・幻ポケモン
        ↓
   より強い個体を作り、上位に挑む
```

## 3. 解放条件

**いずれかの地方で殿堂入りすると、エンドゲームが開放される。**

施設は**段階的に解放する**（バトルタワーが最初、以降はタワーの段位で順次）。

> 地方はロックしないのに施設はロックする理由: **地方は全て同じルールで並列**だが、
> **施設はそれぞれルールが違う。** 一度に全部見せると学習負荷が高すぎる。
> ロックの根拠は難易度ではなく、ルールの学習曲線にある。

## 4. ルールセット ― 施設を安く量産する仕組み

**施設をハードコードしない。** 施設 = **ルールセット + 相手プール + 報酬** の3データで定義する。

```ts
type Ruleset = {
  // 編成
  teamSize: number;                      // 持ち込む数
  battleSize: number;                    // 実際に戦う数（3体選出など）
  teamSource: "own" | "rental" | "hallOfFame";
  levelMode: { kind: "sync"; level: 50 | 100 } | { kind: "asIs" };
  duplicateSpecies: boolean;
  duplicateItems: boolean;
  bannedSpecies?: SpeciesId[];           // 伝説禁止など
  requiredType?: Type;                   // タイプ縛りカップ

  // バトル
  battleFormat: "single" | "double";
  itemsAllowed: boolean;                 // 回復道具の持ち込み
  winCondition: { kind: "faint" } | { kind: "turnLimit"; turns: number; judge: JudgeRule };
  moveSelection: "player" | "auto";      // 技を自分で選べない（パレス式）

  // 連戦
  streakLength: number | "endless";
  healBetweenBattles: boolean;
  carryOverDamage: boolean;              // HP/PPを次戦に持ち越す
  swapAfterWin?: "factory";              // 勝った相手から1体貰う
};
```

**`levelMode.sync` は双方向**（[`progression.md`](progression.md) §12）。
Lv50未満のポケモンも自動で50に引き上げられるため、**捕まえたばかりの個体をそのまま持ち込める。**
これがエンドゲームへの参入障壁を大きく下げる。

## 5. 施設カタログ

| 施設 | 特徴的なルール | 実装コスト |
| --- | --- | --- |
| **バトルタワー** | 標準。`teamSource: own`, Lv50同期, 回復なし | 低（基準） |
| **バトルファクトリー** | `teamSource: rental` + `swapAfterWin` | 低 |
| **バトルアリーナ** | `winCondition: turnLimit(3)` + 採点 | 低 |
| **バトルパレス** | `moveSelection: auto`（性格で行動決定） | 低 |
| **バトルホール** | 1体で連戦。次の相手のタイプを自分で選ぶ | 低 |
| **バトルキャッスル** | BPを消費して回復・相手情報を購入 | 中 |
| **タイプ縛りカップ** | `requiredType` を変えるだけ | **ほぼゼロ**（18種類作れる） |
| バトルピラミッド | ダンジョン探索＋道具制限 | **高（マップが必要）→ 後回し** |

**タイプ縛りカップは `requiredType` を差し替えるだけで18施設ぶんになる。**
ルールセット駆動にした見返りが最も分かりやすく出る例。

### 採点ルール（アリーナ式）

`turnLimit` で決着しなかった場合の判定。データとして持つ。

```ts
type JudgeRule = { criteria: ("hpRatio" | "damageDealt" | "movesHit")[] };
```

## 6. 相手はどこから来るか ―【重要】BattleSet プール

施設は無限に周回できるが、**ネームドは有限**（9地方 × 約30人）。
施設の相手を手書きすると、すぐ枯渇して「同じ相手ばかり」になる。

### 相手パーティは手書きせず、生成する

```ts
type BattleSet = {
  id: string;
  species: SpeciesId;
  moves: [MoveId, MoveId, MoveId, MoveId];
  item: ItemId;
  ability: AbilityId;
  nature: NatureId;
  evs: StatSpread;
  grade: 1 | 2 | 3 | 4;        // 強さの段階。段位に応じてプールを切り替える
  tags: TacticId[];            // "sandstorm" 等。噛み合う組を選ぶのに使う
};
```

- **トレーナークラス**（エリートトレーナー、ベテラン等）ごとに使用可能な `BattleSet` プールを定義
- 段位が上がると使われる `grade` が上がる
- パーティ生成 = プールから種族が重複しないよう抽選 + `tags` の噛み合いを見る

### この設計の効き目

- **`BattleSet` を1件足す = コンテンツが増える。** 施設側のコードは触らない
- **レンタル制（ファクトリー）でも同じデータを使う。** 1つのデータが2用途
- **「全ポケモンが出る」の最も濃い回収先がここ。** 野生分布は生息地の都合で偏るが、
  施設の相手プールは**全1,025種を均等に登場させられる**。
  最初の希望が最も強く実現するのは、実は本編ではなくこの層になる

## 7. トーナメント

ブラック2/ホワイト2の PWT 形式。1回で3〜4戦。

### カップ

出場者プールを差し替えるだけで増やせる。

| カップ | 出場者プール |
| --- | --- |
| 地方カップ（9種） | その地方のジムリーダー・四天王・チャンピオン |
| ジムリーダーカップ | 全地方のジムリーダー |
| 四天王カップ | 全地方の四天王 |
| **チャンピオンカップ** | 歴代チャンピオンのみ。タイプ縛りがないため最高難度 |
| 悪の組織カップ | 各組織のボス・幹部 |
| タイプカップ（18種） | 該当タイプ使いのネームド |
| **究極カップ** | 全ネームドの「極」ティアのみ |

**出場者は毎回プールから抽選する。** 決め打ちにするとリプレイ性が消える。

### ティア解放

```
原作ティアで優勝 → 本気ティア解放 → 制覇 → 極ティア解放
```

同じカップが3回遊べる。[`named-characters.md`](named-characters.md) §6 の3ティアが、
そのまま3周ぶんのコンテンツになる。

## 8. 難易度カーブ

施設の連勝数に応じて、相手の `BattleSet` の `grade` と AI を上げる。

| 連勝 | grade | AI（[`ai.md`](ai.md) §7） |
| --- | --- | --- |
| 1〜10 | 1 | `basic` / 誤り率 0.3 |
| 11〜20 | 2 | `basic` / 0.15 |
| 21〜30 | 3 | `smart` / 0.1 |
| 31〜40 | 4 | `smart` / 0.0 |
| 41〜 | 4 | `smart` / 0.0 / `partial` 知識 |

**10連勝ごとに施設のボス（ブレーン）が出る。**
ブレーンは `NamedCharacter` として定義するため、
[`named-characters.md`](named-characters.md) の枠組み（3ティア・`concept`・`tactic`）をそのまま流用できる。

## 9. BP経済

### 収入

| 経路 | 額 |
| --- | --- |
| 施設の連戦（節目ごと） | **連勝数が上がるほど1戦あたりの額が増える** |
| トーナメント優勝 | カップとティアに応じて |
| 初回クリアボーナス | 各施設・各カップの初回のみ大きく |

### 設計原則：作業ではなく達成に報いる

> **低段位の周回は非効率になるように、連勝数に応じて単価を上げる。**

これにより「1〜5連勝を延々繰り返して稼ぐ」が最適解にならない。
**強くなることが最も効率の良い稼ぎ方**になり、育成とエンドゲームが正しく噛み合う。

### 支出

| 用途 | 備考 |
| --- | --- |
| 育成アイテム（おうかん・ミント・とくせいパッチ・栄養ドリンク） | [`progression.md`](progression.md) §10。**主要な支出先** |
| わざマシン・教え技 | タマゴ技もここに統合 |
| レア個体・道具 | |

孵化システムを作らない代わりに、**個体を仕上げる手段が全て BP に集約される**。
「施設を遊ぶ → BPを稼ぐ → 個体を強化する → 上位に挑む」の循環が、
エンドゲームの主動線になる。

## 10. 報酬設計

### 幻ポケモンの配置

[`capture.md`](capture.md) §7 で「幻はエンドゲーム報酬」と決めた。具体化する。

> **BP交換ではなく、特定施設の特定段位への到達報酬にする。**

BP交換にすると「作業で買える」ものになり、収集の最後のピースとしての重みが消える。
**幻を手に入れるには、その施設を実際に踏破する必要がある**形にする。

### 記録

- 各施設の最高連勝記録
- トーナメントの制覇履歴（カップ × ティア）
- 撃破したネームドとティアの一覧 ―― **これが「全トレーナーが出る」の可視化。**
  何人中何人を、どのティアまで倒したかが一覧で見える形にする

## 11. データ表現

```ts
type Facility = {
  id: FacilityId;
  name: string;
  ruleset: Ruleset;
  opponentPool: { trainerClasses: TrainerClassId[]; gradeByStreak: GradeTable };
  brains: { atStreak: number; character: NamedId }[];
  rewards: {
    bp: BpTable;                                                   // 連勝数 → BP単価
    unlocks: { atStreak: number; grant: ItemId | SpeciesId }[];     // 幻ポケモン等
  };
  unlockedBy?: { facility: FacilityId; streak: number };
};

type Tournament = {
  id: CupId;
  name: string;
  ruleset: Ruleset;
  entrantPool: NamedId[];
  rounds: number;
  tierProgression: ["original", "serious", "ultimate"];
};
```

`Facility` と `Tournament` が**どちらも `Ruleset` を持つ**のが要点。
「トーナメントだけ回復あり」「この施設だけダブル」といった差分が、
コードではなくデータで表現される。

## 12. 調整項目（実装後に決める）

- BPの単価テーブルと育成アイテムの価格（**経済の要。実際に周回してみないと決まらない**）
- 連勝ごとの grade 切り替え点
- ブレーンの出現間隔（10連勝ごとが適切か）
- カップの出場者抽選ロジック（完全ランダムか、難易度が単調増加するよう調整するか）
- `BattleSet` を何件用意すれば「同じ相手ばかり」に感じなくなるか
- 施設の解放順とその条件
- 幻ポケモンをどの施設のどの段位に置くか
