# 10. 画面構成・UI

関連: 全章（特に [`battle-system.md`](battle-system.md) / [`capture.md`](capture.md) / [`endgame.md`](endgame.md)）

---

## 1. 設計方針

UIは「見た目」ではなく**構造の問題**として設計する。本作固有の要求は3つ。

| 要求 | 出どころ |
| --- | --- |
| **数千個体を扱えるリストUI** | 共通ボックス（[`capture.md`](capture.md) §5） |
| **周回に耐える操作の軽さ** | エンドゲーム主軸（[`endgame.md`](endgame.md)） |
| **情報の出し分け** | 本編は育成を隠す（[`progression.md`](progression.md) §1） |

## 2. 描画層の分担 ―【決定】Canvas と DOM を使い分ける

**決定: 世界の描画は Phaser（Canvas）、UIは DOM（HTML/CSS）。**

| 層 | 担当 |
| --- | --- |
| **Phaser / Canvas** | マップ探索、キャラの移動、バトルの演出、エフェクト |
| **DOM / HTML** | メニュー、ボックス、図鑑、編成、ショップ、設定、バトルのHUDと技選択 |

### 理由

- **リスト・検索・スクロールは DOM が圧倒的に安い。** 数千件の仮想スクロールを
  Canvas で自前実装するのは、得るものがない労力になる
- アクセシビリティ・テキスト選択・入力欄が無料で手に入る
- レスポンシブ対応も CSS に任せられる

Canvas でUIまで描く選択は「見た目の統一感」と引き換えに実装量が数倍になる。
本作はコンテンツ量が主戦場なので、**UI実装にコストを割かない方向に倒す。**

## 3. 画面構成

```
タイトル
  │ 続きから / 新規 / インポート
  ▼
┌─ ホーム（拠点）────────────────────────┐
│  本作固有の画面。原作には存在しない      │
│  地方が並列で、エンドゲームが別軸のため   │
│  「地方の外側」に起点が必要になる         │
└─┬──────────────────────────────────────┘
  │
  ├─ 地方を選ぶ ──→ マップ探索 ──→ バトル
  │                    └→ 手持ち / バッグ / 地方ボックス
  │
  ├─ エンドゲーム ──→ 施設選択 ──→ 編成 ──→ 連戦
  │                 └→ トーナメント ──→ カップ選択 ──→ 編成
  │
  ├─ 共通ボックス（§5）
  ├─ 図鑑
  ├─ 殿堂・記録
  └─ 設定
```

### ホーム画面が必要な理由

原作は「1つの地方の中」で完結するのでこの画面が存在しない。
本作は**地方が9つ並列にあり、エンドゲームが地方の外にある**ため、
それらを束ねる起点が構造上どうしても必要になる。

ホームに置くもの: 地方の一覧（進行状況・難易度目安）、エンドゲームへの入口、
BP残高、図鑑の完成率、周回加速の段階。**3本の進行軸がここで一望できる**形にする。

## 4. バトル画面

### core とのつなぎ方

[`battle-system.md`](battle-system.md) の `step()` は **`BattleEvent[]` を返す**。
UIはこれを**キューとして順に消費して演出する**だけ。

```
core:  step(state, actions) → { state, events }
                                   │
UI:    イベントキューを1件ずつ取り出し、演出して次へ
```

- **`core` は時間の概念を持たない。** 演出速度・スキップは完全にUI層の関心事
- これにより「演出を飛ばしても結果が変わらない」ことが構造的に保証される
- テストは `events` を検証するだけでよく、描画を伴わない

### 周回のための高速モード

エンドゲームで数百戦する以上、**演出の長さが直接プレイ体験を殺す。**

| モード | 内容 |
| --- | --- |
| 通常 | 演出あり |
| **高速** | 演出短縮・アニメーション省略 |
| **ログのみ** | 結果テキストだけを流す。連戦の周回向け |

設定で既定値を選べるようにし、バトル中にも切り替えられるようにする。
捕獲演出の短縮（[`capture.md`](capture.md) §8）も同じ設定系統に載せる。

### 表示要素

- HUD: 双方のHP・状態異常・能力ランク（上下矢印）・残り数
- 技選択: タイプ・分類・残PP。**相性の既知/未知の扱いは §6**
- 交代画面: 手持ち一覧、相性の目安
- バトルログ: 遡って読める（何が起きたか分からないまま進まないため）

## 5. 共通ボックス ― 最も設計が要る画面

数千個体を扱う。**普通に作ると破綻する唯一の画面。**

### 必須要件

| 要件 | 理由 |
| --- | --- |
| **仮想スクロール** | 数千件をDOMに一度に置けない。可視範囲だけを描画する |
| **検索・フィルタ** | 種族 / タイプ / 捕獲地方 / レベル / 技 / 性格 / 特性 / お気に入り |
| **ソート** | 図鑑番号 / 捕獲順 / レベル / 種族値合計 |
| **一括操作** | 複数選択して移動・逃がす・お気に入り登録 |
| **名前付きチーム保存** | 施設の周回に必須。毎回6体選び直す摩擦を消す |
| **遅延読み込み** | 個体の実体は別ストア（[`save-data.md`](save-data.md) §2）。可視分だけ読む |

### 捕獲地方の表示

`PokemonInstance.meta.caughtRegion`（[`progression.md`](progression.md) §14）を
一覧に出す。9地方を周回する構造では、**これがプレイヤーの記録＝思い出**になる。
ボックスを眺めること自体が、本作では collection の体験になる。

## 6. 情報の出し分け

[`progression.md`](progression.md) §1 の二段構え（本編は育成を隠す、
エンドゲームで深く見せる）を、UIで実現する。

**画面ごとに分岐を書かない。表示レベルを1つの状態で持ち、各画面がそれを参照する。**

```ts
type DisclosureLevel = "basic" | "advanced";
// basic:    種族・レベル・技・HP・状態のみ
// advanced: + 個体値・努力値・性格補正・実数値・タイプ相性の詳細
```

- 初回の殿堂入りで `advanced` に切り替わる
- 設定で任意に切り替えられるようにする（原作の知識がある人は最初から見たい）

### タイプ相性の表示

技選択画面で「こうかばつぐん」等を出すかは、この `DisclosureLevel` に紐づける。

| レベル | 表示 |
| --- | --- |
| `basic` | **一度でも当てたことがある組み合わせ**のみ相性を表示（原作準拠。図鑑の「捕まえた」種にも表示） |
| `advanced` | 常に表示 |

「既知の相性だけ見せる」ための記録は、図鑑とは別に
`seenMatchups: Record<string, true>`（攻撃タイプ × 防御タイプ）としてセーブに持つ。

分岐を各画面に散らすと、新しい画面を足すたびに漏れる。**1箇所で決める。**

## 7. 操作系

| 入力 | 対応 |
| --- | --- |
| キーボード | 方向キー + 決定/キャンセル。**原作準拠の操作感** |
| マウス | クリック操作。メニュー・ボックスは主にこちら |
| タッチ | スマートフォンでの操作。**レスポンシブ対応が前提** |

ブラウザゲームである以上、**PCとスマートフォンの両方で成立させる。**
DOM主体のUIにした判断（§2）が、ここで効いてくる。

## 8. テキストの扱い

会話・技名・種族名・説明文で、テキスト量は膨大になる。

- **テキストは全てデータとして外出しする。** コードに文字列を埋め込まない
- 日本語のみで進めるが、構造としては差し替え可能にしておく（多言語化は当面やらない）
- 会話データは地方ごとのディレクトリに置く（[`data-schema.md`](data-schema.md) §4）

## 9. 実装の段階

| 版 | UI |
| --- | --- |
| v0.1 | **なし**（CLI/テストのみ） |
| v0.2 | バトル画面（HUD・技選択・最小限の演出） |
| v0.3 | 施設の編成画面・連戦画面・結果画面 |
| v0.4 | マップ探索・移動 |
| v0.5 | 手持ち・バッグ・ボックス・セーブ画面 |
| v0.6〜v1.0 | ホーム画面・図鑑・殿堂・設定 |

**ホーム画面は v1.0 で作る。** それまでは地方が1つしかなく、束ねる必要がないため。
UIは「必要になった時点で作る」で問題ない領域なので、
[`README.md`](README.md) の線引きに従い、細部は設計しすぎない。

## 10. 調整項目（実装後に決める）

- 具体的なレイアウト・配色・フォント
- 高速モードの既定値（初回から高速にすると初見の演出を見られない）
- ボックスの1画面あたりの表示件数
- `DisclosureLevel` を殿堂入り前でも切り替え可能にするか
- バトルログを何ターンぶん保持するか
- スマートフォンでのマップ操作方法（仮想パッドか、タップ移動か）
