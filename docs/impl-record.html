v0.1

バトルの骨格

目的は機能の完成ではなく アーキテクチャの証明。設計が間違っていた場合に最小の傷で分かる形にする。データは5種・8技・攻撃技のみ。

実装

  • GameData interface による依存性注入 — core はデータを静的 import しない
  • toBattlePokemon — 3つの出どころ (実個体 / 設計図 / BattleSet) を入口で1つに正規化。levelOverride が後のレベル同期の入口
  • step(data, state, actions) — 「状態＋入力 → 新状態＋イベント列」の純関数。呼び出し元の state は不変
  • シード固定の疑似乱数 (xorshift32)。消費回数も状態に保持
  • ダメージ計算・18×18 タイプ相性・命中判定・急所・PP消費・優先度・素早さ順
  • Action 型は4種すべて定義し、move のみ実装

完了条件の達成

  • 達成 ランダムAI同士が1,000戦して例外なく決着 (無限ループ検出つき)
  • 達成 同一シードで2回流して結果が完全一致

実装して判明したこと

設計文書に「わるあがき」の記述が無かった。 PP が尽きると両者が行動不能になり、バトルが永久に終わらない。 完了条件が「1,000戦が例外なく決着する」なので、ここで必ず引っかかる。 文書レビューを5回やっても出てこなかった種類の穴で、実装したから見つかった。
v0.2

バトルの完成

骨格の上に、バトルとして成立するための要素を積む。データを20種41技へ拡張。

実装

  • 状態異常6種＋混乱 — タイプ無効・スリップダメージ・行動阻害・解除条件
  • 能力ランク補正 (−6〜+6) — 攻撃系と命中/回避で別の倍率表。急所は相手の防御上昇と自分の攻撃下降を無視
  • 交代 — 手持ちを配列化。ひんし後は pendingSwitch で交代を要求し、その間ターンを進めない
  • 変化技と効果レジストリの本格運用 — status / confuse / flinch / statChange / heal / multiHit を追加
  • 命中判定に命中/回避ランクを反映

設計原則の実証

41技すべてが JSON のデータだけで表現できた。 技を1件追加するのに書いたコードは 0行。 新規に書いたのは「効果の種類」6つぶんのハンドラだけ。 「コンテンツを1件足すコストをゼロに近づける」という設計方針の実測値になる。

設計文書の誤りを1件修正

  • もうどくは交代でカウンタが1に戻るだけで、通常のどくには戻らない。文書は「通常のどく扱いに戻る」としていたが原作の挙動と違っていた

v0.4

データ基盤とカントー151種

手入力から解放される回。以降の全ての版がこの基盤に乗る。20種41技 → 151種105技。

実装

  • tools/import.ts — TSV（人が編集する形式）→ JSON。種族値の合計を冗長に持ち、各能力の和と照合する。151件すべて一致
  • tools/gen-ids.ts — ID のユニオン型を JSON から生成。数千箇所の参照をコンパイル時に守る
  • tools/validate.ts — 設計文書のルールを機械検証に落とす。CI で回す
  • tools/scaffold.ts — 1件追加時の雛形生成

実装して判明したこと

「原作の機構を必要とする技」を威力だけ写すと、原作より強い別の技になる。 はかいこうせんは 次ターン動けない から威力150が許されている。 反動を実装しないまま入れると、単に壊れた威力150の技になる。 該当する技を NEEDS_UNIMPLEMENTED_MECHANIC として列挙し、 機構が無いのにデータが存在したら検証が落ちる形にした。5件を差し替え。
gen-ids.ts --check が何も検証せずに通っていた。 「自分が直接実行されたときだけ動く」というガードが実行環境で成立せず、 CI が静かに素通りしていた。無条件実行に変更し、終了コード1を確認した。

learnset は暫定

  • 151種の習得レベルの正確なデータが手元に無いため、規則生成した暫定値を learnsetSource: "provisional" と宣言して持つ
  • 検証が毎回「151/151 が暫定」と報告する。差し替え期限は v0.8（育成）。それまで learnset は体験に影響しない
  • 生成規則には品質条件を入れた ―― 攻撃技のタイプが必ず2種類以上（ノーマル単はゴーストに詰む）、得意な攻撃側と技の分類が噛み合う（とくこうが倍あるのに物理技だけ、を防ぐ）

バトルタワー

エンドゲームの最初の形。連戦が成立し、記録が残るところまで。特性・持ち物・ルールセット・AI basic・最小セーブ。

実装

  • 特性・持ち物の機構 — 効果35種のレジストリ。特性48種（うち37種が戦闘中に働く）・持ち物32種
  • Ruleset 駆動の施設 — 施設 = ルールセット + 相手プール + 報酬 の3データ。2つ目の施設でコードは1行も増えていない

実機検証

PWT型トーナメント

作りたかったゲームがここで動く。 マップも捕獲も無いまま、歴代のジムリーダー・四天王・ライバルと戦えるようになる。

実装

  • ネームド13人 × 2ティア — カントーのジムリーダー8人・四天王4人・ライバル。原作ティアと本気ティア
  • カップ3種 — 勝ち抜き。ティアはカップごとに解放される
  • selectParty — 原作の6体パーティから3体を選ぶ。署名ポケモンを必ず残す
  • キャラ1人を足すとティアぶんのコンテンツが増える構造（TSV に行を足すだけ）

ここで見つかった最大の欠陥

本気ティアの相手が、全員 NaN の実数値で戦っていた。 PartySpec.evs の型は6項目そろった StatSpread だったが、 データ側は「攻撃と素早さだけ」のように部分的に書いていた。 Math.floor(undefined / 4) が NaN になり、実数値が全部 NaN になる。
NaN は > 0 の比較を静かに素通りする。 そのため症状は「相手が最初から全員ひんし扱い」という形でしか表に出ず、 ワタルが60戦60敗したのを見て初めて分かった。 入口で欠けた値を埋め、実数値が有限でなければ例外を投げるようにした。

v0.7

マップ探索・野生エンカウント

3つの希望の最後のひとつ「原作のマップを再現」に最初の1歩を入れる。目標は良いマップを作ることではなく、マップを大量に流し込める仕組みを用意すること。

実装

  • イベントのインタプリタ — 18種のコマンドをレジストリで解決する。バトルと同じく core は時間を持たず、演出に当たったら中断して UI に返す
  • 移動・衝突・向き直り・段差・warp・エンカウント — すべて純関数。描画も時間も持たない
  • マップ4枚 — マサラタウン / 主人公の家 / オーキド研究所 / 1番道路。テキストの原本から変換する
  • Action.run（逃走）— 野生戦でだけ選べる。原作の逃走判定式（試行回数で成功率が上がる）
  • フラグによる分岐。NPC が消える形と、台詞が変わる形の2つ

設計判断

Tiled も Phaser も、予定していたが入れなかった。 どちらも「タイル画像を扱う」ための道具で、本作にはまだ絵が1枚もない （公式素材はリポジトリに入れられないため／game-plan.md §10）。 Tiled の価値は塗ることにあり、塗るタイルが無い。 Phaser が担当するはずだった描画は、実装したら60行ほどで足りたのに対し、 バンドルは約1MB増える。
どちらも「入れない」ではなく「入れる条件」を書いて先に進めた ―― 公式素材を実際に描き始めたとき、描画対象が数百に増えたとき。

v0.8

捕獲・育成・戦闘後シーケンス

v0.7 のマップと v0.5〜v0.6 のエンドゲームを1本に繋ぐ。完了条件は「自分で捕まえた個体を施設に持ち込める」―― この1文が満たされるとき、途中の全部が動いている。

実装

  • PokemonInstance（実在する1体） — HP・PP・状態異常・経験値・努力値・なつき度・個体値・性格がバトルをまたいで残る
  • 戦闘後シーケンス — 経験値 → レベル → 技習得 → 努力値 → なつき度 → 進化 → 図鑑の7段。core は「何が起きたか」を返すだけで、演出は UI
  • 捕獲 — ボール9種。補正は BallBonus のデータで、ボールを1種足すのは JSON を1行足すこと
  • 手持ち6匹とボックス — 二重所属を Storage の関数でしか触れない形にして禁じる
  • 図鑑・公式 learnset（技 105 → 247）・進化 72件・経験値テーブル6種

レベルを個体に持たせない

PokemonInstance が持つのは累計経験値だけで、レベルはそこから導く。 二重に持つと必ずずれる ―― 「レベルアップしたのに経験値が足りない個体」は、 保存と読み込みを挟んだ瞬間に生まれる。

公式データをどう入れたか

v0.4 の learnset は規則生成の暫定データで、原作の習得レベルではなかった。 v0.8 で @pkmn/dex（Pokémon Showdown のデータ）を生成時のみの devDependency として使い、 第9世代 → 第8世代 → 第7世代の順に落として取り込んだ。

世代種備考
第9世代99そのまま採用
第8世代40剣盾に居ない種のフォールバック
第7世代12さらに古い種
律速は learnset ではなく技の数だった。 公式 learnset を入れた直後の技の充足率は 39% ―― 半分以上の技が 「まだ実装していない効果」だった。技を 105 → 247 に増やしてようやく形になる。 入れなかった 155 件は source/moves-todo.tsv に理由つきで残している （効果を表せない／場の効果／制約が強さを釣り合わせている 等）―― 入れていないことと入れ忘れを区別できるようにするため。

v1.1-f ―― 世界が「消える」だけでなく「動く」ようになった

ここまで世界の変化はすべて消えるものだった（どけた岩・見つけた隠しアイテム・ 条件で入れ替わるオブジェクト）。消えるものはどこへ消えたかを持たなくてよい。 押せる岩は行き先を持つので、初めて「動いた位置」という状態が要った ―― WorldState.moved。これも保存しない（cleared と同じ扱い。 保存すると「岩を隅に押し込んで二度と解けないダンジョン」がセーブに固定される）。

差し替えは visibleObjects() の1箇所だけ。この関数はすでに 「消えるものを落とす唯一の場所」だったので、当たり判定・描画・視線・調べる が勝手に揃った ―― 押した岩の当たり判定を別に書く必要は無かった。

v1.1-h ―― Ruleset に寄せなかったのが効いた

サファリゾーンは「歩数制限・エサ/イシ・戦闘不可」という、既存のどれとも違う規則を持つ。 施設の Ruleset（teamSource / levelMode / streakCap）に寄せる案もあったが、 寄せると4施設すべてが無視する任意欄が8個増える ―― 「1件足すコストをゼロに近づける」の正反対になる。

代わりに足したのは MapData.rules の1欄だけ。 encounters: / onEnter: と同じ形なので、 2つ目のサファリは JSON 1件で増える。

決めたこと理由
歩数は保存しないcleared・moved と同じ派生値。セーブに「あと何歩」が溜まると、歩数を変えた日に古いセーブが壊れる
エサ・イシを道具にしないバッグに入ると外へ持ち出せてしまい、「その場所だけの規則」という前提が消える
BattleState.safari は真偽値にしない{rocks, baits} | null。「段階を持っているか」がそのまま「サファリか」―― 2つ持つと「サファリなのに段階が無い」が表現できる
怒りと食事を1本の軸に2つ持つと「怒りながら食べている」の意味を決めないといけなくなる
サファリは「入ったら出られる」ことが全て。

特性は約310種、持ち物は数百ある。1つずつ if を書く構造にすると、 「コンテンツを1件足すコストをゼロに近づける」という中心原則が崩れる。技効果と同じ形にした。

const heldHandlers = {

AI ― 情報を型で制限する

AI に BattleState をそのまま渡さない。 渡すと、実装者が無意識に「相手の手持ち・技・持ち物を知っている」前提のコードを書いてしまい、 一度そうなると剥がせない。AiView という制限された型を渡して機械的に縛る。 
type AiView = {
  own: { active; party; activeIndex };          // 自分のものは全部見える
  foe: {
    species; level; types;
    hpRatio;          // 割合だけ。実数値は見えない
    status; statStages;
    revealedMoves;    // 一度使われた技だけ
    revealedParty;    // 一度場に出た個体だけ
  };
  turn; legal;
};

相手の実数値は種族値・レベル・個体値31・努力値0 から推定する。 実際より低く出ることが多いが、basic の判断には十分な精度になる。 相手の特性・持ち物は推定に混ぜない ―― 見えないものは使わない。

mistakeRate の傾きが緩いことが分かった。 定義どおり「スコア上位3手からランダムに選ぶ」ため、 候補が4〜6手しかないバトルでは上位3手がほぼ全体になり、 それでも全手から等確率に選ぶ random よりずっと強い。

悪手の回帰テスト

  • 相性0倍の技を選ばない ／ PP切れの技を選ばない
  • 満タンの相手に回復技を撃たない ／ HPが減っていれば回復する
  • すでに状態異常の相手に状態異常技を撃たない
  • 倒せる技があれば必ずそれを選ぶ
  • 同じ盤面では必ず同じ行動を返す（決定性）

セーブ ― 抽象化を先に、実装を後に

v0.5 で保存したのは BP と施設の記録だけだった。 だが 保存先の抽象化とマイグレーションの鎖はそのときに作った ―― 後から挟めないため。 v0.9 で世界の状態が入り、鎖は2本目になった。

v0.5 localStorage・v1

記録だけを保存する暫定実装。packages/game/src/save.ts の1ファイル、37行。

v0.9 IndexedDB・v3

共通ボックス数千体で 5MB を超えるため移行した。 差し替えたのは上の1ファイルだけで、呼び出し側は1行も変わっていない。

4バージョン先に効いた抽象化。 v0.5 の時点では SaveStore は「localStorage を呼ぶだけの interface」で、 抽象化する意味がほとんど無いように見えた。 v0.9 で localStorage → IndexedDB という非同期・別ストア構成への差し替えが 1ファイルで済んだのは、そのとき書いた4行の interface のおかげだった。 
type SaveData = {
  schemaVersion: 3;                     // 必ず最初のフィールド
  global: {                             // 地方をまたぐ（恒久）
    bp: number;
    dex: Record<SpeciesId, "seen" | "caught">;
    bag: Record<ItemId, number>;
    endgame: { facilityRecords; tournamentRecords };
  };
  pokemon: Record<uid, PokemonInstance>;  // 個体の実体
  regions: Record<RegionId, {             // 地方ごとの進行
    flags; money; badges;
    partyUids: string[]; boxUids: string[];   // 器（誰がどこに居るか）
    position; respawn;
  }>;
  settings: { battleSpeed; lossPenalty };
};

器と個体を分ける

「誰がどこに居るか」（uid の配列）と「その個体そのもの」を別に持つ。 IndexedDB でも別のオブジェクトストアに分けてあり、 ボックスに数千体入ったときに1体入れ替えるたび全体を書き直さない。

壊れ方どう扱うか理由
器に居ない個体がある消さない施設の連戦中のように、手持ちにもボックスにも居ないまま参照される場面がある
uid が食い違う個体捨てる参照しようがない
手持ちとボックスの二重所属読み込みで直す（手持ち優先）外から編集されたセーブを読むときに起きうる
器から外れた個体書き込み側で捨てる捨てる判断は「今の状態を保存する」ときにだけ確実に下せる

過去の版を CI が読み続ける

マイグレーションが壊れていることに気づくのは、常に手遅れになってから。 版を上げたら fixtures/saves/vN.json を1件足す規則にして、 CI が全ての過去版を最新版まで引き上げられることを毎回確かめている。

  • 現在より新しいセーブは読まずに拒否する（壊すより読めない方がよい）
  • 壊れた値は既定値に落として読み込む ―― 不正の検出ではなくクラッシュの防止のため
  • 読めなかったときに黙って新規データを作らない
エクスポートはファイル保存ではなくテキストにした。 設計では「JSONファイルとしてのエクスポート」と書いていたが、 この遊べる版は単一 HTML として埋め込んで見ることがあり、 その中では <a download> もスクリプトからの保存も封じられている。
押しても何も起きないボタンは、バックアップ機能として最悪の形をしている。 テキストエリアに出してコピーさせる形なら必ず動く。

まだやっていないこと

設計の破損対策4つのうち、実装したのは「黙って新規データを作らない」だけ。 アトミックな書き込み・1世代前の保持・スキーマ検証は入れていない。 進行不能にはならないが、「壊れたセーブから復旧する」機能はまだ無く、 エクスポートが唯一の保険になっている。

世界 ― マップとイベントのデータ駆動

9地方で数百マップになる。だから設計の目標は「良いマップを作る」ことではなく、 マップを大量に流し込める仕組みを用意することに置いてある。

レジストリは6つ目になった

同じ形が6回目になった ―― 種類ごとにハンドラを1つ書き、残りはデータで足す。 イベントのコマンドも、ボールの補正も、道具の効果もこの形にした。 地方を追加しても種類は増えず、増えるのは JSON だけになる。

6回とも同じ判断をしている。 きずぐすり・いいキズぐすり・すごいキズぐすりは同じ heal の数値違いで、 ネットボール・クイックボール・ダークボールは同じ「条件つき倍率」の条件違い。 「全部入り」はゴールではなく設計制約という方針が、 毎回このレジストリの形になって現れる。

バトルと同じ構造にした

core は時間を持たない。演出を伴うコマンドに当たったら実行を止めて UI に返し、読み終わったら続きを実行する。 バトルが BattleEvent[] を返すのと同じ考え方で、イベントは EventEffect[] を返す。

stepEvent(runner, world)
      │
      ├─ setFlag / if / giveItem …   中断しない。まとめて処理する
      └─ message / choice / battle   ここで止めて UI に返す
                                     UI が読み終わったら、また stepEvent を呼ぶ
battle だけは原子性を保てない。 バトルは数分かかるので、途中でブラウザを閉じられるとイベントの途中状態が残ってしまう。 設計では battle はスクリプトの最後にしか書けないと決めていたが、 if や choice の枝の中にある場合を規定していなかった。
実装では 「自分の列の末尾であり、かつ祖先も全て末尾」まで縛った。 ライバル戦は「選んだ1匹に応じて相手が変わる」ため if の3分岐の底に battle があり、 最初の実データでこの規定が破れていた。

フラグは2つの形で効く

存在ごと消す

オブジェクトが condition を持つ。最初の1匹を受け取るまで、町の北口はオーキド本人が塞いでいる。フラグが立つと居なくなり、道が通る。

台詞を変える

イベントの中の if。同じ NPC が、フラグの前後で違うことを言う。条件の型は分岐・出現条件・ショップ解禁で共有していて、用途ごとに作っていない。

フラグ名は静的データ側で宣言必須にした。 タイプミスで永久に立たないフラグは、症状が出てから原因に辿り着くのが極めて難しい。 設計では「調整項目」だったが、v0.7 で必須に確定し、検証がエラーで弾くようにした。

v0.7 までの手持ちは PartySpec（「Lv5のヒトカゲ」という設計図）で、 バトルのたびに満タンで作り直されていた。そのため 野生戦に消耗が無く、遭遇そのものに意味が生まれなかった。

レベルを個体に持たせない。 持つのは累計経験値だけで、レベルはそこから導く。 二重に持つと必ずずれる ―― 「レベルアップしたのに経験値が足りない個体」は、 保存と読み込みを挟んだ瞬間に生まれる。 同じ理由で、最大HP も個体には持たせず毎回計算する。

バトルとの往復は2本の関数だけ

instanceToSpec(data, instance)   … 出るとき。今の HP を「割合」で渡す
writeBack(data, instance, after) … 戻るとき。HP・PP・状態異常・消えた持ち物だけ

HP を割合で渡すのは、施設のレベル同期で最大HPが変わっても 「半分減っている」という事実が保たれるため。 戻すときはランク補正や混乱のような「その場限りのもの」を戻さない ―― バトルの外に持ち出す意味があるものだけを選ぶ。

戦闘後シーケンスは7段

経験値 → レベル → 技習得 → 努力値 → なつき度 → 進化 → 図鑑

core が返すのは PostBattleEvent[] だけで、 「おぼえますか？」を聞くのも、進化の演出も UI の仕事。 バトル中の BattleEvent とまったく同じ形にしてある ―― 同じ構造を2度目に使うとき、設計判断は1回で済む。

器（手持ち・ボックス）は関数でしか触れない

1体が手持ちとボックスに同時に居る状態は、データとしては簡単に作れてしまう。 Storage を用意し、addCaught / withdraw / deposit / release / reorder を通してしか触れない形にした。 配列を直接編集する道を残さないので、二重所属は「気をつける」ものではなくなる。

読み込みでは個体を減らさない。 器に居ない個体を「ゴミ」として消す実装を書きかけたが、 施設の連戦中のように手持ちにもボックスにも居ないまま参照される場面がある。 プレイヤーのデータを消す方向の推測は、間違えたときに取り返しがつかない。 捨てるのは書き込み側の仕事にした。

経済 ― お金と BP を分けたまま保つ

本作の主動線は「施設を遊ぶ → BP を稼ぐ → 個体を強くする → 上位に挑む」。 お金でも同じものが買えると、この循環が二重になって薄まる。 2つの経済を分けたまま保つことが、エンドゲームの設計そのもの。

お金

その地方を攻略するための消耗品を買う。ボール・回復道具・基本的な持ち物。 地方をクリアした時点で役目が終わる。

BP

施設で稼ぐ。対戦で強い持ち物（たべのこし・こだわり系・きあいのタスキ…）と 交換できる。お金では絶対に買えない。

この原則を CI の合否にした。 #66「お金でも BP でも買える道具が無い」／#67「お金でも BP でも手に入らない持ち物が無い」。
書いた瞬間に、対戦用の持ち物14種が v0.5 からどこからも入手できないまま置かれていたことが分かった ―― 35種の持ち物効果は動いていたが、届いていたのは施設の貸しポケモンだけだった。
