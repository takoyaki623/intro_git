# ポケモン風RPG 開発方針

最終更新: 2026-08-16 / ステータス: ドラフト（v0.1 着手前）

---

## 1. この文書の目的

「どんなゲームを作るか」と「どう作れば途中で破綻しないか」を決める。
作りたいものが大きいので、スコープの扱い方を最初に固定する。

## 2. ゲームの全体像

**一本道のストーリーを進めるゲームではなく、「制覇率」で進むゲーム。**

構造は2層に分かれる。

```
┌─ 本編：地方チャレンジ ────────────────┐
│  各地方 = 独立した1本のゲーム         │  ← ポケモンを集める層
│  Lv5 から始まり殿堂入りで完結          │
│  手持ちは地方をまたいで持ち越さない     │
└───────────────┬──────────────────────┘
                │ 捕まえたポケモンは共通ボックス・共通図鑑へ永続蓄積
                ▼
┌─ エンドゲーム：横断コンテンツ ────────┐
│  歴代ネームドキャラのトーナメント       │  ← 集めたポケモンを使う層
│  ルール特化のバトル施設群              │  ← ゲームの本体はここ
└──────────────────────────────────────┘
```

進行の軸は3本。どれをどの順で進めてもよい。

1. **地方を殿堂入りする**（横に増える）
2. **図鑑を埋める**（地方をまたぐ）
3. **エンドゲームを踏破する**（縦に深まる）

### なぜ「地方を順に制覇」にしないのか

各地方は「Lv5で始まり Lv60前後で終わる」前提で設計されている。これを直列に繋ぐと、

- **レベルカーブが成立しない。** 2地方目の入口で手持ちが既にLv60。金銀がカントーを再調整したのと同じ問題が8回起きる。しかも地方を1つ足すたびに既存地方の調整をやり直すことになる。
- **「全ポケモンが出る」が死ぬ。** カントー完走時点で完成した手持ちがあると、ジョウトのLv5を捕まえる理由がない。1,025種入れても使われるのは最初の30種だけになる。
- **同じ構造の9回反復。** 合計200時間超。遊ぶ側も作る側も持たない。

地方を独立させると全て解ける。そして開発上いちばん効くのは、
**地方を追加するときに既存地方を再調整しなくてよくなる**こと。1地方 = 1リリースになる。

> 補足: 「1本の連続した旅」にこだわる場合、地方2つが上限。金銀がやったのがそれで、3つ目からは破綻する。

## 3. 3つの希望の扱い

| 希望 | 素直に実装した場合の規模（概算） | 本方針での回収先 |
| --- | --- | --- |
| 全てのポケモンが出る | 1,025種 + フォルム違い。技は約900。 | 各地方でその地方のポケモンを使わざるを得ない構造 → 自然に全種へ出番が回る。共通ボックスに蓄積。 |
| 今までの全てのトレーナーが出る | 本編累計で数千人。 | 地方内の配置 + **エンドゲームのトーナメント**。ネームドキャラはこちらが主戦場。 |
| 原作のマップを再現 | 9地方・数百マップ。1マップ数時間〜。 | 地方単位で1つずつ追加。最も工数が重いので最後に回す。 |

### 中心原則

> **「全部入り」はゴールではなく設計制約。**
> エンジン（ルール）とコンテンツ（データ）を分離し、
> コンテンツを1件足すコストが限りなくゼロに近づくように作る。

この原則を守る限り、途中で開発が止まっても「遊べるもの」が手元に残る。

## 4. 本編：地方チャレンジ

- 各地方は Lv5 スタート・8バッジ・四天王・殿堂入りで完結する独立した1本。
- **手持ちは地方をまたいで持ち越さない。** 各地方は現地のポケモンで攻略する。
- 捕まえたポケモンは共通ボックス・共通図鑑に永続的に蓄積される。
- 殿堂入りしたチームは「殿堂」に記録され、エンドゲームで使える。
- 地方は順不同に選べる（最初はカントーのみ、以降は緩い解放条件）。
- **相棒枠**: 次の地方に1体だけ連れて行ける（Lv は現地の帯に合わせて補正）。喪失感の緩和用、要調整。

## 5. エンドゲーム（ゲームの本体）

集めたポケモンの行き場であり、長期的に遊ばれる層。**マップをほぼ必要としない**ため、
個人開発と極めて相性が良い。ルールを1つ変えるだけで新コンテンツになる。

### 5.1 歴代ネームド トーナメント

ブラック2/ホワイト2の PWT（ポケモンワールドトーナメント）形式を下敷きにする。
1回のプレイで3〜4戦のトーナメントを勝ち抜く形。セッションの区切りが良い。

**難易度ティア** — 同じキャラのデータを使い回して段階的に強化する:

| ティア | 内容 |
| --- | --- |
| 原作 | 地方攻略中に戦う姿。レベル・構成とも原作準拠。 |
| **本気** | Lv50統一・持ち物あり・技構成を実戦的に・AI強化。 |
| **極** | 個体値/努力値最適化・特性と持ち物フル活用・6体・AI最強・そのキャラのコンセプトを極めた構築。 |

ティアはレベル/持ち物/技/AI強度の差し替えだけで表現する。**キャラを1人追加すれば3段階ぶんのコンテンツになる。**

**カップ（トーナメントの種類）** — 出場者プールを変えるだけで増やせる:

- 地方カップ（カントーカップ = その地方のジムリーダー・四天王・チャンピオンから抽選）
- ジムリーダーカップ（全地方のジムリーダー）
- タイプカップ（ほのおカップ等 = 該当タイプ使いのネームドが集まる）
- チャンピオンカップ（歴代チャンピオンのみ）
- 悪の組織カップ
- 究極カップ（全ネームドの「極」ティアのみ）

### 5.2 バトル施設（ルールセット駆動）

バトルフロンティアの本質は「**ルールを変えることで少ないアセットから大量のコンテンツを生む**」こと。
そのため **施設をハードコードせず、「ルールセット」というデータとして表現する。**

```ts
type Ruleset = {
  levelCap: 50 | 100 | null;              // レベル統一
  teamSize: number;
  teamSource: "own" | "rental";           // レンタル制なら育成不要で遊べる
  itemsAllowed: boolean;                  // 回復道具の持ち込み
  duplicateSpecies: boolean;              // 種族被り禁止
  winCondition: "faint" | "turnLimit";    // ターン制限＋採点（アリーナ式）
  moveSelection: "player" | "auto";       // 技を自分で選べない（パレス式）
  healBetweenBattles: boolean;
  streakLength: number | "endless";
  opponentPool: string;                   // 相手プールのID
};
```

施設 = **ルールセット + 相手プール + 報酬**。この3つのデータで1施設が定義できる。

| 施設 | ルール | 実装コスト |
| --- | --- | --- |
| バトルタワー | 素直な連勝。Lv50統一。 | 低（基準） |
| バトルファクトリー | レンタルポケモンで戦い、勝った相手から1体貰う | 低 |
| バトルアリーナ | 3ターンで判定（残HP・与ダメ・技の当たり方で採点） | 低 |
| バトルパレス | 技を自分で選べない（性格が行動を決める） | 低 |
| バトルホール | 単体で連戦。次の相手のタイプを自分で選ぶ | 低 |
| バトルキャッスル | BPを消費して回復・相手情報を購入する資源管理 | 中 |
| バトルピラミッド | ダンジョン探索＋道具制限 | **高（マップが必要）→ 後回し** |

ピラミッド以外はマップ資産をほぼ必要としない。ここが狙い目。

### 5.3 報酬と進行

エンドゲームには「続ける理由」が要る。

- **BP（バトルポイント）**: 全施設共通通貨。育成アイテム・わざマシン・レア個体・進化アイテムと交換。
- **記録**: 連勝記録、トーナメント制覇履歴、撃破したネームドとティアの一覧。
- **段階解放**: 「本気」ティアは原作ティア撃破後、「極」ティアは本気ティア撃破後に解放。

## 6. 技術スタック

| 項目 | 選定 | 理由 |
| --- | --- | --- |
| 言語 | TypeScript | 型でデータ構造を守れる。データ件数が増えるほど効く。 |
| 実行環境 | ブラウザ | 環境構築が軽く、GitHub Pages で即公開・共有できる。 |
| 描画 | Phaser 3（2D） | タイルマップ・スプライト・入力が揃っている。導入は v0.2 以降。 |
| ビルド | Vite | 設定がほぼ不要。 |
| テスト | Vitest | バトルロジックは全てユニットテストで守る。 |
| データ検証 | zod | JSONデータの形をランタイムで検証し、壊れたデータを早期に検出する。 |

## 7. アーキテクチャ

```
packages/
  core/    ルールエンジン。Phaser にもDOMにも依存しない純粋なTS。
           バトル計算・タイプ相性・レベルアップ・状態異常・ルールセット解釈。
           → ここが全ての中心。テストで守る。
  data/    JSON + zodスキーマ。種族・技・トレーナー・ネームド・ルールセット・マップ定義。
           → 増えるのはここだけ、が理想。
  game/    Phaser 層。描画・入力・シーン遷移・セーブ。
  tools/   データ検証、雛形生成、一括変換のスクリプト。
```

**依存の向きは `game → core → data` の一方向のみ。**
これによりバトルロジックをブラウザなしでCLIとテストから動かせる（= v0.1 が成立する）。

### 中核データモデル（初版イメージ）

```ts
type Species = {
  id: string;              // "pikachu"
  dexNo: number;           // 25
  name: string;            // "ピカチュウ"
  types: [Type] | [Type, Type];
  baseStats: { hp; atk; def; spa; spd; spe };
  abilities: string[];
  learnset: { level: number; move: string }[];
};

type Move = {
  id: string; name: string; type: Type;
  category: "physical" | "special" | "status";
  power: number | null; accuracy: number | null; pp: number;
  priority: number; target: Target;
  effect?: { kind: string; chance?: number; /* データ駆動の効果ID */ };
};

type Trainer = {
  id: string; name: string; class: string;   // "ジムリーダー"
  tier: "original" | "serious" | "ultimate"; // 強化ティア
  party: { species: string; level: number; moves: string[];
           item?: string; ability?: string; nature?: string }[];
  ai: "random" | "basic" | "smart";
  dialogue: { before: string; win: string; lose: string };
};
```

技の効果は `switch` の巨大な塊にせず、**効果IDとハンドラのレジストリ**にする。
新しい技を追加する = JSONを1行足す（既存の効果なら）で済むようにする。

## 8. マイルストーン

各マイルストーンは「そこで開発が止まっても遊べる／価値が残る」単位で切る。

**重要な組み替え:** エンドゲーム（バトル施設）はマップをほぼ必要としないため、
**マップより先に作れる**。しかもレンタル制にすれば育成システムすら要らない。
これにより「マップが完成しないと何も遊べない」という個人開発最大のリスクを回避する。

| 版 | 内容 | 完了条件 |
| --- | --- | --- |
| **v0.1** | バトルエンジン（UIなし・CLI/テストのみ） | 20種・40技でCPU戦が最後まで決着する。テストが緑。 |
| v0.2 | バトル画面（Phaser + HUD・技選択・演出最小限） | ブラウザで1戦を通しで遊べる。 |
| **v0.3** | **バトルタワー最小版**（レンタルチーム + 連勝式） | **マップなしで「遊べるゲーム」が成立する。** |
| v0.4 | マップ探索・野生エンカウント | 1つの町と1本の道路を歩き、野生戦に入れる。 |
| v0.5 | 手持ち・ボックス・道具・捕獲・育成・セーブ | 捕まえて育てて再開できる。 |
| v0.6 | カントー全域＋ジムリーダー8人 | ジムを順に攻略できる。 |
| **v1.0** | カントー殿堂入り + 共通ボックス/共通図鑑 | 1地方を完走し、集めたポケモンがタワーに持ち込める。 |
| v1.1 | PWT型トーナメント（カントーのネームド・「本気」ティアまで） | 歴代ネームド戦が成立する。 |
| v1.x〜 | 施設追加・地方追加・ネームド追加・「極」ティア | ここからは「入力作業」。1件追加のコストが低いことを確認する。 |

v1.0 到達時点で、拡張が**コード変更なしで可能な状態**になっていることが本当の目標。

## 9. v0.1 の詳細スコープ（次にやること）

**含む:**
- ターン制シングルバトル 1体 vs 1体
- 素早さ順の行動決定、技の優先度
- ダメージ計算（第9世代準拠：レベル・威力・攻撃/防御・タイプ一致1.5倍・相性・急所・乱数85〜100%）
- 18×18 のタイプ相性表
- 命中判定、PP消費、ひんし判定
- 状態異常5種（どく・まひ・やけど・ねむり・こおり）
- 能力ランク補正（-6〜+6）
- 交代
- **シード固定の疑似乱数**（同じシードなら同じ試合結果 → テストが書ける）
- CPU AI は "random"（弱くてよい。賢さは v0.3 以降で）

**含まない:** ダブルバトル、特性、持ち物、天候・フィールド、Zワザ/メガ/テラスタル等のギミック、経験値・レベルアップ。
（特性と持ち物はエンドゲームに必須なので v0.3〜v0.5 で入れる。影響範囲が広いのでバトルの骨格が固まってから）

**データ量:** 種族20（御三家3系統＋序盤ポケモン中心）、技40。全ポケモンは入れない。

## 10. 権利について

原作のドット絵・BGM・マップ画像をそのまま同梱して公開すると権利上の問題になる。
グラフィックとBGMは自作かフリー素材に置き換え、コードとデータのみをリポジトリで管理する方針にする。
非公開・個人利用の範囲であれば実質的な問題は生じにくいが、公開時に差し替えられるよう、
**アセットは最初から `assets/` に分離し、コードから直接パス依存しない**構造にしておく。

## 11. リポジトリ運用（git練習を兼ねる）

- `master`: 常に動く状態を保つ。
- 作業ブランチ: `feat/<内容>`、`fix/<内容>` を切って作業し、PRでマージ。
- コミットは「1つの意味の変更」単位で小さく。メッセージは何を変えたかを日本語で書く。
- マイルストーン到達時にタグを打つ（`v0.1` など）。
