# 01. バトルシステム詳細仕様

準拠世代: **第9世代**（未決事項だった準拠世代をここで確定する）
関連: [`ai.md`](ai.md) / [`named-characters.md`](named-characters.md)

---

## 1. 設計方針

- `packages/core` に置く。**Phaser・DOM・描画に一切依存しない純粋なTS。**
- バトルは「状態 + 入力 → 新しい状態 + イベント列」の純関数として表現する。
  描画層はイベント列を受け取って演出するだけ。これにより**UIなしでバトルが完走できる**（= v0.1 が成立する）。
- 乱数は**シード固定の疑似乱数**。同じシード・同じ入力なら必ず同じ結果になる。テストの前提。

### マスタデータの受け渡し ― `core` はデータを「持たない」

`core` は種族値や技の威力を知らなければ計算できない。
だが**モジュールとして直接 import すると、`core` が全データに静的に依存してしまう。**
テストで20種だけを使うこともできず、遅延ロードもできなくなる。

**決定: マスタデータは引数で渡す（依存性注入）。`core` はグローバルなデータを一切参照しない。**

```ts
interface GameData {
  species(id: SpeciesId): Species;
  move(id: MoveId): Move;
  ability(id: AbilityId): Ability;
  item(id: ItemId): Item;
  typeChart: TypeChart;
  natures: Record<NatureId, NatureModifier>;
}

// core の関数はすべて GameData を第1引数に取る
function step(data: GameData, state: BattleState, actions: [Action, Action]): StepResult;
```

- **v0.1 のテストは20種・40技だけの `GameData` を渡せる。** これが v0.1 成立の前提になる
- `packages/data` は `GameData` の**実装を提供するだけ**。`core` は interface しか知らない
- 遅延ロード（[`data-schema.md`](data-schema.md) §9）を後から入れても `core` は無変更

依存の向き `game → core → data`（[`../game-plan.md`](../game-plan.md) §7）は、
**型の依存であって実体の依存ではない**、という形にする。

### バトル参加者の正規化

バトルに出るポケモンの出どころは3つあり、**形がすべて違う**。

| 出どころ | 型 | 性質 |
| --- | --- | --- |
| プレイヤーの個体 | `PokemonInstance` | 実在する個体。HP・PP・経験値を持つ |
| ネームドのパーティ | `Party`（仕様） | 「Lv50のリザードン」という**設計図** |
| 施設の相手 | `BattleSet` | 同上。`grade` から個体値を導出 |

**`core` はこの3つを直接扱わない。** 入口で1つの型に正規化する。

```ts
function toBattlePokemon(data: GameData, source: PokemonInstance | Party[number] | BattleSet,
                         levelOverride?: number): BattlePokemon;
```

- `levelOverride` が[`progression.md`](progression.md) §12 のレベル同期を担う
- 実数値の計算（[`progression.md`](progression.md) §2）はここで1回だけ行い、
  以降バトル中は計算済みの値を使う
- **バトルエンジンは出自を区別しない**（[`data-schema.md`](data-schema.md) §5）を、
  この関数が実際に成立させている

```ts
type BattleState = { /* 不変。毎ターン新しい状態を返す */ };
type Action =
  | { kind: "move"; moveIndex: number; target?: TargetRef }   // target はダブル対応用に先に用意
  | { kind: "switch"; partyIndex: number }
  | { kind: "item"; item: ItemId; targetPartyIndex?: number } // 回復薬・ボール（capture.md §2）
  | { kind: "run" };                                          // 野生戦からの逃走
type BattleEvent = { kind: "damage" | "faint" | "statusApplied" | "statChange" | ... };

function step(state: BattleState, actions: [Action, Action]): {
  state: BattleState;
  events: BattleEvent[];
};
```

## 2. ターンの流れ

```
1. 両者の行動を受け取る
2. 行動順を決定する（§3）
3. 先攻の行動を解決 → イベント発行
4. ひんし判定。ひんしなら交代を要求
5. 後攻の行動を解決 → イベント発行
6. ひんし判定
7. ターン終了処理（§7 状態異常のスリップダメージ等）
8. ひんし判定 → 勝敗判定
```

**交代・道具・逃走は攻撃より常に先に処理される**（優先度の外側の扱い）。

### 道具と逃走（v0.1 の Action に含める）

捕獲（[`capture.md`](capture.md) §2）も、戦闘中の回復薬も、**ターンの行動として実行される**。
`Action` にこれらがないと、そもそも野生ポケモンを捕まえられない。

| 行動 | 挙動 | 可否 |
| --- | --- | --- |
| ボールを投げる | 捕獲判定（[`capture.md`](capture.md) §2）。成功でバトル終了 | 野生戦のみ |
| 回復薬などの道具 | `ItemEffect` を適用（[`economy.md`](economy.md) §6） | `Ruleset.itemsAllowed` に従う |
| 逃げる | 素早さ比較で成否判定。成功でバトル終了 | 野生戦のみ |

トレーナー戦・施設では、ボールと逃走は**選択肢に出さない**。
道具の可否は [`endgame.md`](endgame.md) §4 の `Ruleset.itemsAllowed` が決める。

**v0.1 では `Action` の形だけ用意し、`item` / `run` の中身は v0.7〜v0.8 で実装する。**
型を後から広げると、行動順の処理を書き直すことになる。

## 3. 行動順の決定

1. **道具・逃走・交代 > 技**（この3つは常に技より先に処理される）
2. **技の優先度**（`priority`）の降順。でんこうせっか +1、まもる +4、など
3. **実効素早さ**の降順。まひ時は ×0.5、ランク補正を適用
4. **同速の場合は乱数**で決定

## 4. ダメージ計算

### 基礎ダメージ

```
base = floor( floor( floor(2 × Lv / 5 + 2) × 威力 × A / D ) / 50 ) + 2
```

- `A` = 物理なら攻撃、特殊なら特攻（ランク補正適用後）
- `D` = 物理なら防御、特殊なら特防（ランク補正適用後）

### 補正の適用順

| 順 | 補正 | 倍率 |
| --- | --- | --- |
| 1 | 複数対象 | 0.75（ダブル時。v0.1 対象外） |
| 2 | 天候 | 1.5 / 0.5（v0.1 対象外） |
| 3 | 急所 | **1.5** |
| 4 | 乱数 | 0.85 〜 1.00（16段階の整数から抽選） |
| 5 | タイプ一致（STAB） | 1.5（てきおうりょくなら 2.0） |
| 6 | タイプ相性 | 0 / 0.25 / 0.5 / 1 / 2 / 4 |
| 7 | やけど | 0.5（物理技のみ。こんじょう等は除外） |
| 8 | その他 | 持ち物・特性・半減実など |

**各段階で切り捨て。最低ダメージは 1**（相性0倍の「こうかがない」は除く）。

### タイプ相性

18×18 の相性表は **`data/type-chart.json` にデータとして持つ**。コードに埋め込まない。
第6世代以降の仕様に準拠（フェアリー追加、はがねの ゴースト/あく 耐性は削除済み）。

```ts
type TypeChart = Record<Type, Record<Type, 0 | 0.5 | 1 | 2>>;  // 攻撃側 → 防御側
```

複合タイプは両方の倍率を掛け合わせる（最大4倍、最小0.25倍）。

## 5. 命中判定

```
実効命中率 = 技の命中率 × 命中ランク補正(命中ランク − 回避ランク)
```

- 命中ランクと回避ランクの差を -6〜+6 にクランプしてから倍率を引く
- `accuracy: null` の技は**必中**（判定をスキップ）

## 6. 能力ランク補正

範囲は **-6 〜 +6**。攻撃系と命中/回避で倍率表が異なる。

| ランク | 攻撃・防御・特攻・特防・素早さ | 命中・回避 |
| --- | --- | --- |
| +6 | 4.0 | 3.0 |
| +2 | 2.0 | 1.67 |
| +1 | 1.5 | 1.33 |
| 0 | 1.0 | 1.0 |
| -1 | 0.67 | 0.75 |
| -2 | 0.5 | 0.6 |
| -6 | 0.25 | 0.33 |

```
攻撃系:   n ≥ 0 → (2 + n) / 2      n < 0 → 2 / (2 + |n|)
命中/回避: n ≥ 0 → (3 + n) / 3      n < 0 → 3 / (3 + |n|)
```

**交代するとランク補正はリセットされる。**

## 7. 急所

| 急所ランク | 発生確率 |
| --- | --- |
| 0 | 1/24 |
| 1 | 1/8 |
| 2 | 1/2 |
| 3以上 | 必ず急所 |

- 倍率 **1.5**
- **急所時は相手の防御上昇ランクと自分の攻撃下降ランクを無視する**

## 8. 状態異常

同時に1つのみ。既に状態異常なら新たに付与されない。

| 状態 | 効果 | 解除 |
| --- | --- | --- |
| **どく** | ターン終了時に最大HPの 1/8 減少 | 交代では解除されない |
| **もうどく** | ターン終了時に 最大HP × n/16（n = 経過ターン数、毎ターン増加） | 交代でカウンタが1に戻る。**もうどく自体は解除されない**（v0.2 実装時に修正。当初「通常のどくに戻る」と書いていたが原作の挙動と異なっていた） |
| **まひ** | 素早さ **×0.5**、行動時 **25%** で行動不能 | — |
| **やけど** | ターン終了時に最大HPの **1/16** 減少、**物理技の威力が半減** | — |
| **ねむり** | **1〜3ターン**行動不能 | ターン経過で自然回復 |
| **こおり** | 行動不能。行動しようとするたび **20%** で自然解凍 | ほのお技を受けると即解凍 |

### タイプによる無効

- どく／もうどく: どく・はがね タイプは無効
- やけど: ほのお タイプは無効
- まひ: でんき タイプは無効
- こおり: こおり タイプは無効

### 混乱（状態異常とは別枠。重複する）

- 1〜4ターン継続
- 行動時 **1/3** の確率で自分を攻撃（威力40・タイプなしの物理技を自分に。急所なし）
- **交代で解除される**

## 9. 交代とひんし

- 交代は常に最速で処理される
- **交代でリセットされるもの**: 能力ランク、混乱、しめつけ等の拘束
- **交代でリセットされないもの**: 状態異常、残りHP、PP
- 全てのポケモンがひんしになった側の負け
- ひんし時は次のポケモンを選ぶまでターンが進まない

## 10. 乱数

```ts
interface Rng {
  next(): number;              // [0, 1)
  int(maxExclusive: number): number;
  chance(probability: number): boolean;
  pick<T>(items: T[]): T;
}
```

- **シード固定の疑似乱数**（xorshift 等の単純な実装で十分）
- `BattleState` がシードと呼び出し回数を保持する → **リプレイ・再現が可能**
- テストでは固定シードを使い、「このシードならこの技は必ず急所」といった検証を書く

**乱数を使う箇所を1箇所に集約する。** `Math.random()` を `core` 内で直接呼ぶことを禁止する
（lint ルールで機械的に禁止する）。

## 10.5 バトル終了後の処理（戦闘後シーケンス）

**「バトル終了イベントに戦闘結果を含める」の一行しかなかった部分。**
経験値・努力値・進化・図鑑・賞金は、それぞれ別の章で設計されているが、
**誰がいつ実行するかが、どの章にも書かれていなかった。**

`core` の別モジュールが、決まった順序で1回だけ実行する。

```ts
function applyBattleResult(data: GameData, save: SaveData, result: BattleResult): {
  save: SaveData;
  notifications: PostBattleEvent[];   // レベルアップ・進化・技習得の提案をUIへ
};
```

### 実行順（この順序が重要）

| 順 | 処理 | 定義章 |
| --- | --- | --- |
| 1 | 参加個体に**経験値を付与**（周回加速の倍率を適用） | [03](progression.md) §7 |
| 2 | **レベルアップ判定** → 実数値の再計算 | [03](progression.md) §2 |
| 3 | **技習得の提案**（レベル技。4つ埋まっていれば入れ替えを問う） | [03](progression.md) §8 |
| 4 | **努力値を付与**（倒した種族の獲得努力値） | [03](progression.md) §4 |
| 5 | **なつき度を更新** | [03](progression.md) §11 |
| 6 | **進化判定**（§下記） | [03](progression.md) §11 |
| 7 | **図鑑を更新**（対面した種を `seen`、捕獲した種を `caught`・色違いなら `shinyCaught`） | [04](capture.md) §6 |
| 8 | **賞金を加算**（トレーナー戦のみ） | [12](economy.md) §4 |
| 9 | **HP・PP・状態異常を個体へ書き戻す** | ― |
| 10 | **オートセーブ** | [09](save-data.md) §6 |

**2 の前に 4 を行わない。** 努力値はレベルアップ後の実数値計算に影響するため、
順序が変わると計算結果が変わる。

### 進化判定のタイミング（未定義だった）

| 契機 | 判定する条件 |
| --- | --- |
| **バトル終了後（レベルアップした個体のみ）** | `level` / `friendship` / `knownMove` / `location` |
| 道具を使ったとき | `item` / `link`（つながりのヒモ） |

- 進化はプレイヤーがキャンセルできる（原作準拠）
- 進化すると `learnset` が変わるため、**3（技習得）より後に置く**。
  進化後の技は次のレベルアップから提案される

### レンタル個体は対象外

`teamSource: "rental"`（[`endgame.md`](endgame.md) §4）の個体は実体を持たないため、
1〜6・9 をすべて飛ばす。図鑑（7）も更新しない ―― **レンタルで見た種で図鑑が埋まると、
収集の意味が失われる。**

## 11. 技の効果のデータ表現

技を追加するたびにコードを書き換える構造にしない。
**効果IDとハンドラのレジストリ**にする。

```ts
type MoveEffect =
  | { kind: "status"; status: StatusId; chance: number }
  | { kind: "statChange"; target: "self" | "foe"; stat: StatId; stages: number; chance: number }
  | { kind: "drain"; ratio: number }
  | { kind: "recoil"; ratio: number }
  | { kind: "multiHit"; min: number; max: number }
  | { kind: "flinch"; chance: number }
  | { kind: "heal"; ratio: number }
  | ...;

const effectHandlers: Record<MoveEffect["kind"], EffectHandler> = { ... };
```

**新しい技の追加 = JSONを1行足す**（既存の効果の組み合わせなら）。
新しい `kind` が必要な技だけコードを書く。1,000近い技を扱う上での生命線。

### 原作と違うと分かっていて入れた技（v1.2-c）

**「入れていない」と「違う形で入れた」を分ける。** 入れていないものは
`moves-todo.tsv` に理由つきで残る。ここに書くのは、**入れたが原作と違うもの**
―― 表からは読み取れないので、書き残す場所がここしか無い。

| 技 | 原作 | この世界 | なぜ |
| --- | --- | --- | --- |
| ひみつのちから | 追加効果が**場所で変わる**（草むらなら ねむり、水上なら こうげき低下…） | 常に 30% で まひ（原作の平地と同じ） | バトルは場所を知らない。`BattleState` に地形を持たせると、捕獲・出現・描画のどれと同じ地形なのかが決まらなくなる |
| からげんき | 状態異常のとき威力2倍。**やけどの攻撃半減も無視する** | 威力2倍だけ | やけどの半減はダメージ計算の別の段にあり、技ごとの例外を1つ作ることになる |

## 12. v0.1 のスコープ

### 含む

シングルバトル1対1 / 行動順決定 / ダメージ計算 / タイプ相性 / 命中判定 / 急所 /
PP消費 / 状態異常5種 + 混乱 / 能力ランク補正 / 交代 / ひんしと勝敗判定 / シード固定乱数 /
AI は `random`

### 含まない（拡張ポイントを空けておく箇所）

| 未実装要素 | 空けておく拡張ポイント |
| --- | --- |
| 特性 | ダメージ計算・状態異常付与・行動順に**フック機構**を用意しておく |
| 持ち物 | 同上。ターン終了処理にもフックが要る |
| 天候・フィールド | `BattleState` に `field` スロットを最初から持たせる（中身は空でよい） |
| ダブルバトル | `Action` と対象指定を**最初から配列前提**で設計する |
| メガ/Z/テラスタル | 各ターンに「バトル開始時の1回限りの宣言」枠を空けておく |
| 経験値・レベルアップ | バトル終了イベントに戦闘結果を含める（計算は `core` の別モジュール） |

### 導入時期の確定

「v0.3〜v0.5」と幅を持たせていたが、**v0.5 のバトルタワーが `BattleSet`（持ち物を含む）を
要求する**ため、幅のままでは成立しない。以下に確定する。

| 要素 | 導入 | 根拠 |
| --- | --- | --- |
| **持ち物** | **v0.5（必須）** | `BattleSet` が持ち物前提（[`endgame.md`](endgame.md) §6） |
| **特性** | **v0.5（必須）** | 同上。`BattleSet.ability` がある |

> **v0.5 で入れるのは「機構」であって、全種類ではない。**
> 特性は約310種、持ち物は数百あるが、v0.5 で必要なのは
> **フックとレジストリが動き、数十種が正しく機能すること**。
> 残りは技と同じくデータとして順次足す（[`data-schema.md`](data-schema.md) §7）。

#### v0.5 実装時の判断（実装後に追記）

**1. 特性と持ち物でレジストリを分けない。**
両者を別々に設計していたが、実装すると効果が実際に重なった
（あついしぼう＝特性 と タイプ半減の実＝持ち物、がんじょう と きあいのタスキ）。
分けると同じ効果を2回書くことになるため、
**`HeldEffect` という1つの語彙に統一し、ハンドラも1つのレジストリにまとめた。**
`Ability.effect` と `Item.held` が同じ型を指す。

**2. `inert` を明示的な効果として持つ。**
ようりょくそ（天候）・メロメロボディ（メロメロ）のように、
**まだ機構が無い特性**が48種中11種あった。
これを「効果なし」として黙って入れると、動かない特性が静かに増える。
`{ kind: "inert", reason: "..." }` として理由つきで持ち、検証が件数を報告する。
§11 の未実装技を検証で弾く方針（`NEEDS_UNIMPLEMENTED_MECHANIC`）と同じ考え方。

**3. `Move.contact` をデータとして持つ。**
せいでんき・ゴツゴツメットは接触技にだけ反応する。
接触かどうかは**分類から導けない**（じしんは物理だが非接触、ドレインキッスは特殊だが接触）ため、
技データの列として持つ。

**4. `legalActions` が `GameData` を取るようになった。**
こだわり系の技固定・とつげきチョッキの変化技禁止・じりょくの交代封じは、
すべて「どの行動が選べるか」の問題なので選択肢の側で解く。
バトル本体で弾くと、**UI が選べない行動を表示してしまう。**

**5. 反動・吸収でひんしになっても `faint` が出ていなかった（v0.2 からの欠陥）。**
`effects.ts` が `currentHp` を直接書き換えていたため、
ひんし判定を持つ経路を通っていなかった。勝敗判定は別経路で正しく動いていたので
バトルは壊れていなかったが、**UI に「たおれた!」が出ない**。
HP を動かす手段を `hurt` / `heal` として1組にまとめ、
`effects.ts` と特性・持ち物のフックはそれを受け取る形にした。
| 天候・フィールド | v1.2 | ネームドの `tactic` に必要（[`ai.md`](ai.md) §5） |
| ダブルバトル | **v1.2 以降** | `Ruleset.battleFormat` は定義だけ先に置き、`"single"` のみ受け付ける |
| メガ/Z/テラスタル | 未定（v1.x 以降） | 地方ごとのギミック。該当地方の実装時に判断 |

**特性と持ち物はエンドゲームに必須**（[`named-characters.md`](named-characters.md) の強化ティアが
持ち物前提）なので、v0.5 で必ず入れる。**そのためのフックだけは v0.1〜v0.2 で用意しておく。**
後から差し込む形にすると、ダメージ計算を全面的に書き直すことになる。

ダブルバトルは `Ruleset` に型として存在するが**エンジンが未対応の期間がある**。
その間は検証スクリプトで `battleFormat: "double"` のデータを弾く。

## 13. テスト方針

`core` は UI に依存しないため、全てユニットテストで守れる。

- **計算式**: 既知の値で検証（例: Lv50 の特定の組み合わせでダメージが期待範囲に入る）
- **タイプ相性**: 18×18 の全組み合わせをデータ検証
- **状態異常**: 各状態の付与・効果・解除を個別に
- **決定性**: 同じシード・同じ入力を2回流して同一の結果になること
- **完走テスト**: ランダムAI同士を1,000戦させて、例外なく決着すること（無限ループ検出）

最後の完走テストが v0.1 の完了条件。

## 14. 調整項目（実装後に決める）

- 演出の待ち時間・イベントの粒度
- AI の思考の重さ（1ターンの計算時間の上限）
- ダメージ計算の丸め位置の細部（原作との差異が体感に影響するか）
