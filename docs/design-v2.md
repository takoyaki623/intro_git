# 第2版 設計 ― 不便の解消と「旅の終わり」

いまのゲームは「町 → 道 → ジム」を2回くり返したところで、**終わりがないまま止まる**。
この設計は、遊んで見つかった4つの不便を直したうえで、旅にゴールと物語の背骨を入れる。

対象ブランチ: `claude/pokemon-style-game-s4v9rf`

---

## Phase G ― 不便4点の修正

### G-1／G-2. 「交代できない」と「HPバーが1テンポ遅い」は同じ原因

`src/game/battle.js:129`:

```js
const foeAction = chooseAction(ctx.foe, ctx.mine, ctx.rng, ctx.trainer?.skill ?? 0);
const actions = mine.type === 'move' ? [mine, foeAction] : [foeAction];   // ← ここ
```

**こちらの行動が「わざ」でないとき、選んだ行動そのものが捨てられている。**
`chooseCommand()` は `{ type:'switch', index }`（`battle.js:175`）や `{ type:'item', ... }`（同 169）を
ちゃんと返しているのに、ターンの実行ループに乗らない。結果:

- **交代**: ポケモンを選ぶ → 何も起きず、敵の攻撃だけ飛んでくる。
- **どうぐ**: 回復そのものは `PartyScene.js:161` の中で先に適用されてしまっている。
  一方 `BattleScene` の `dispHP`（表示用のHP）は `hpTween` エフェクトでしか追いつかないので、
  **次に何かがHPを動かすまでバーが止まったまま**＝「1テンポ遅い」。

#### 直しかた ― どうぐと交代を「正式な1手」に格上げする

```js
// battle.js
const foeAction = chooseAction(ctx.foe, ctx.mine, ctx.rng, ctx.trainer?.skill ?? 0);
const actions = orderActions([mine, foeAction], ctx.rng);   // mine を必ず含める
for (const act of actions) {
  if (ctx.over) break;
  yield* executeAction(ctx, act);
}
```

`executeAction()` に2本の分岐を足す:

```js
if (act.type === 'switch') return yield* doSwitch(ctx, act.index);
if (act.type === 'item')   return yield* doItem(ctx, act.item, act.target);
```

```js
function* doSwitch(ctx, index) {
  const out = ctx.mine, next = state.party[index];
  yield msg(`もどれ！ ${displayName(out)}！`);
  yield anim('recall');
  resetBattleState(out);              // 能力ランク・こんらんを解除（本家準拠）
  ctx.mine = next;
  ctx.participants.add(next);         // 経験値の分配に参加させる
  yield anim('switchIn');
  yield msg(`ゆけっ！ ${displayName(next)}！`);
  yield { t:'hpTween', onFoe:false };
}

function* doItem(ctx, item, target) {
  const r = applyItem(target, item);              // ← 効果はここで初めて適用する
  consumeItem(item);
  yield msg(`${state.player.name}は ${item.name}を つかった！`);
  yield { t:'hpTween', onFoe:false };             // ← 直後にバーが動く
  for (const line of r.messages) yield msg(line); // 「HPが かいふくした！」など
}
```

**あわせて必要な変更:**

1. `applyItem(mon, item)` を `src/game/monster.js` に切り出し、`PartyScene`・`BagScene`・`battle.js` の
   3か所が同じ実装を呼ぶようにする。いまはフィールド用の適用処理が `PartyScene` の中に埋まっている。
2. `BagScene` / `PartyScene` に `selectOnly: true` を足す。バトル中は**選ぶだけ**にして、
   適用は `battle.js` に任せる（＝二重適用と表示ズレの再発を構造的に防ぐ）。
3. `executeAction()` の対象は**実行時に `ctx` から引き直す**。
   選択時に `act.target` を固定すると、交代後に敵が「もういない前のポケモン」を殴る。
   現状 `const target = user === ctx.mine ? ctx.foe : ctx.mine;` になっているのでこの規律は維持する。
4. `PartyScene` の `mode:'switch'` で、**ひんしと現在の先頭は選べない**ようにグレーアウト。
5. 交代は優先度6（`priorityOf`）なので、敵のわざより先に出る。ここは既存のままでよい。

#### 回帰テスト（`tests.html` に追加）

- `chooseCommand` が返す全 `type`（move / item / switch / ball / run）について、
  **battleLoop が必ず1手として消費する**ことをスクリプト実行で確認する。
- どうぐ使用後、`hpTween` エフェクトが**次のメッセージより前に**yield される順序を検査。
- 交代後、`ctx.mine` が選んだ個体に入れ替わり、能力ランクが 0 に戻ることを検査。

### G-3. 文字が重なる

`src/engine/font.js:38`:

```js
const adv = m.measureText(ch).width > SIZE * 0.7 ? FULL_W : HALF_W;   // 12 か 6 の二択
```

**送り幅を 6px か 12px に丸めているのに、字形は実測幅のまま焼いている。**
システムフォント（Yu Gothic / IPAPGothic など）はプロポーショナルなので、
実測 6〜8.4px の文字 ―― 数字、英字、一部の記号 ―― は
**「6px しか進まないのに 8px 描かれる」** ことになり、次の文字に食い込む。
`HP 21/21` や `Lv 12` のような数字まじりの表示で目立つのはこのため。
さらに `fillText(ch, 1, SIZE)` の 1px の左オフセットも送り幅に入っていない。

#### 直しかた ― 幅の判定を実測基準にし、はみ出す字は詰めて焼く

レイアウト側（HP枠・メニュー・折り返し）が 6/12 のグリッドを前提にしているので、
**グリッドは崩さず、字形のほうを送り幅に収める**:

```js
function bakeGlyph(ch) {
  const w = m.measureText(ch).width;
  const full = m.measureText('あ').width;          // 全角の実測を基準にする
  const adv  = w > full * 0.75 ? FULL_W : HALF_W;  // SIZE*0.7 という当て推量をやめる

  m.save();
  if (w > adv) m.scale(adv / w, 1);                // はみ出すぶんだけ横に詰める
  m.fillText(ch, 0, SIZE);                         // 左オフセットの 1px も廃止
  m.restore();
  // …以降、2値化は今のまま
}
```

12px＋2値化では横方向の詰めは目視でほぼ分からず、重なりだけが消える。
`CELL` は 16 のままで足りる（全角 12px + 影 1px）。

#### 回帰テスト

ゲーム内で実際に使われる文字を `SPECIES` / `MOVES` / `ITEMS` / `MAPS`（台詞・看板）から
すべて集め、各文字について **焼き上がったインクの右端 ≤ `charWidth(ch)`** を検査する。
これで「どこかの台詞に入れた記号1文字で崩れる」が二度と起きない。

### G-4. 御三家の交換をクリア後にする

いま3人とも `src/data/maps/center.js`（はじまりのむらのセンター、58〜91行）にいる。

**移設先: はじまりのむらのセンターのまま、殿堂入り後にだけ現れる。**

- 理由: 旅を終えて出発点に戻る動線ができる（「そらをとぶ」の使い道にもなる）。
  新規マップが不要で、Phase K に必要な作業がほぼゼロで済む。
- 出し分けは Phase H で入れる **NPC の `when:` 条件**（後述）で行う:

```js
{ id:'tradeGirl', x:6, y:4, sprite:'girl', when:'hallOfFame', lines:[ … ] }
```

- クリア前は、同じ場所に別のNPCを1人置いて
  「いつか つよい トレーナーが ここに あつまるらしいよ」程度の伏線にする。
- **副次的な効果**: 選ばなかった御三家2種はクリア後にしか手に入らなくなるので、
  **図鑑の完成そのものがクリア後の目的になる**。Phase K の図鑑報酬と噛み合う。

## Phase H ― エンジンの土台

以降の全部がここに乗る。順番として先にやる。

### H-1. NPC・どうぐの出現条件 `when:` / `unless:`

いまマップの `npcs` は静的配列で、フラグによる出し分けができない。

```js
// data/maps/*.js
{ id:'rival1', x:9, y:12, sprite:'rival', when:'gotStarter', unless:'rival_beat_1', … }
```

`src/game/world.js` がマップ読み込み時に `state.flags` で絞る。
**これ1つでライバルの出現、クリア後の交換NPC、イベントの進行がすべて解ける。**
`items` と `warps` にも同じフィールドを効かせる（リーグの門を「バッジ2つで開く」など）。

### H-2. 固定シンボル `statics`（ぬしポケモン）

```js
statics: [
  { x:12, y:5, id:10, lv:8,  flag:'boss_route1', lines:['グルル…'] },
]
```

- フィールドに**普通のポケモンのドット絵で立っている**。話しかける／ぶつかると戦闘。
- 倒す or 捕まえるとフラグが立って消える。逃げた場合は残る。
- 配置案: １ばんどうろ ぬしポッポ Lv8 ／ トキワのもり ぬしバタフリー Lv15 ／
  おつきみやま ぬしゴローン Lv25 ／ ３ばんどうろ ぬしギャラドス Lv32。
- **マップに「目的地」ができる**のが本質。通り道が寄り道になる。

### H-3. もちもの（held item）

- `items.js` に `hold:{ … }` を追加。`mon.held`（道具名 or null）を持たせ、セーブに含める。
- v1 は3種だけ:
  | 道具 | 効果 |
  |---|---|
  | `オボンのみ` | HPが半分以下になったら 1/4 回復（1回だけ） |
  | `たべのこし` | 毎ターン終わりに 最大HPの 1/16 回復 |
  | `きあいのハチマキ` | ひんしになるダメージを 10% の確率で HP1 で耐える |
- 差し込み口: `endOfTurn()` に `endTurnHeal`、`damageMon()` の後に `pinchHeal`、
  ダメージ確定前に `endure`。
- UI: `PartyScene` に「もたせる／あずかる」、`SummaryScene` に表示欄。
- **とくせいを入れずに読み合いを増やす**のがねらい。未知の `hold.kind` は黙って無視する
  （データがエンジンより先行しても落ちない、既存の方針どおり）。

### H-4. むしよけスプレー・あなぬけのヒモ

- `むしよけスプレー` `{ kind:'repel', steps:100 }` → `state.repelSteps` を減算。
  `encounter.js` の先頭で 0 より大きければ遭遇なし。切れたら「スプレーの ききめが きれた！」。
- `あなぬけのヒモ` `{ kind:'escape' }` → `state.lastEntrance` へワープ。
  `world.js` のワープ処理で **`outdoor:false` のマップに入った瞬間に入口を記録**しておく。
- ショップの品ぞろえ（でんきバッジ以降）に追加。money の使い道が増える。

### H-5. 戦闘速度

`settings.js` に `battleSpeed: 'おそい' | 'ふつう' | 'はやい'` を追加し、
`hpTween` の速度・`anim` の長さ・`wait` のフレーム数に係数を掛ける。
加えて **Bを押しているあいだは演出を早送り**（文字送りと同じ手ざわり）。

## Phase J ― ポケモンリーグと殿堂入り（エンディング）

### 追加するマップ

```
おつきみやま ちか１かい ─ ３ばんどうろ ─ リーグ前のセンター ─ ポケモンリーグ（回廊）
```

- **３ばんどうろ**: クリア前の最後の育成場所。Lv26〜32 の野生。ぬしギャラドス。
- **リーグ前のセンター**: ここが最後の回復・ショップ。`when:'badge_iwa'` で門が開く。
- **ポケモンリーグ**: 1枚の回廊マップ。**入ったら回復もセンターもなしで4連戦**。
  - 四天王までは作らない。**3人＋チャンピオン（ライバル）**で十分に「最後」の重さは出る。
  - 各部屋の扉は前の相手を倒すまで開かない（`warps` の `when:` を使う）。

| 相手 | タイプ | パーティ | レベル |
|---|---|---|---|
| エリート1 | むし／どく | 3体 | 30〜32 |
| エリート2 | みず | 3体 | 32〜34 |
| エリート3 | いわ／じめん | 4体 | 34〜36 |
| チャンピオン（ライバル） | 混成 | 5体 | 36〜38 |

### 殿堂入り演出 `src/scenes/HallOfFameScene.js`

1. 画面が白へ → 「○○は チャンピオンに なった！」
2. 手持ちを1体ずつ、ドット絵＋名前＋Lv で順に表示（1体ごとに音）
3. スタッフロール（この作りかたの記録＝データ・エンジン・音の担当を並べる）
4. `flags.hallOfFame` を立てて**自動セーブ** → タイトルへ
5. 「つづきから」の枠に **★** と殿堂入り回数を表示

### レベル上限に対する種族数の問題（重要な前提）

いま25種、最大 Lv22 の設計。Lv38 のリーグを作るなら、**種族をあと8〜10足したい。**
足さないと、リーグのパーティが既存25種の使い回しになって最終戦が軽くなる。

追加案（すべて既存のタイプ表と進化方式でまかなえる）:
イーブイ＋分岐3種 ／ ケーシィ→ユンゲラー ／ ワンリキー→ゴーリキー ／ ロコン→キュウコン ／
マダツボミ→ウツドン ／ ニャース→ペルシアン

**この作画がフェーズ最大のコスト**なので、`placeholderSprite()` で先に組み上げてから
1体1コミットで置き換える（従来どおりの進めかた）。

## まとめ

- **G が最優先**。交代とHPバーは「壊れている」に近く、しかも原因が1か所なので費用対効果が高い。
- **H を先に作る**ことで、I・J・K が新しいエンジン改造なしに、ほぼデータ追加だけで済む。
  特に NPC の `when:` は、ライバル・クリア後の交換・リーグの門を**同じ1つの仕組み**で解く。
- **J の前に種族追加が要る**のが唯一の隠れコスト。ここだけ先に把握しておきたい。
