# 06. エンドゲーム

関連: [`named-characters.md`](named-characters.md) / [`ai.md`](ai.md) / [`progression.md`](progression.md) / [`capture.md`](capture.md) / [`regions.md`](regions.md)

---

## 1. 設計方針

**ここがゲームの本体。** 地方チャレンジは「ポケモンを集め、愛着を作る層」で、
プレイ時間の大半はこの層で消費される。

エンドゲームが個人開発と相性が良い理由:

> **マップをほぼ必要とせず、ルールを1つ変えるだけで新しいコンテンツになる。**

そのため設計の目標は「面白い施設を作る」ことではなく、
**「施設を安く量産できる構造を作る」**ことに置く。

## 2. 構造

```
┌─ トーナメント ──────────────────────┐
│  歴代ネームドが出場する勝ち抜き戦      │  有限だが密度が高い
│  3〜4戦で1セット。カップで分類        │  「誰と戦うか」が主役
└──────────────────────────────────────┘
┌─ バトル施設 ────────────────────────┐
│  ルール特化の連勝チャレンジ           │  無限に遊べる
│  段位が上がるほど相手が強くなる        │  「どう戦うか」が主役
└──────────────────────────────────────┘
        ↓ 両方から BP を得る
   BP → 育成アイテム・レア個体・幻ポケモン
        ↓
   より強い個体を作り、上位に挑む
```

## 3. 解放条件

**いずれかの地方で殿堂入りすると、エンドゲームが開放される。**

施設は**段階的に解放する**（バトルタワーが最初、以降はタワーの段位で順次）。

> 地方はロックしないのに施設はロックする理由: **地方は全て同じルールで並列**だが、
> **施設はそれぞれルールが違う。** 一度に全部見せると学習負荷が高すぎる。
> ロックの根拠は難易度ではなく、ルールの学習曲線にある。

## 4. ルールセット ― 施設を安く量産する仕組み

**施設をハードコードしない。** 施設 = **ルールセット + 相手プール + 報酬** の3データで定義する。

```ts
type Ruleset = {
  // 編成
  teamSize: number;                      // 持ち込む数
  battleSize: number;                    // 実際に戦う数（3体選出など）
  teamSource: "own" | "rental" | "hallOfFame";
  levelMode: { kind: "sync"; level: 50 | 100 } | { kind: "asIs" };
  duplicateSpecies: boolean;
  duplicateItems: boolean;
  bannedSpecies?: SpeciesId[];           // 伝説禁止など
  requiredType?: Type;                   // タイプ縛りカップ

  // バトル
  battleFormat: "single" | "double";
  itemsAllowed: boolean;                 // 回復道具の持ち込み
  winCondition: { kind: "faint" } | { kind: "turnLimit"; turns: number; judge: JudgeRule };
  moveSelection: "player" | "auto";      // 技を自分で選べない（パレス式）

  // 連戦
  streakLength: number | "endless";
  healBetweenBattles: boolean;
  carryOverDamage: boolean;              // HP/PPを次戦に持ち越す
  swapAfterWin?: "factory";              // 勝った相手から1体貰う
};
```

**`levelMode.sync` は双方向**（[`progression.md`](progression.md) §12）。
Lv50未満のポケモンも自動で50に引き上げられるため、**捕まえたばかりの個体をそのまま持ち込める。**
これがエンドゲームへの参入障壁を大きく下げる。

## 5. 施設カタログ

| 施設 | 特徴的なルール | 実装コスト |
| --- | --- | --- |
| **バトルタワー** | 標準。`teamSource: own`, Lv50同期, **1戦ごとに回復**（下記の訂正） | 低（基準） |
| **バトルファクトリー** | `teamSource: rental` + `swapAfterWin` | 低 |
| **バトルアリーナ** | `winCondition: turnLimit(8)` + 採点 | 低 |
| **バトルパレス** | `moveSelection: auto`（性格で行動決定） | 低 |
| **バトルホール** | 1体で連戦。次の相手のタイプを自分で選ぶ | 低 |
| **バトルキャッスル** | BPを消費して回復・相手情報を購入 | 中 |
| **タイプ縛りカップ** | `requiredType` を変えるだけ＋**`teamSource: own`**（§11.6） | **ほぼゼロ**（18種類作れる） |
| バトルピラミッド | ダンジョン探索＋道具制限 | **高（マップが必要）→ 後回し** |

**タイプ縛りカップは `requiredType` を差し替えるだけで18施設ぶんになる。**
ルールセット駆動にした見返りが最も分かりやすく出る例。

### 採点ルール（アリーナ式）

`turnLimit` で決着しなかった場合の判定。データとして持つ。

```ts
type JudgeRule = { criteria: ("hpRatio" | "damageDealt" | "movesHit")[] };
```

## 6. 相手はどこから来るか ―【重要】BattleSet プール

施設は無限に周回できるが、**ネームドは有限**（9地方 × 約30人）。
施設の相手を手書きすると、すぐ枯渇して「同じ相手ばかり」になる。

### 相手パーティは手書きせず、生成する

```ts
type BattleSet = {
  id: string;
  species: SpeciesId;
  moves: [MoveId, MoveId, MoveId, MoveId];
  item: ItemId;
  ability: AbilityId;
  nature: NatureId;
  evs: StatSpread;
  ivs?: StatSpread;            // 省略時は grade から決まる既定値（下記）
  grade: 1 | 2 | 3 | 4;        // 強さの段階。段位に応じてプールを切り替える
  tags: TacticId[];            // "sandstorm" 等。噛み合う組を選ぶのに使う
};
```

**個体値は `grade` から既定値を導く**（grade 1 は低め、grade 4 は全て31）。
数千件の `BattleSet` すべてに個体値を手書きさせない。
特別な調整が要る個体だけ `ivs` を明示する。

```ts
const DEFAULT_IVS_BY_GRADE = { 1: 0, 2: 10, 3: 20, 4: 31 };  // 調整項目
```

- **トレーナークラス**（エリートトレーナー、ベテラン等）ごとに使用可能な `BattleSet` プールを定義
- 段位が上がると使われる `grade` が上がる
- パーティ生成 = プールから種族が重複しないよう抽選 + `tags` の噛み合いを見る

### この設計の効き目

- **`BattleSet` を1件足す = コンテンツが増える。** 施設側のコードは触らない
- **レンタル制（ファクトリー）でも同じデータを使う。** 1つのデータが2用途
- **「全ポケモンが出る」の最も濃い回収先がここ。** 野生分布は生息地の都合で偏るが、
  施設の相手プールは**全1,025種を均等に登場させられる**。
  最初の希望が最も強く実現するのは、実は本編ではなくこの層になる

## 7. トーナメント

ブラック2/ホワイト2の PWT 形式。1回で3〜4戦。

### カップ

出場者プールを差し替えるだけで増やせる。

| カップ | 出場者プール |
| --- | --- |
| 地方カップ（9種） | その地方のジムリーダー・四天王・チャンピオン |
| ジムリーダーカップ | 全地方のジムリーダー |
| 四天王カップ | 全地方の四天王 |
| **チャンピオンカップ** | 歴代チャンピオンのみ。タイプ縛りがないため最高難度 |
| 悪の組織カップ | 各組織のボス・幹部 |
| タイプカップ（18種） | 該当タイプ使いのネームド |
| **究極カップ** | 全ネームドの「極」ティアのみ |

**出場者は毎回プールから抽選する。** 決め打ちにするとリプレイ性が消える。

### カップの解放条件 ― ネタバレを避ける

地方はロックしない（[`regions.md`](regions.md) §3）が、
**トーナメントは出場者そのものがネタバレになる。**
カントーしかクリアしていない人に、未プレイ地方のチャンピオンを見せてしまう。

> **決定: カップの出場者プールは、殿堂入り済みの地方のネームドに限定する。**

- 地方カップは、**その地方を殿堂入りすると出現する**
- 横断カップ（ジムリーダーカップ等）の出場者プールは、
  **殿堂入り済み地方のネームドだけで構成される**
- 殿堂入り地方が増えると、同じカップの顔ぶれが自然に厚くなる

カップ自体を隠すのではなく**プールが育っていく**形にすることで、
地方を1つ進めるたびにエンドゲームも豊かになる。
地方チャレンジとエンドゲームが、収集以外の線でも繋がる。

### ティア解放

```
原作ティアで優勝 → 本気ティア解放 → 制覇 → 極ティア解放
```

同じカップが3回遊べる。[`named-characters.md`](named-characters.md) §6 の3ティアが、
そのまま3周ぶんのコンテンツになる。

## 8. 難易度カーブ

施設の連勝数に応じて、相手の `BattleSet` の `grade` と AI を上げる。

| 連勝 | grade | AI（[`ai.md`](ai.md) §7） |
| --- | --- | --- |
| 1〜10 | 1 | `basic` / 誤り率 0.3 |
| 11〜20 | 2 | `basic` / 0.15 |
| 21〜30 | 3 | `smart` / 0.1 |
| 31〜40 | 4 | `smart` / 0.0 |
| 41〜 | 4 | `smart` / 0.0 / `partial` 知識 |

**10連勝ごとに施設のボス（ブレーン）が出る。**
ブレーンは `NamedCharacter` として定義するため、
[`named-characters.md`](named-characters.md) の枠組み（3ティア・`concept`・`tactic`）をそのまま流用できる。

## 9. BP経済

### 収入

| 経路 | 額 |
| --- | --- |
| 施設の連戦（節目ごと） | **連勝数が上がるほど1戦あたりの額が増える** |
| トーナメント優勝 | カップとティアに応じて |
| 初回クリアボーナス | 各施設・各カップの初回のみ大きく |

### 設計原則：作業ではなく達成に報いる

> **低段位の周回は非効率になるように、連勝数に応じて単価を上げる。**

これにより「1〜5連勝を延々繰り返して稼ぐ」が最適解にならない。
**強くなることが最も効率の良い稼ぎ方**になり、育成とエンドゲームが正しく噛み合う。

### 支出

| 用途 | 備考 |
| --- | --- |
| 育成アイテム（おうかん・ミント・とくせいパッチ・栄養ドリンク） | [`progression.md`](progression.md) §10。**主要な支出先** |
| わざマシン・教え技 | タマゴ技もここに統合 |
| レア個体・道具 | |

孵化システムを作らない代わりに、**個体を仕上げる手段が全て BP に集約される**。
「施設を遊ぶ → BPを稼ぐ → 個体を強化する → 上位に挑む」の循環が、
エンドゲームの主動線になる。

## 10. 報酬設計

### 幻ポケモンの配置

[`capture.md`](capture.md) §7 で「幻はエンドゲーム報酬」と決めた。具体化する。

> **BP交換ではなく、特定施設の特定段位への到達報酬にする。**

BP交換にすると「作業で買える」ものになり、収集の最後のピースとしての重みが消える。
**幻を手に入れるには、その施設を実際に踏破する必要がある**形にする。

### 記録

- 各施設の最高連勝記録
- トーナメントの制覇履歴（カップ × ティア）
- 撃破したネームドとティアの一覧 ―― **これが「全トレーナーが出る」の可視化。**
  何人中何人を、どのティアまで倒したかが一覧で見える形にする

## 11. データ表現

```ts
type Facility = {
  id: FacilityId;
  name: string;
  ruleset: Ruleset;
  opponentPool: { trainerClasses: TrainerClassId[]; gradeByStreak: GradeTable };
  brains: { atStreak: number; character: NamedId }[];
  rewards: {
    bp: BpTable;                                                   // 連勝数 → BP単価
    unlocks: { atStreak: number; grant: ItemId | SpeciesId }[];     // 幻ポケモン等
  };
  unlockedBy?: { facility: FacilityId; streak: number };
};

type Tournament = {
  id: CupId;
  name: string;
  ruleset: Ruleset;
  entrantPool: NamedId[];
  rounds: number;
  tierProgression: ["original", "serious", "ultimate"];
};
```

`Facility` と `Tournament` が**どちらも `Ruleset` を持つ**のが要点。
「トーナメントだけ回復あり」「この施設だけダブル」といった差分が、
コードではなくデータで表現される。

## 11.5 v0.5 実装で判明したこと（実装後に追記）

バトルタワーを実際に動かして、本章の3つの記述が**成立しないこと**が分かった。
いずれも「連戦」という形式そのものから来る問題で、机上では見えなかった。

### 訂正1: バトルタワーは1戦ごとに回復する

§5 の表は「回復なし」としていたが、**20連戦を無回復で通すのは不可能**で、
原作のバトルタワーも各戦の前に HP・PP が全回復する。
`Ruleset.healBetweenBattles: true` / `carryOverDamage: false` に訂正した。
（`carryOverDamage` は残す。バトルピラミッド型の施設で必要になる。）

### 訂正2: `grade` は個体値だけでなく努力値も割り引く

§6 は個体値だけを `grade` から導くとしていた。
だが**個体値の差は Lv50 で各能力 +7 にしかならない**のに対し、
努力値252は +31 動く。個体値だけを段階にすると `grade` がほとんど効かず、
grade 1 と grade 4 の相手が体感でほぼ同じ強さになった。

```ts
const DEFAULT_EV_RATIO_BY_GRADE = { 1: 0, 2: 0.5, 3: 0.75, 4: 1 };  // 調整項目
```

`BattleSet` に書いた努力値は「その個体の役割」を表すので、**割合だけを落とす。**
強さの段階を実際に作っているのは、個体値ではなくこちらだった。

### 訂正3 ―【重要】相手と同じ強さの個体を貸すと、連勝施設は成立しない

**本章で最も見落としていた点。**

レンタル制の施設で、相手と同じプールから貸し出すと1戦の勝率が五分になる。
すると n 連勝の確率は 0.5ⁿ になり、**連勝数の中央値は必ず1に落ち着く。**
実測（AI 同士・60回）でも、20連勝の制覇率は 0/60、平均連勝 1.4 だった。

> **連勝が伸びる施設は、序盤の相手がはっきり弱くないと成立しない。**

原作の施設ではプレイヤーが自分で育てた個体を持ち込むため、この差が自然にあった。
本作の v0.5 は全施設がレンタル制（下記）なので、差を**データとして明示する**必要がある。

```ts
type Facility = {
  rentalGrade: Grade;   // 相手の band より上に置く
  // ...
};
```

`rentalGrade: 4` / 相手 grade 1→2 にしたところ、制覇率 45/60・平均連勝 18.6 になった。
2つ目の施設（相手 grade 2→3）は 10/60・平均 11.7 で、難易度の差が出ている。
検証スクリプトが「`rentalGrade` が最初の相手 grade 以下」をエラーとして弾く。

### v0.5 では `teamSource: "own"` が成立しない

捕まえた個体が存在するのは v0.8 から。それまで手持ちという概念が無いため、
**v0.5 の全施設がレンタル制**になる。検証が `own` を明示的に弾いている。
バトルタワーが本来の `own` に戻るのは v0.8。

副産物として、**1つの `BattleSet` が相手プールとレンタルの両方に使われる**形になった。
§6 の「1つのデータが2用途」が、狙いより早く効いている。

## 11.6 v0.6 実装で判明したこと（実装後に追記）

トーナメントを実装して、**施設で得た結論がそのままでは通用しない**ことが分かった。

### レンタルの強さの正解が、施設とカップで逆になる

§11.5 では「相手と同じ強さを貸すと連勝が 0.5ⁿ で潰れる」ため、
レンタルを相手より**強く**した。トーナメントで同じことをすると逆に壊れた。

| | 施設（連戦） | カップ（勝ち抜き） |
| --- | --- | --- |
| 構造 | 勝率が n 乗される。五分だと中央値1連勝 | 3〜4戦で終わる。勝率がそのまま出る |
| 同格を貸すと | 成立しない | ちょうどよい |
| 強いものを貸すと | ちょうどよい | 原作ティアの勝率98%＝演出になる |

> **同じ「レンタルの強さ」という調整項目でも、連戦か勝ち抜きかで正解が逆になる。**

決定: `Tournament.rentalGradeByTier` を持ち、**ティアと同じ投資水準を貸す**。
原作ティア（持ち物なし・努力値なし）には grade 2、本気ティアには grade 4。

実測（AI 同士）:

| ティア | レンタル | 1戦の勝率 | 3人抜き |
| --- | --- | --- | --- |
| 原作 | grade 4 | 98% | 93%（＝演出） |
| 原作 | **grade 2** | 78% | **48%** |
| 本気 | grade 3 | 43% | 8% |
| 本気 | **grade 4** | 71% | **35%** |

### 原作パーティを3体に絞るとエースが落ちる

原作の手持ちは**弱い順に並び、エースが最後**にいる。
PWT は3対3なので、素直に先頭から3体取ると
ワタルからカイリューが、サカキからサイドンが消える。
`signature` を必ず残してから残りを埋める `selectParty` を用意し、
**検証が「選出でエースが落ちる」を弾く**ようにした。

### 専門タイプの強さの格差は、実際に数字に出た

§5 で「格差は原作の再現として受け入れる」と決めていた。
本気ティアの実測（AI 同士・各40戦、ネームド側の勝率）:

```
70% カスミ    57% ワタル    45% グリーン   43% ナツメ
30% キョウ    25% カンナ    20% サカキ     15% シバ
10% タケシ     8% マチス     5% エリカ      5% カツラ / キクコ
```

みず・ドラゴン・エスパーが上位、でんき・ほのお・ゴーストが下位。
**均さない。** 代わりに難易度はカップの編成（出場者プールと勝ち抜き数）で作る、
という §5 の方針がそのまま効いている。

## 11.6 v0.11 実装で判明したこと（実装後に追記）

### 訂正: タイプ縛りカップを「レンタルで」やると詰む

§5 は「`requiredType` を差し替えるだけで18種類作れる」としていた。
差し替えだけで済むのは**エンジンの話**としては正しい。だが実際に置いてみると、
**レンタルの候補6体にそのタイプが3体入らない限り、編成が組めない。**

数えたら grade 4 のドラゴンは `BattleSet` に **1件**しか無かった。
6体の抽選でドラゴンが3体出ることは起こらないので、
このカップは「開いた瞬間に、やめる以外に何もできない画面」になる。

**決定: タイプ縛りカップは `teamSource: "own"` にする。**
自分で育てたそのタイプで挑む。

縛りは制限ではなく、**集めた成果を使う場所**だと考えれば、こちらが本来の形だった。
「ほのおを3体そろえてから来る」こと自体が目的になる ―― レンタルで貸してもらうと、
その動機が丸ごと消える。

検証 #76 を足して、**レンタル×タイプ縛りの組み合わせを機械が止める**ようにした。
（外して試したら実際に `grade 4 の dragon が 1 件` で止まった。
検査が一度も火を噴かないなら、その検査は無いのと同じ）

### 実装した機構は2つだけだった

§5 のカタログのうち、v0.11 で足したのは次の2つ。

| 施設 | 要った機構 | どこに書いたか |
| --- | --- | --- |
| バトルファクトリー | `swapAfterWin` | `endgame/facility.ts`（36行） |
| バトルアリーナ | `winCondition: turnLimit` + 採点 | `battle.ts`（`judge()` と集計） |

**アリーナだけが `core` のバトルに触る。** ターン制限は「いつ終わるか」の規則なので、
イベント列を作る側が知っているしかない。ファクトリーは施設の進行の話なので、
バトルには一切触れていない。

採点の実装で決めたこと。

- **観点を合成しない。** 「HPの残り → 与えたダメージ → 当てた技」の順に見て、
  差がついた時点で決める。点数を足し合わせると**なぜ負けたかが読めなくなる**
- 決着の直前に `judged` イベントを出し、**どの観点で差がついたかを必ず表示する** ――
  理由が見えない判定負けは理不尽にしか見えない
- ターン制限はひんしより**後**に見る。制限ターンぴったりで倒れたなら、それは決着

アリーナは `healBetweenBattles: false` + `carryOverDamage: true` にした。
8ターンで終わるので1戦は短いが、**削られたまま次へ行く**ので連戦としては重くなる。
同じ「ターン制限」でも、回復の有無で性格が変わる ―― ここもデータの値だけで決まる。

### `swapAfterWin` は「断れる」ことが機構の一部

勝った相手から1体もらえる。**断れないと、引くほど弱くなる事故が起きる。**
交換のあとも「同じ種を重ねない」「同じ持ち物を重ねない」は守る必要があり、
守れない候補は最初から並べない（押してから断られる方が分かりにくい）。

交換したら持ち越しの HP は捨てる。**中身が変わった編成に、
前の編成の HP を当てはめる意味が無い。**
